LayerZero 跨鏈訊息

2026-09-11 · LayerZero V2 · OApp · OFT · DVN · 開發者指南

LayerZero 不是 rollup，也不是 canonical 橋。它是一條可配置的跨鏈訊息層：來源鏈的合約把 bytes 交給 Endpoint，一組你選定的驗證者（DVN）在目的鏈證明「這則封包確實存在」，再由 Executor（或任何人）呼叫目的合約。資產怎麼鎖、燒、鑄，是 OApp／OFT 自己的事，不是協議替你保證的 L1 最終性。合約作者要寫對的是 peer 的 bytes32 packing、Endpoint 守衛、enforced options、compose 的重入，以及「Executor 不是權限來源」。

把 OP／ZK 的出入金想成「L2 狀態機的門」；把 LayerZero 想成「任意兩條鏈上兩份合約之間的掛號信」。信件的真實性取決於你選的郵差，不取決於 Ethereum 的挑戰期或 zk verifier。

V2 的元件

元件職責信任
EndpointV2每條鏈一個入口；send／lzReceive、nonce、餘額不可升級的薄層（以官方部署為準）；OApp 面對的唯一介面
MessageLib（ULN 302）對封包雜湊、向 worker 派工、收驗證OApp 可選 Send／Receive lib；多數走 Ultra Light Node
DVN獨立驗證來源鏈上確有此封包安全在這裡：X of Y 的組合就是你的安全模型
Executor目的鏈上代付 gas、呼叫 lzReceive活性，不是安全；驗證過後任何人都能執行
OApp你的合約：編碼訊息、處理 _lzReceive必須自己驗證 origin.sender 是 peer

Security stack：你選的 X of Y

每條 pathway 設定兩組 DVN：

  • Required DVNs：每一個都必須提交驗證，少一個封包就不能 verified。
  • Optional DVNs + threshold：N 個候選裡要湊滿 optionalThreshold 個。

通過條件是「全部 required 且 足夠 optional」。把 LayerZero Labs、Google Cloud、某個 zk DVN、某條鏈的 native bridge adapter 塞進同一 stack，攻擊者必須同時收買或同時騙過這一批。反過來說：若 required 只有你自己的 DVN，那這條通路的安全就等於你自己的伺服器。

讀 OFT 或跨鏈治理時，先打開 getConfig／Scan 上看 Security Stack。APY 文案不會告訴你這條通路是 2-of-2 還是「單一 labs DVN」。

OApp：最小跨鏈合約

OApp 繼承官方 base，做三件事：設定 peer、送訊息、收訊息。Peer 是「目的鏈上那個被允許對我說話的 bytes32 地址」。少了這層檢查，任何人都能從任意鏈偽造 _lzReceive 的業務語意——Endpoint 只保證「這則封包被你的 DVN 驗證過」，不保證「發送者是你想要的合約」。

struct Origin {
    uint32 srcEid;
    bytes32 sender;
    uint64 nonce;
}

function send(uint32 dstEid, bytes calldata message, bytes calldata options)
    external payable
{
    _lzSend(dstEid, message, options, MessagingFee(msg.value, 0), payable(msg.sender));
}

function _lzReceive(
    Origin calldata origin,
    bytes32 guid,
    bytes calldata message,
    address executor,
    bytes calldata extraData
) internal override {
    // base 已檢查 peers[origin.srcEid] == origin.sender
    (address to, uint256 amount) = abi.decode(message, (address, uint256));
    _credit(to, amount);
}

guid 全域唯一，可當冪等鍵。nonce 對每個 (srcEid, sender, receiver) 在 Endpoint 上嚴格遞增，但 V2 預設是無序送達：nonce 3 可以在 nonce 2 之前執行。業務層若假設「先到先處理」，會被重排。要有序，必須自己 override nextNonce／_acceptNonce，並且在 send 的 options 加上 addExecutorOrderedExecutionOption()——只改合約、不加這個 option，Executor 仍會亂序嘗試，然後在你的 nonce 檢查 revert。

Peer 是 bytes32，不是 address。EVM 地址要右對齊（高位填 0）；左對齊會讓 peer 對不上，看起來「訊息過了 DVN」卻在 _lzReceive 被 OApp base revert NoPeer／OnlyPeer。非 EVM（Solana 等）本來就是 32 bytes，不要 address(uint160(uint256(peer))) 截斷。

function toPeer(address a) internal pure returns (bytes32) {
    return bytes32(uint256(uint160(a)));   // 右對齊；錯誤寫法是 bytes32(bytes20(a))
}
function fromPeer(bytes32 p) internal pure returns (address) {
    return address(uint160(uint256(p)));
}

function setPeer(uint32 eid, bytes32 peer) public onlyOwner {
    peers[eid] = peer;                     // A→B 與 B→A 要兩邊都設，互為獨立 pathway
}

_lzReceive 的 msg.sender 是 Endpoint（OApp.lzReceive 有 onlyEndpoint），不是 Executor。任何人在封包 verified 之後都能呼叫 endpoint.lzReceive；不要用 executor 參數當授權。業務層只信任 origin.srcEid + origin.sender == peers[srcEid]（base 已做）以及你自己解出來的 payload。

路徑是有向的：A 上 setPeer(eidB, peerB) 不會自動在 B 上設回來，Security Stack 也是每條方向一份。Delegate（setDelegate）可以改 DVN／options 而不必是 owner——熱錢包 delegate 等於熱錢包能改橋的安全模型。換 peer 或 MessageLib 前先暫停出站、等 Scan 上 in-flight 全部 delivered；半路把 peer 指到新合約，舊封包會卡在 NoPeer。

enforcedOptions、重入、compose

使用者可以在 send 時把 destination gas 設到 0。OApp 應繼承 OAppOptionsType3，用 _setEnforcedOptions 設下限，send／quote 走 combineOptions。同型 option 是相加，不是取 max：enforced 50_000 + 使用者 20_000 = 70_000。沒有下限，Executor 一執行就 OOG，封包停在 verified-but-unexecuted，看起來像「橋壞了」。有 compose 時還要另加 addExecutorLzComposeOption(index, gas, value)，漏了則 receive 成功、compose 永遠跑不起來。

function _lzReceive(
    Origin calldata origin,
    bytes32 guid,
    bytes calldata message,
    address /* executor */,
    bytes calldata /* extraData */
) internal override {
    (address to, uint256 amount, bytes memory composeMsg) = abi.decode(message, (address, uint256, bytes));
    _credit(to, amount);                   // 先記帳，CEI；不要在 credit 前外部呼叫
    if (composeMsg.length > 0) {
        endpoint.sendCompose(composer, guid, 0, composeMsg);  // composer 常是另一份合約
    }
}

function lzCompose(
    address fromOApp,
    bytes32 guid,
    bytes calldata message,
    address /* executor */,
    bytes calldata /* extraData */
) external {
    require(msg.sender == address(endpoint), "not endpoint");
    require(fromOApp == trustedOApp, "not oapp");  // 不要寫 address(this)，除非 composer 就是 OApp
    require(!_used[guid], "replay");       // compose 失敗會被重試，必須冪等
    _used[guid] = true;
    _handleCompose(message);
}

Compose 是同鏈、非同步的第二筆呼叫：receive 先過，再由 Executor（或任何人）跑 lzCompose。sendCompose 的第一個參數是 composer 合約，常常不是 OApp 自己；composer 裡要檢查 msg.sender == endpoint 且 fromOApp == trustedOApp，不要寫 address(this)。在 _lzReceive 裡直接 ITarget(to).onReceive{value: ...}() 很容易把 receive gas 打爆，或讓惡意 to 在 credit 完成前重入 send。需要目的鏈原生幣時，用 addExecutorNativeDropOption(amount, receiver) 讓 Executor 代轉，不要假設 _lzReceive 裡 msg.value != 0（預設是 0，除非 options 帶了 value）。

從 _lzReceive 再 _lzSend 出去（hop／ping-pong）時，來源這筆的 options 必須覆蓋目的鏈上「執行 receive + 再 quote 下一跳」的 gas。漏了，第一跳成功、第二跳永遠發不出。Foundry 用官方 TestHelperOz5（devtools-evm-foundry）：在測試裡 setUpEndpoints、部署兩份 OApp、wireOApps，然後 verifyPackets(dstEid, toAddress) 模擬 DVN+Executor。不要自己 mock Endpoint 卻忘了 nonce／peer 檢查。

Options 與 quote

Options 是給 Executor 的 gas／value 指示，用 OptionsBuilder 組，不要手拼 bytes：

bytes memory options = OptionsBuilder.newOptions()
    .addExecutorLzReceiveOption(200_000, 0);   // gas, msg.value on dst

MessagingFee memory fee = _quote(dstEid, message, options, false);
_lzSend(dstEid, message, options, fee, payable(msg.sender));

目的鏈 gas 估太低，Executor 會執行失敗，封包停在 verified-but-unexecuted。任何人（含使用者自己）可以補 gas 再執行。這不是丟錢，是「信已驗證、還沒拆」。另外還有 lzCompose：_lzReceive 先入帳，再非同步呼叫同鏈另一個合約，避免在 receive 裡做重型外部呼叫把 gas 上限打爆。

OFT：跨鏈同質代幣

OFT 是 OApp 的一種：來源 _debit，目的 _credit。預設是 burn / mint——總供給在所有鏈的加總不變。若某條鏈已有官方 canonical token（例如以太坊主網的 USDC），改用 OFT Adapter：來源鎖進 adapter，目的鏈 mint OFT；回來時 burn OFT、adapter 解鎖。

struct SendParam {
    uint32 dstEid;
    bytes32 to;
    uint256 amountLD;       // local decimals
    uint256 minAmountLD;    // 滑點／灰塵保護
    bytes extraOptions;
    bytes composeMsg;
    bytes oftCmd;
}

oft.send{value: fee.nativeFee}(sendParam, fee, refundAddress);

to 同樣是 bytes32。EVM 目標用 bytes32(uint256(uint160(recipient)))。自訂 payload 用 abi.encode／abi.decode 成對；abi.encodePacked(address) 不能再 abi.decode(..., (address))。OFT 標準路徑走 SendParam.to，弄錯 packing 代幣會鑄到 address(0) 或一個你不擁有的位址。

Adapter 鎖的是既有 ERC-20：使用者要先 approve adapter，_debit 才 transferFrom。Fee-on-transfer、rebasing、有 hook 的 token 會讓「來源扣的量 ≠ 目的鑄的量」，OFT 預設不管這件事——供給會漂。這類 token 不要套 OFT；要嘛包一層先轉成內部會計單位，要嘛拒收。

decimalConversionRate = 10^(localDecimals - sharedDecimals)。18→6 時，少於 1e12 的灰塵留在來源。UI 若顯示「全額到帳」是錯的；合約要用 _removeDust 後的 amountReceivedLD 當準。

量級控制是 OFT 自己的事，不是 Endpoint 的：官方 RateLimiter 是線性衰減的 in-flight 額度，不是每分鐘歸零的計數器。出站限額在 send 前擋下，失敗乾淨；入站限額在 credit 時擋，來源已 burn／lock，會變成「半邊完成」要能 retry。另設 pause 與每條 pathway 的 mint cap，避免單一 peer 被盜後鑄爆。

什麼時候不該用 LayerZero

需求該用原因
把 ETH 從 OP Mainnet 提回 EthereumCanonical Portal你要的是 L2 狀態機的出金，不是另一種 wrapped ETH
同一套治理／NFT／ERC-20 出現在十條鏈OApp / OFT沒有共享 L1 狀態機可推導；需要訊息層
「這就是官方 USDC」Circle CCTP 或官方 native mintOFT adapter 再包一層，對使用者是另一個 token
要繼承 rollup 的詐欺／有效性證明該 rollup 的 messengerLayerZero 的證明來自 DVN，不是 Cannon 或 zk verifier

實務上很多 L2 會同時有 canonical ETH、Circle USDC、以及若干 OFT。錢包顯示的 ticker 相同，贖回路徑與對手方完全不同。產品文案寫「跨鏈」時，要寫清走哪一扇門。

開發者檢查清單

  • 每條 pathway 顯式 setPeer，bytes32 右對齊；部署腳本把 eid ↔ 地址雙向印出來對。Peer 設錯等於把鑄幣權交給陌生人。
  • 把 Security Stack 當協議參數一樣審：required DVN 集合、optional threshold、誰有權 setConfig／setDelegate。Owner 或 delegate 熱錢包能改 DVN，等於能改橋的安全模型。
  • _lzReceive 只信 Endpoint + peer；不要用 executor 當授權。先記帳再外部呼叫；compose 必須冪等（guid 去重），composer 信的是 trustedOApp 不是 address(this)。
  • 設 enforcedOptions 下限並用 combineOptions；同型 gas 是相加。測試「使用者 gas = 0 → 只有下限」以及「仍不夠 → verified 未執行 → 手動 retry」。預設無序；要 FIFO 才加 OrderedExecution。
  • Quote 的原生手續費在來源鏈付；目的鏈 gas／native drop 在 options 裡。Hop 下一跳要把下一跳的 quote 算進這一跳的 options。
  • OFT 只與自己的 peer OFT／adapter 對打。拒絕 fee-on-transfer。Adapter 測未 approve、短收、灰塵。設 rate limit／pause／mint cap；入站限額失敗要能 retry。
  • 用 TestHelperOz5 測雙鏈 round-trip、錯 peer、亂序 nonce、compose 重試。監控 PacketSent／PacketDelivered、verified-but-not-executed 堆積、DVN 延遲。

Cross-chain messaging with LayerZero

2026-09-11 · LayerZero V2 · OApp · OFT · DVN · Developer guide

LayerZero is not a rollup and not a canonical bridge. It is a configurable messaging layer: a contract on the source chain hands bytes to an Endpoint, a DVN set you chose attests on the destination that "this packet really exists," and an Executor (or anyone) calls the destination contract. How assets lock, burn, or mint is the OApp / OFT's job — not L1 finality the protocol guarantees for you. Contract authors need peer bytes32 packing, the Endpoint guard, enforced options, compose reentrancy, and the rule that "the Executor is not an authority."

Think of OP / ZK deposits and withdrawals as doors on an L2 state machine. Think of LayerZero as registered mail between two contracts on arbitrary chains. Authenticity of the letter depends on the couriers you picked, not Ethereum's challenge period or a zk verifier.

V2 pieces

PieceJobTrust
EndpointV2One per chain; send / lzReceive, nonce, feesA thin layer (see official deployments); the only interface an OApp talks to
MessageLib (ULN 302)Hashes the packet, assigns workers, collects verificationsOApp can pick send / receive libs; most use the Ultra Light Node
DVNIndependently verifies the packet exists on the source chainSecurity lives here: your X-of-Y set is your security model
ExecutorPays gas on the destination and calls lzReceiveLiveness, not safety; anyone can execute once verified
OAppYour contract: encode the message, handle _lzReceiveMust check origin.sender is the peer

Security stack: the X of Y you choose

Each pathway configures two DVN groups:

  • Required DVNs: every one must submit a verification; miss one and the packet never becomes verified.
  • Optional DVNs + threshold: out of N candidates you need optionalThreshold of them.

The pass condition is "all required and enough optional." Put LayerZero Labs, Google Cloud, a zk DVN, and a native-bridge adapter in the same stack, and an attacker has to bribe or fool that whole set at once. Conversely: if the only required DVN is yours, this pathway's security equals your server.

When you read an OFT or cross-chain governor, open getConfig / LayerZero Scan and look at the Security Stack. The APY copy will not tell you whether the pathway is 2-of-2 or "a single labs DVN."

OApp: the smallest cross-chain contract

An OApp inherits the official base and does three things: set peers, send, receive. A peer is "the bytes32 address on the destination that is allowed to talk to me." Skip that check and anyone can forge the business meaning of _lzReceive from any chain — the Endpoint only guarantees "this packet was verified by your DVNs," not "the sender is the contract you meant."

struct Origin {
    uint32 srcEid;
    bytes32 sender;
    uint64 nonce;
}

function send(uint32 dstEid, bytes calldata message, bytes calldata options)
    external payable
{
    _lzSend(dstEid, message, options, MessagingFee(msg.value, 0), payable(msg.sender));
}

function _lzReceive(
    Origin calldata origin,
    bytes32 guid,
    bytes calldata message,
    address executor,
    bytes calldata extraData
) internal override {
    // base already requires peers[origin.srcEid] == origin.sender
    (address to, uint256 amount) = abi.decode(message, (address, uint256));
    _credit(to, amount);
}

guid is globally unique and works as an idempotency key. nonce increases strictly per (srcEid, sender, receiver) on the Endpoint, but V2 delivers unordered by default: nonce 3 can execute before nonce 2. If your business logic assumes FIFO, it will be reordered. Ordered delivery means overriding nextNonce / _acceptNonce and appending addExecutorOrderedExecutionOption() on send — change only the contract and the Executor still tries out of order, then your nonce check reverts.

A peer is bytes32, not address. EVM addresses are right-aligned (high bytes zero); left-align and the peer will not match — DVNs pass the packet, then OApp base reverts NoPeer / OnlyPeer. Non-EVM (Solana, …) is 32 bytes already; do not truncate with address(uint160(uint256(peer))).

function toPeer(address a) internal pure returns (bytes32) {
    return bytes32(uint256(uint160(a)));   // right-align; bytes32(bytes20(a)) is the bug
}
function fromPeer(bytes32 p) internal pure returns (address) {
    return address(uint160(uint256(p)));
}

function setPeer(uint32 eid, bytes32 peer) public onlyOwner {
    peers[eid] = peer;                     // A→B and B→A are separate pathways; set both
}

msg.sender in _lzReceive is the Endpoint (OApp.lzReceive is onlyEndpoint), not the Executor. Anyone can call endpoint.lzReceive after the packet is verified; do not treat the executor argument as authorization. The business layer trusts origin.srcEid + origin.sender == peers[srcEid] (base already checks) and the payload you decode.

Pathways are directional: setPeer(eidB, peerB) on A does not set the reverse on B, and the Security Stack is per direction too. A delegate (setDelegate) can change DVNs / options without being owner — a hot-wallet delegate is a hot wallet that can change the bridge's security model. Before rotating a peer or MessageLib, pause outbound and wait until Scan shows every in-flight packet delivered; pointing peer at a new contract mid-flight leaves old packets stuck on NoPeer.

enforcedOptions, reentrancy, compose

Users can set destination gas to 0 on send. The OApp should inherit OAppOptionsType3, _setEnforcedOptions a floor, and send / quote through combineOptions. Duplicate option types sum, they do not take max: enforced 50_000 + user 20_000 = 70_000. Without a floor, the Executor OOGs immediately, the packet sits verified-but-unexecuted, and it looks like "the bridge is broken." Compose also needs addExecutorLzComposeOption(index, gas, value); miss it and receive succeeds while compose never runs.

function _lzReceive(
    Origin calldata origin,
    bytes32 guid,
    bytes calldata message,
    address /* executor */,
    bytes calldata /* extraData */
) internal override {
    (address to, uint256 amount, bytes memory composeMsg) = abi.decode(message, (address, uint256, bytes));
    _credit(to, amount);                   // book first, CEI; no external calls before credit
    if (composeMsg.length > 0) {
        endpoint.sendCompose(composer, guid, 0, composeMsg);  // composer is often a different contract
    }
}

function lzCompose(
    address fromOApp,
    bytes32 guid,
    bytes calldata message,
    address /* executor */,
    bytes calldata /* extraData */
) external {
    require(msg.sender == address(endpoint), "not endpoint");
    require(fromOApp == trustedOApp, "not oapp");  // not address(this), unless the composer is the OApp
    require(!_used[guid], "replay");       // compose retries on failure; must be idempotent
    _used[guid] = true;
    _handleCompose(message);
}

Compose is a second, asynchronous call on the same chain: receive lands first, then the Executor (or anyone) runs lzCompose. The first argument of sendCompose is the composer contract, often not the OApp itself; the composer checks msg.sender == endpoint and fromOApp == trustedOApp, not address(this). Calling ITarget(to).onReceive{value: ...}() inside _lzReceive blows the receive gas cap, or lets a malicious to reenter send before credit finishes. If you need destination native token, use addExecutorNativeDropOption(amount, receiver) so the Executor transfers it; do not assume msg.value != 0 in _lzReceive (it is 0 unless options carry value).

If _lzReceive _lzSends onward (hop / ping-pong), this hop's options must cover "execute receive + quote the next hop" on the destination. Miss that and hop one succeeds, hop two never leaves. In Foundry use official TestHelperOz5 (devtools-evm-foundry): setUpEndpoints, deploy two OApps, wireOApps, then verifyPackets(dstEid, toAddress) to simulate DVN+Executor. Do not mock the Endpoint and forget nonce / peer checks.

Options and quotes

Options tell the Executor how much gas / value to use. Build them with OptionsBuilder; do not hand-roll bytes:

bytes memory options = OptionsBuilder.newOptions()
    .addExecutorLzReceiveOption(200_000, 0);   // gas, msg.value on dst

MessagingFee memory fee = _quote(dstEid, message, options, false);
_lzSend(dstEid, message, options, fee, payable(msg.sender));

If destination gas is too low, the Executor's call fails and the packet sits verified-but-unexecuted. Anyone (including the user) can top up gas and retry. That is not lost funds; it is "the letter is authenticated, not yet opened." There is also lzCompose: _lzReceive credits first, then asynchronously calls another contract on the same chain, so a heavy external call does not blow the receive gas cap.

OFT: omnichain fungible tokens

An OFT is one kind of OApp: _debit on source, _credit on destination. The default is burn / mint — total supply across all chains is conserved. If a chain already has the official canonical token (USDC on Ethereum L1, say), use an OFT Adapter instead: lock in the adapter on source, mint OFT on destination; coming back, burn OFT and unlock the adapter.

struct SendParam {
    uint32 dstEid;
    bytes32 to;
    uint256 amountLD;       // local decimals
    uint256 minAmountLD;    // slippage / dust guard
    bytes extraOptions;
    bytes composeMsg;
    bytes oftCmd;
}

oft.send{value: fee.nativeFee}(sendParam, fee, refundAddress);

to is also bytes32. EVM recipients use bytes32(uint256(uint160(recipient))). Custom payloads should abi.encode / abi.decode as a pair; abi.encodePacked(address) cannot be abi.decoded as address. The OFT standard path uses SendParam.to — wrong packing mints to address(0) or an address you do not own.

An adapter locks an existing ERC-20: the user must approve the adapter before _debit transferFroms. Fee-on-transfer, rebasing, and hooked tokens make "amount debited ≠ amount minted"; OFT does not handle that, and supply drifts. Do not wrap those tokens as OFT — either wrap into an internal accounting unit first, or reject them.

decimalConversionRate = 10^(localDecimals - sharedDecimals). From 18 to 6, dust below 1e12 stays on source. A UI that says "full amount arrives" is wrong; the contract should treat amountReceivedLD after _removeDust as truth.

Volume controls are the OFT's job, not the Endpoint's. The official RateLimiter is linearly decaying in-flight capacity, not a counter that snaps to zero. An outbound limit fails cleanly before send; an inbound limit fires at credit, after source already burned / locked — that is a half-finished state you must be able to retry. Add a pause and a per-pathway mint cap so a stolen peer cannot mint unbounded supply.

In practice many L2s host all three: canonical ETH, Circle USDC, and several OFTs. Tickers match; redemption paths and counterparties do not. When product copy says "cross-chain," name the door.

Developer checklist

  • setPeer explicitly on every pathway, bytes32 right-aligned; print eid ↔ address in both directions from the deploy script. A wrong peer is mint authority handed to a stranger.
  • Review the Security Stack like protocol parameters: required DVN set, optional threshold, who may setConfig / setDelegate. An owner or delegate hot wallet that can change DVNs can change the bridge's security model.
  • _lzReceive trusts only Endpoint + peer; do not authorize via executor. Book-keep before any external call; compose must be idempotent (dedupe on guid) and the composer trusts trustedOApp, not address(this).
  • Set an enforcedOptions floor and send through combineOptions; same-type gas sums. Test "user gas = 0 → floor only" and "still short → verified but unexecuted → manual retry." Default is unordered; add OrderedExecution only if you need FIFO.
  • Native fee is paid on source; destination gas / native drop live in options. A hop must fold the next hop's quote into this hop's options.
  • OFTs only talk to their peer OFT / adapter. Reject fee-on-transfer. For adapters, test missing approve, short receipt, and dust. Set rate limits / pause / mint cap; inbound limit failures must be retryable.
  • Use TestHelperOz5 for a two-chain round-trip, wrong peer, out-of-order nonce, compose retry. Watch PacketSent / PacketDelivered, verified-but-not-executed backlog, DVN latency.
