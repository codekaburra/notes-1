ZK Rollup：有效性證明與出入金

2026-09-11 · zkEVM · Validity Proof · Canonical Bridge · 開發者指南

ZK rollup 用有效性證明取代「先相信、再挑戰」。Sequencer 仍然排序交易、把資料發到 L1，但狀態轉換要附上一份 SNARK／STARK：L1 上的 verifier 合約驗過，這個批次在密碼學上就是合法的。出金因此不必等七天挑戰期——瓶頸改成「證明何時做出來、何時被 L1 收進」。對象同樣是合約作者：L1→L2 的 msg.sender 規則、refund 位址、L2→L1 訊息怎麼跟 finalize 配對、以及 zkEVM 跟 Ethereum 哪些 opcode 不一樣。

先對照上一則：optimistic 的安全是經濟與活性（至少一個誠實驗證者）；ZK 的安全是電路與證明系統。入金兩種 rollup 都很像（L1 鎖定 + 強制收件）；出金的等待理由完全不同。

有效性證明在保證什麼

一份 validity proof 回答的問題是：給定舊狀態根、這批交易（或 state diff）、新狀態根，是否存在一條合法的執行軌跡把它們連起來。L1 不必重放每一筆 L2 交易，只驗證明——verifier gas 大致固定。整筆 L1 成本仍隨 DA 成長（blob／calldata／state diff 的 bytes），不要把「證明便宜」當成「批次上 L1 也便宜」。

OptimisticZK
L1 相信新狀態的條件挑戰期結束且無人成功挑戰verifier 接受證明
錯誤狀態上 L1可能短暫存在，靠挑戰撤回過不了 verifier，批次不被接受
Canonical 出金約 7 天空氣牆批次 execute 之後即可（另加升級時鎖／安全委員會延遲）
運算成本L1 便宜；挑戰時才跑重型證明每批都要產證明，prover 是常態成本
新的信任面verifier 軟體、資料可用性電路正確性、trusted setup（若有）、verifier 合約、資料可用性

資料放什麼：交易 vs state diff

Validity 保證執行正確，不自動保證你能自己重建狀態。還要把資料放到 L1（或被協議承認的 DA 層），節點才能同步、使用者才能自己構造出金證明。

  • 重放型（Scroll、多數 zkEVM）：發布足夠的交易資料，完整節點可重放得出狀態。
  • State diff 型（zkSync Era）：發布狀態變更壓縮，而不是每筆原始交易。驗證者仍能重建帳戶樹；對區塊瀏覽器與除錯的意義不同。

DA 走 EIP-4844 blob 後，資料在 L1 上會過期；協議要嘛承認「blob 視窗內有人存下來就夠」，要嘛另接長期 DA。這與 optimistic rollup 相同，不是 ZK 獨有。Validium／外部 DA 則是「有證明、資料不在以太坊」——你能相信執行正確，卻可能無法自己重建狀態、也無法獨立構造出金證明。

zkEVM 的四型（你實際在跑哪一種）

Vitalik 的分類問的是：電路承諾的執行環境，離 Ethereum 有多近。越近，L1 工具與客戶端越能複用；越遠，電路越好寫、證明越快，但相容性要自己補。

型等價程度實務含義
Type 1對 Ethereum 等價可驗證甚至替換 L1 執行；電路極重，目前少見於通用 L2
Type 2對 EVM 等價Solidity／opcode 行為對齊，gas 與狀態樹可不同（Scroll 目標帶）
Type 3幾乎 EVM少數 opcode 或 precompile 改寫；多數合約能跑，邊角要測
Type 4高階語言等價編譯進自有 VM（zkSync 原生 EraVM、Starknet Cairo）；要專用工具鏈

同一條鏈會隨電路升級移動。不要拿「它叫 zkEVM」當「Foundry 測試能直接當 L1 用」。合約作者實際會踩到的差異：

點你要改的假設
zkSync native AA「EOA」也有 code。不要用 extcodesize == 0 判斷能否 transfer／擋合約。預設帳戶是合約，tx.origin 語意也不同。
pubdatazkSync 的稀缺資源是寫進 state diff 的 bytes，不是單純 L2 gas。l2GasPerPubdataByteLimit 估低，L1→L2 呼叫會失敗。
precompileType 3/4 可能缺 modexp、blake2、或 pairing 行為不同。不要假設主網通過的密碼學函式庫在 L2 相同 gas／相同輸出。
CREATE／CREATE2原生 EraVM（zksolc）的位址 derivation 與 Ethereum 不同。v27 起的 EVM Emulator 用標準 solc，CREATE2 與主網相同。兩條路徑不要混在同一個工廠。
gasleft / gas 定價Type 2 也可能改 gas schedule。用 gasleft() 做精確經濟模型會漂。

zkSync 現在兩條執行棧並存：原生 EraVM（zksolc、hardhat-zksync）與 EVM Emulator（標準 solc／Foundry）。delegatecall 不能跨這兩種 bytecode。合約要先問自己跑在哪一側，再談 CREATE2 與 gas。

入金：L1 優先佇列，L2 執行

與 optimistic 相同精神：把請求寫進 L1，L2 必須收。ZK 系統通常有一條 priority queue／mailbox，但「超時後任何人強制推進下一批」不是每條鏈都一樣：Scroll 靠 L1 訊息必須按 QueueIndex 排進區塊（Euclid 另有 permissionless batch）；zkSync 是優先佇列，強制模式依鏈配置而變；Starknet 是訊息佇列而非 EVM deposit tx。寫合約前先讀這條鏈的 forced-inclusion 文件。

zkSync 入金（示意）

struct L2TransactionRequestDirect {
    uint256 chainId;
    uint256 mintValue;
    address l2Contract;
    uint256 l2Value;
    bytes l2Calldata;
    uint256 l2GasLimit;
    uint256 l2GasPerPubdataByteLimit;
    bytes[] factoryDeps;
    address refundRecipient;
}

// Elastic Network：經 Bridgehub，不要再用 Era-only Mailbox.requestL2Transaction
bridgehub.requestL2TransactionDirect{value: amount + l2Fee}(
    L2TransactionRequestDirect({
        chainId: eraChainId,
        mintValue: amount + l2Fee,
        l2Contract: alice,
        l2Value: amount,
        l2Calldata: "",
        l2GasLimit: l2GasLimit,
        l2GasPerPubdataByteLimit: l2GasPerPubdata,
        factoryDeps: new bytes[](0),       // 經 L1 部署新合約時才需要 bytecode
        refundRecipient: alice             // 必須是 L2 上已存在的地址
    })
);

與 Arbitrum retryable 類似：L1 成功 ≠ L2 執行成功。L2 gas、pubdata 上限、refund recipient、factoryDeps 都要設對。factoryDeps 空陣列只適合作 EOA 轉 ETH；L1→L2 第一次部署合約漏傳 bytecode 會失敗。

refundRecipient 與別名：最常見的鎖死

L1→L2 失敗時，zkSync 把 mint 的 ETH 退到 refundRecipient——在 L2，不是退回 L1。若你填 L1 合約地址，L2 上的收款人是 aliased 位址（與 OP 同一 0x1111…1111 偏移）。那個門牌若沒有合約，ETH 會停在那——不要假設之後 CREATE2 部署就能救回。實務：refund 填一個 L2 上已存在的 EOA。

uint160 constant OFFSET = uint160(0x1111000000000000000000000000000000001111);
function applyL1ToL2Alias(address l1) internal pure returns (address) {
    unchecked { return address(uint160(l1) + OFFSET); }
}

address constant L1_MESSENGER = 0x0000000000000000000000000000000000008008; // L2 上的 L1Messenger

// 僅當 L1 發送者是合約：L2 msg.sender = alias(l1Contract)
// EOA 從 L1 打過來：L2 msg.sender 就是那個 EOA，沒有別名
address public immutable l1CounterpartAliased;

constructor(address l1Counterpart) {
    l1CounterpartAliased = applyL1ToL2Alias(l1Counterpart);
}

function finalizeLock(address user, uint256 amount) external {
    require(msg.sender == l1CounterpartAliased, "not L1 counterpart");
    _credit(user, amount);
}

// L2 → L1：sendToL1 的 bytes 必須與 L1 finalize 時傳入的 message 逐位相同
function requestExit(address user, uint256 amount) external {
    bytes memory message = abi.encode(user, amount);
    IL1Messenger(L1_MESSENGER).sendToL1(message);
}

applyL1ToL2Alias 與 OP／Arbitrum 同一偏移。注意差別：OP／Scroll 的守衛是 msg.sender == messenger && xDomainMessageSender() == counterpart；zkSync 的 L1→L2 交易沒有再包一層 messenger call——msg.sender 直接是（合約才別名的）L1 發送者。寫成 OP 那套會永遠 revert。L1 發送者是 EOA 時不要套 aliased 守衛。

Scroll 比較接近 OP：L1ScrollMessenger.sendMessage → L2 L2ScrollMessenger.relayMessage，守衛同樣是 messenger + xDomainMessageSender。不要假設「ZK 就等於 zkSync 的 msg.sender 模型」。

Starknet 入金是訊息，不是「同一筆 tx」

// L1：把訊息寫進 StarknetCore
starknet.sendMessageToL2{value: fee}(l2Contract, selector, payload);

// L2 Cairo：l1_handler 消費；再從 L2 出金時 send_message_to_l1
// L1 出金：對同一 payload 呼叫 consumeMessageFromL2 後才能解鎖
starknet.consumeMessageFromL2(l2Contract, payload);

Starknet 的 L1↔L2 訊息是顯式的、可重放檢查的雜湊佇列，不是 EVM 式的 deposit transaction。合約必須把「訊息已消費」當成狀態機的一環，不能假設 handler 會自動再入。

Cairo 的 l1_handler selector、payload 裡每個 felt252、uint256 拆成 low／high，都必須與 L1 sendMessageToL2 的陣列逐元素一致。L1 consumeMessageFromL2 同樣比對整份 payload 的 hash；多一個 padding、uint256 端序錯，證明過了也 consume 不了。L1 解鎖前要 require(msg.sender == starknetCore) 且自行檢查 payload 欄位——Core 只保證「這則 L2 訊息存在且未被消費」，不保證語意是你的協議。

出金：證明之後，兩種領法

使用者在 L2 燒毀或鎖定資產，並 enqueue 一則 L2→L1 訊息。等包含該訊息的批次被 L1 接受，才能在 L1 領。這裡有兩種領法，不要混用：

  • Merkle 日誌（zkSync、Scroll）：對已 execute 的批次根做 inclusion proof，再 finalizeWithdrawal。
  • 訊息雜湊佇列（Starknet）：L1 呼叫 consumeMessageFromL2(l2Contract, payload)，Core 比對雜湊；使用者不組 Merkle proof。雜湊含 L1 msg.sender，必須由預定的消費合約來呼叫。

zkSync 還要把批次生命週期分開：commit（資料上 L1）→ prove（verifier 接受）→ execute（狀態根生效、L2→L1 tree 可證）。證明過了 ≠ 可出金，要等 execute。

// zkSync：對已 execute 的批次做 Merkle 證明（Bridgehub / L1Nullifier，不要再用 finalizeEthWithdrawal）
l1Nullifier.finalizeWithdrawal(
    chainId,
    l2BatchNumber,
    l2MessageIndex,
    l2TxNumberInBatch,
    message,
    merkleProof
);

// 同一則 message 只能 finalize 一次；證明綁定已 execute 的 L2→L1 tree
// message 必須與 L2 sendToL1 的 bytes 完全相同，含 abi.encode 的 padding

L1 橋在 finalize 時通常只驗證「這則 log／message 在已執行批次的樹裡」，然後把 ETH 轉給 message 解出來的 to。若你自建 L1 escrow，不要只呼叫 proveL2MessageInclusion 就付錢：還要檢查 sender 是你的 L2 合約、selector／前綴是你的協議、這則 hash 尚未付過，並且 先 paid[hash] = true 再轉帳。官方 ERC-20 bridge 已經做了這些；自己 fork 時漏掉 sender 檢查，等於任何人只要能從任意 L2 合約 sendToL1 就能提走 escrow。

證明系統與升級

  • SNARK（Groth16、PLONK、Honk／Boojum 一類）：L1 驗證極便宜；部分系統需要 trusted setup 或 universal SRS。
  • STARK（Starknet）：無需 trusted setup，證明較大，L1 驗證較貴，常再包一層 SNARK recursive。
  • 遞迴：先把很多區塊證成一棵證明樹，L1 只驗根。這讓出金延遲取決於「根何時提交」，不是「每一塊何時單獨證明」。

電路升級等於換掉「什麼叫合法執行」。嚴肅的 ZK L2 會把 verifier 放在時鎖後面，有的還保留 Security Council 緊急路徑。讀出金延遲時，要把證明時間和治理時鎖分開算。

開發者檢查清單

  • 先確認這條鏈的 L1→L2 模型：zkSync 合約發送者是「msg.sender = 別名後的 L1 合約」，EOA 不別名；Scroll／多數 OP 風格 zkEVM 是 messenger + xDomainMessageSender。抄錯守衛會主網直接死。
  • 入金參數（L2 gas、pubdata、refund recipient、factory deps）當成會失敗的路徑來測。refund 填 L2 已有的 EOA，不要填還沒部署的 L1 合約位址，也不要賭 CREATE2 救援。
  • L2 餘額可花，不代表 L1 橋已承認這筆入金所在的批次；需要 L1 最終性的應用要等 executed batch，不要等 sequencer receipt 或只看到 prove。
  • 出金先分模型：zkSync／Scroll 是 Merkle + execute；Starknet 是 consume hash。自組 Merkle proof 是主幹 bug。L1 escrow 必須檢查 L2 sender，先標記已付再轉帳。
  • Token 對映仍是官方 bridge 清單，不是「L2 上叫 USDC 的東西」。許多 ZK 鏈同時存在 canonical ERC-20 與第三方 OFT。
  • zkSync：新代碼走 Bridgehub／L1Nullifier。不要用 extcodesize == 0 當 EOA 檢查；CREATE2 只在 EraVM 路徑與 L1 不同；測 factoryDeps 漏傳。EVM Emulator 與 EraVM 不要 delegatecall 互調。
  • 電路／verifier 升級時，舊的 withdrawal proof 可能對不上新的 tree；升級視窗要凍結出金或提供遷移路徑。

ZK Rollups: Validity Proofs and Bridging

2026-09-11 · zkEVM · Validity proof · Canonical bridge · Developer guide

A ZK rollup replaces "believe then challenge" with a validity proof. The sequencer still orders transactions and publishes data to L1, but every state transition carries a SNARK or STARK. Once the L1 verifier contract accepts it, that batch is cryptographically legal. Canonical withdrawals therefore skip a seven-day challenge window — the bottleneck becomes "when is the proof produced and included on L1." This is still a contract-author note: L1→L2 msg.sender rules, refund addresses, pairing L2→L1 bytes with finalize, and which opcodes are not Ethereum.

Contrast with the previous note: optimistic safety is economic and live (one honest verifier); ZK safety is circuits and the proof system. Deposits look alike (lock on L1 + forced inclusion); the reason you wait to withdraw is completely different.

What a validity proof actually guarantees

A validity proof answers: given the old state root, this batch of transactions (or a state diff), and a new state root, does there exist a legal execution trace connecting them? L1 does not replay every L2 transaction; it checks the proof — verifier gas is roughly constant. Total L1 cost still scales with DA (blob / calldata / state-diff bytes). Cheap proofs are not cheap batches.

OptimisticZK
When L1 trusts a new stateChallenge window ends with no successful disputeVerifier accepts the proof
A wrong state on L1Can exist briefly, then be rolled backCannot pass the verifier; the batch is rejected
Canonical withdrawal~7-day air gapAfter the batch is executed (plus any upgrade timelock / security-council delay)
Compute costCheap on L1; heavy only during a challengeEvery batch is proved; the prover is a standing cost
New trust surfaceVerifier software, data availabilityCircuit correctness, trusted setup (if any), verifier contract, data availability

What gets published: transactions vs state diffs

Validity says execution was correct; it does not automatically mean you can reconstruct state yourself. Data still has to land on L1 (or a DA layer the protocol accepts) so nodes can sync and users can build withdrawal proofs.

  • Replay style (Scroll, most zkEVMs): publish enough transaction data that a full node can replay to the state.
  • State-diff style (zkSync Era): publish compressed state changes instead of raw transactions. Verifiers can still rebuild the account tree; explorers and debugging feel different.

After EIP-4844, blob data expires on L1. The protocol either treats "someone stored it during the blob window" as enough, or plugs in longer-term DA. Optimistic rollups share this problem; it is not ZK-specific. Validium / external DA is "a proof, data not on Ethereum" — you can trust execution and still be unable to reconstruct state or build a withdrawal proof yourself.

Four zkEVM types (which one you are actually running)

Vitalik's taxonomy asks how close the circuit's execution environment is to Ethereum. Closer means L1 tools and clients reuse; farther means easier circuits and faster proving, with a custom toolchain.

TypeEquivalenceIn practice
Type 1Ethereum-equivalentCan verify or even replace L1 execution; circuits are extremely heavy, rare as a general L2
Type 2EVM-equivalentSolidity / opcode behaviour matches; gas and the state tree may differ (Scroll's target band)
Type 3Almost EVMA few opcodes or precompiles rewritten; most contracts run, edges need tests
Type 4High-level-language equivalentCompile into a custom VM (native zkSync EraVM, Starknet Cairo); you need that toolchain

A chain can move types as circuits upgrade. "It is called a zkEVM" is not "Foundry tests against L1 will just work." Differences contract authors actually hit:

PointAssumption to drop
zkSync native AA"EOAs" have code. Do not use extcodesize == 0 to decide transfer or to block contracts. The default account is a contract; tx.origin also differs.
pubdataThe scarce resource on zkSync is bytes written into the state diff, not L2 gas alone. Underestimate l2GasPerPubdataByteLimit and the L1→L2 call fails.
precompilesType 3/4 may lack modexp, blake2, or differ on pairing. Do not assume a mainnet crypto library has the same gas or the same output on L2.
CREATE / CREATE2Native EraVM (zksolc) derives addresses differently from Ethereum. The v27+ EVM Emulator uses stock solc and matches mainnet CREATE2. Do not mix the two paths in one factory.
gasleft / gas scheduleEven Type 2 may change the schedule. Precise gasleft() economics will drift.

zkSync now runs two stacks side by side: native EraVM (zksolc, hardhat-zksync) and the EVM Emulator (stock solc / Foundry). delegatecall does not cross those bytecodes. Ask which side you are on before talking CREATE2 or gas.

Deposits: L1 priority queue, L2 execution

Same spirit as optimistic rollups: write the request on L1, L2 must take it. ZK systems usually expose a priority queue / mailbox, but "after a timeout anyone force-advances the next batch" is not universal: Scroll requires L1 messages in QueueIndex order (Euclid also has permissionless batches); zkSync has a priority queue whose force mode depends on chain config; Starknet is a message queue, not an EVM deposit tx. Read that chain's forced-inclusion docs before you write the contract.

zkSync deposit (sketch)

struct L2TransactionRequestDirect {
    uint256 chainId;
    uint256 mintValue;
    address l2Contract;
    uint256 l2Value;
    bytes l2Calldata;
    uint256 l2GasLimit;
    uint256 l2GasPerPubdataByteLimit;
    bytes[] factoryDeps;
    address refundRecipient;
}

// Elastic Network: go through Bridgehub; do not use Era-only Mailbox.requestL2Transaction
bridgehub.requestL2TransactionDirect{value: amount + l2Fee}(
    L2TransactionRequestDirect({
        chainId: eraChainId,
        mintValue: amount + l2Fee,
        l2Contract: alice,
        l2Value: amount,
        l2Calldata: "",
        l2GasLimit: l2GasLimit,
        l2GasPerPubdataByteLimit: l2GasPerPubdata,
        factoryDeps: new bytes[](0),       // bytecode only when deploying a new contract via L1
        refundRecipient: alice             // must already exist on L2
    })
);

Same class of bug as Arbitrum retryables: L1 success ≠ L2 execution. L2 gas, pubdata limits, refund recipient, and factoryDeps all have to be right. An empty factoryDeps is fine for ETH to an EOA; skipping bytecode on a first-time L1→L2 deploy fails.

refundRecipient and aliasing: the usual lockup

When L1→L2 fails, zkSync refunds minted ETH to refundRecipient — on L2, not back to L1. If you pass an L1 contract, the L2 payee is the aliased address (same 0x1111…1111 offset as OP). If nothing is deployed there, ETH sits — do not assume a later CREATE2 deploy will recover it. In practice: refund an EOA that already exists on L2.

uint160 constant OFFSET = uint160(0x1111000000000000000000000000000000001111);
function applyL1ToL2Alias(address l1) internal pure returns (address) {
    unchecked { return address(uint160(l1) + OFFSET); }
}

address constant L1_MESSENGER = 0x0000000000000000000000000000000000008008; // L1Messenger on L2

// Only if the L1 sender is a contract: L2 msg.sender = alias(l1Contract)
// EOA from L1: L2 msg.sender is that EOA, no alias
address public immutable l1CounterpartAliased;

constructor(address l1Counterpart) {
    l1CounterpartAliased = applyL1ToL2Alias(l1Counterpart);
}

function finalizeLock(address user, uint256 amount) external {
    require(msg.sender == l1CounterpartAliased, "not L1 counterpart");
    _credit(user, amount);
}

// L2 → L1: sendToL1 bytes must match the message passed to L1 finalize, bit for bit
function requestExit(address user, uint256 amount) external {
    bytes memory message = abi.encode(user, amount);
    IL1Messenger(L1_MESSENGER).sendToL1(message);
}

applyL1ToL2Alias is the same offset as OP / Arbitrum. The guard differs: OP / Scroll use msg.sender == messenger && xDomainMessageSender() == counterpart. A zkSync L1→L2 transaction has no extra messenger call — msg.sender is the L1 sender (aliased only if that sender is a contract). Copying the OP guard reverts forever. Do not use the aliased guard when the L1 sender is an EOA.

Scroll is closer to OP: L1ScrollMessenger.sendMessage → L2 L2ScrollMessenger.relayMessage, same messenger + xDomainMessageSender guard. Do not assume "ZK means zkSync's msg.sender model."

Starknet deposits are messages, not "the same tx"

// L1: enqueue a message on StarknetCore
starknet.sendMessageToL2{value: fee}(l2Contract, selector, payload);

// L2 Cairo: consumed by an l1_handler; withdrawals send_message_to_l1
// L1 exit: consumeMessageFromL2 on the same payload, then unlock
starknet.consumeMessageFromL2(l2Contract, payload);

Starknet L1↔L2 messages are an explicit, replay-checked hash queue, not an EVM-style deposit transaction. Contracts must treat "message consumed" as part of the state machine; the handler will not re-enter for you.

The Cairo l1_handler selector, each felt252 in the payload, and uint256 split into low/high must match the L1 sendMessageToL2 array element for element. consumeMessageFromL2 hashes that whole payload; extra padding or the wrong uint256 limb order and you cannot consume even after the proof. Before unlocking on L1, require(msg.sender == starknetCore) and check the payload fields yourself — Core only guarantees "this L2 message exists and has not been consumed," not that it is your protocol.

Withdrawals: two ways to claim after the proof

The user burns or locks on L2 and enqueues an L2→L1 message. Only after L1 accepts the batch that contains it can they claim. There are two claim models — do not mix them:

  • Merkle logs (zkSync, Scroll): inclusion-proof against an executed batch root, then finalizeWithdrawal.
  • Message-hash queue (Starknet): L1 calls consumeMessageFromL2(l2Contract, payload); Core matches the hash. Users do not assemble a Merkle proof. The hash includes L1 msg.sender, so the intended consumer contract must be the caller.

zkSync also splits the batch lifecycle: commit (data on L1) → prove (verifier accepts) → execute (state root live, L2→L1 tree provable). Proved ≠ withdrawable — wait for execute.

// zkSync: Merkle-prove an L2 log from an executed batch (Bridgehub / L1Nullifier; not finalizeEthWithdrawal)
l1Nullifier.finalizeWithdrawal(
    chainId,
    l2BatchNumber,
    l2MessageIndex,
    l2TxNumberInBatch,
    message,
    merkleProof
);

// Each message finalizes once; the proof is bound to the executed L2→L1 tree
// message must equal the L2 sendToL1 bytes, including abi.encode padding

On finalize the L1 bridge typically checks "this log/message is in an executed batch's tree," then sends ETH to the to decoded from the message. If you roll your own L1 escrow, do not pay after proveL2MessageInclusion alone: check the sender is your L2 contract, the selector/prefix is yours, the hash has not been paid, and set paid[hash] = true before the transfer. The official ERC-20 bridge already does this; fork it without a sender check and anyone who can sendToL1 from any L2 contract drains the escrow.

Proof systems and upgrades

  • SNARKs (Groth16, PLONK, Honk / Boojum-class): verification on L1 is cheap; some need a trusted setup or a universal SRS.
  • STARKs (Starknet): no trusted setup, larger proofs, more expensive L1 verification, often wrapped in a recursive SNARK.
  • Recursion: many blocks collapse into a proof tree; L1 verifies the root. Withdrawal delay then tracks "when the root is posted," not "when each block is proved alone."

A circuit upgrade changes the definition of legal execution. Serious ZK L2s put the verifier behind a timelock; some keep a Security Council emergency path. When you read withdrawal delay, split proving time from governance timelock.

Developer checklist

  • Confirm the L1→L2 model: on zkSync a contract sender is "msg.sender = aliased L1 contract" (EOAs are not aliased); Scroll / most OP-style zkEVMs are messenger + xDomainMessageSender. The wrong guard is dead on day one.
  • Treat deposit parameters (L2 gas, pubdata, refund recipient, factory deps) as failing paths. Refund an EOA that exists on L2; do not pass an undeployed L1 contract, and do not bet on CREATE2 recovery.
  • A spendable L2 balance does not mean the L1 bridge has accepted the batch that contains the deposit. Apps that need L1 finality wait for an executed batch, not a sequencer receipt or a prove-only batch.
  • Pick the exit model first: zkSync / Scroll are Merkle + execute; Starknet is consume-hash. Hand-built Merkle proofs are the main bug factory. L1 escrow must check the L2 sender and mark paid before transferring.
  • Token mappings are still the official bridge list, not "whatever is called USDC on L2." Many ZK chains host both canonical ERC-20s and third-party OFTs.
  • zkSync: new code goes through Bridgehub / L1Nullifier. Do not use extcodesize == 0 as an EOA check; CREATE2 differs from L1 only on the EraVM path; test missing factoryDeps. Do not delegatecall between EVM Emulator and EraVM.
  • After a circuit / verifier upgrade, old withdrawal proofs may not match the new tree; freeze exits during the window or ship a migration path.
