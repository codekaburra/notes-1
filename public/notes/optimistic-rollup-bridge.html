Optimistic Rollup 的入金與出金

2026-09-11 · OP Stack · Arbitrum · Canonical Bridge · 開發者指南

Optimistic rollup 的跨鏈不是另一座任意橋，而是 L2 狀態如何從 L1 推導出來的一部分。入金會寫進 L1，再被 L2 的 derivation pipeline 收成一筆特殊交易；出金則是 L2 先承諾「這筆訊息存在」，等輸出根經過挑戰期、無人成功挑戰後，L1 才放行資產。本則以 OP Stack 為主線、對照 Arbitrum，對象是要在 L1／L2 寫合約的人：你真正要寫對的是 msg.sender、xDomainMessageSender、gas、失敗 replay，而不是「呼叫哪個 bridge UI」。

先記住安全模型

Optimistic 的意思是：proposer 先把 L2 輸出根貼上 L1，假設它是對的。任何人都可以在挑戰期內用欺詐證明／fault proof 反駁。因此 canonical 出金必須等這個視窗結束——OP Mainnet 與 Arbitrum One 都約是七天量級，不是因為轉帳慢，而是因為安全依賴「有人看、有人挑戰」。

角色做什麼信任邊界
Sequencer排序 L2 交易、給軟確認可審查、可重組自己的 unpublished 佇列；不能永久擋 L1 入金
Batcher把交易資料發到 L1 calldata／blob資料必須在 L1 可重建，否則節點無法同步
Proposer把 output root／dispute game 貼上 L1錯的根可被挑戰；fault proof 上線後不必信任單一 proposer
Verifier／Challenger重放 L2、挑戰錯誤輸出安全假設：至少一個誠實驗證者在線，且能負擔挑戰

錢包顯示「已上 L2」只是 sequencer 的軟確認。資產要能在 L1 被信任，必須等到資料上 L1、輸出根定案。

入金：L1 鎖定，L2 推導出一筆 deposit tx

使用者在 L1 把 ETH 或 ERC-20 交給 canonical bridge。OP Stack 裡這會走到 OptimismPortal.depositTransaction，發出 TransactionDeposited。每個 L2 節點（含 sequencer）依 derivation 規則，把這筆事件收成 deposit transaction（交易型別 0x7e）：先把 mint 的 ETH 記入 L2 帳戶，再執行 data 呼叫。

常見兩條路徑：

  • 只想在 L2 拿到 ETH：直接往 Portal 的 receive() 或 depositTransaction 打，L2 同位址入帳。
  • 走 StandardBridge（ETH 或 ERC-20，可指定收款人）：L1 L1StandardBridge → L1CrossDomainMessenger → Portal。L2 端由 messenger relayMessage 再叫 L2StandardBridge.finalizeBridgeETH／finalizeBridgeERC20。

地址別名

L1 合約當 sender 時，L2 上的 from／msg.sender 會加上常數偏移，避免 L1 合約與 L2 同址合約搶同一個身份。EOA 不別名。Arbitrum、zkSync 用同一條偏移。跨域訊息裡的 xDomainMessageSender 才是「對岸真實來源」——L2 應用合約不要把 deposit tx 的 msg.sender 當成 L1 使用者，那通常是 aliased messenger。

uint160 constant OFFSET = uint160(0x1111000000000000000000000000000000001111);

function applyL1ToL2Alias(address l1) internal pure returns (address) {
    unchecked { return address(uint160(l1) + OFFSET); }
}
function undoL1ToL2Alias(address l2) internal pure returns (address) {
    unchecked { return address(uint160(l2) - OFFSET); }
}

L2→L1 不會再別名一次：MessagePasser 記下的是 L2 真實地址，L1 上 xDomainMessageSender() 就是那個 L2 合約。所以 L1／L2 成對合約常見做法是 CREATE2 部署到同一個地址，各自跟對岸 messenger 驗證「sender == 我的 counterpart」，而不是驗證 msg.sender == counterpart。

Solidity：入金

interface IL1StandardBridge {
    function bridgeETHTo(address to, uint32 minGasLimit, bytes calldata extraData) external payable;
    function bridgeERC20To(
        address localToken, address remoteToken, address to,
        uint256 amount, uint32 minGasLimit, bytes calldata extraData
    ) external;
}

// ETH：Portal 鎖定；L2 由 derivation 鑄出對應餘額
L1_BRIDGE.bridgeETHTo{value: amount}(alice, 200_000, "");

// ERC-20：先 approve 給 L1StandardBridge，再鎖進 bridge
IERC20(usdc).approve(address(L1_BRIDGE), amount);
L1_BRIDGE.bridgeERC20To(usdc, l2Usdc, alice, amount, 200_000, "");

minGasLimit 是目標合約被 relay 時可用的 gas，不是整筆 deposit 的上限。Messenger 自己還要吃一截 overhead；官方建議寧可高估。設太低，L2 呼叫 revert，訊息進 failedMessages，資產可能卡在 messenger／bridge，要再 relayMessage。ERC-20 的 remoteToken 必須是官方對映；填錯會鑄到無人認得的 L2 token。

Portal 的 depositTransaction(to, value, gasLimit, isCreation, data) 裡，msg.value 會變成 L2 的 mint（先記入 from），參數 value 才是內層呼叫的 callvalue。StandardBridge 把 ETH mint 給 aliased L1 messenger，再以 callvalue 轉給 L2 bridge——自己組 deposit 時不要把兩個 value 搞反。

你的合約：跨域訊息的正確守衛

Token 橋只是 messenger 的一個客戶。自己的協議（鎖倉、治理、NFT 遷移）也走同一條管線。L2 預部署地址在每條 OP Stack 鏈都一樣：

預部署地址
L2CrossDomainMessenger0x4200000000000000000000000000000000000007
L2StandardBridge0x4200000000000000000000000000000000000010
L2ToL1MessagePasser0x4200000000000000000000000000000000000016
L1Block0x4200000000000000000000000000000000000015
GasPriceOracle0x420000000000000000000000000000000000000F
 
ICrossDomainMessenger constant MESSENGER =
    ICrossDomainMessenger(0x4200000000000000000000000000000000000007);

address public immutable l1Counterpart; // L1 上的成對合約，建構時寫死

modifier onlyFromCounterpart() {
    require(msg.sender == address(MESSENGER), "not messenger");
    require(MESSENGER.xDomainMessageSender() == l1Counterpart, "bad sender");
    _;
}

// L1 → L2：只准對岸合約經 messenger 進來
function finalizeLock(address user, uint256 amount) external onlyFromCounterpart {
    _credit(user, amount);
}

// L2 → L1：發起出金／訊息；L1 要等 prove+finalize 才收得到
function sendToL1(bytes calldata payload, uint32 minGas) external {
    MESSENGER.sendMessage(l1Counterpart, payload, minGas);
}

兩條 require 缺一不可。xDomainMessageSender 只在 messenger 正在 relay 時有意義：不綁 msg.sender，攻擊者可以在別人一筆合法 relay 的 callback 裡重入你，或讓你去讀一個假 messenger。Messenger 地址要寫死成預部署，不要當 constructor 參數隨便傳。

L1 側同一套守衛，只是 messenger 換成 L1CrossDomainMessenger（每條 L2 一個，地址不是 0x420…）。finalizeWithdrawalTransaction 成功後，Portal 會轉呼叫 L1 messenger，L1 messenger 再 call 你的 L1 合約：那時 msg.sender 是 L1 messenger，xDomainMessageSender() 是 L2 成對合約。

Foundry 測 L2 入口時不要真的跑 derivation，直接假裝 messenger：

vm.prank(address(MESSENGER));
vm.mockCall(
    address(MESSENGER),
    abi.encodeCall(ICrossDomainMessenger.xDomainMessageSender, ()),
    abi.encode(l1Counterpart)
);
app.finalizeLock(user, amount);

vm.prank(address(MESSENGER));
vm.mockCall(..., abi.encode(attacker));
vm.expectRevert("bad sender");
app.finalizeLock(user, amount);

L1Block 與 confirmation

L2 的 block.number／block.timestamp 是 L2 自己的。要錨 L1 狀態（防 sequencer 短程重組、做 L1 TWAP、驗證「這筆入金所在的 L1 區塊」），讀 L1Block predeploy，不要把 L2 timestamp 當成 L1 最終性。

interface IL1Block {
    function number() external view returns (uint64);
    function timestamp() external view returns (uint64);
    function hash() external view returns (bytes32);
    function sequenceNumber() external view returns (uint64);
    function basefee() external view returns (uint256);
    function blobBaseFee() external view returns (uint256);
}
IL1Block constant L1_BLOCK = IL1Block(0x4200000000000000000000000000000000000015);

RPC 的 latest 在 sequencer 上是 unsafe（軟確認）。safe 表示已從 L1 資料推導；finalized 跟著 L1 最終性。合約裡無法直接讀這三個標籤，但後端／Keeper 在證明出金、發跨域指令前，應等 safe 或 finalized，不要只看 sequencer receipt。

出金：L2 承諾，L1 等挑戰期

出金是三步，不能合併成一筆 L1 交易：

  1. Initiate（L2）：L2StandardBridge.bridgeETHTo／bridgeERC20To → messenger → L2ToL1MessagePasser.initiateWithdrawal。ETH 從 L2 流通量移除，訊息雜湊寫入 MessagePasser storage。
  2. Prove（L1）：等到包含該 L2 區塊的 output root 被提出（現在是 FaultDisputeGame），用 Merkle／storage proof 向 Portal 證明「這筆 withdrawal 在那份狀態裡」。
  3. Finalize（L1）：等 dispute game 解析完成，再加上最終化延遲（約七天空氣牆）。Portal 放行 ETH，或 StandardBridge 解鎖 ERC-20。

Fault proof 之後的出金

舊的 L2OutputOracle.proposeL2Output 是許可制 proposer。OP Mainnet 已改成 DisputeGameFactory 開 FaultDisputeGame（Cannon 指令集證明）：任何人都可以對某個 L2 區塊提出輸出根，也任何人都可以逐步挑戰。Portal（OptimismPortal2）只接受已 DEFENDER_WINS、且過了 proofMaturityDelay 的 game。Guardian／Security Council 仍能黑名單錯誤 game 或切回許可制——fault proof 不是「沒有治理後門」。

struct WithdrawalTransaction {
    uint256 nonce;
    address sender;
    address target;
    uint256 value;
    uint256 gasLimit;
    bytes data;
}

portal.proveWithdrawalTransaction(
    withdrawalTx,
    disputeGameIndex,
    outputRootProof,
    withdrawalProof          // MessagePasser 的 storage proof
);

// 等 game 結束 + proofMaturityDelay（約 7 天）
portal.finalizeWithdrawalTransaction(withdrawalTx);

SDK（如 @eth-optimism/sdk 的後繼、viem OP Stack actions、Superchain 官方 SDK）會幫你組 output proof 與 withdrawal proof。手刻 Merkle proof 很容易對錯 slot。

Portal 用兩個 mapping 防重放：provenWithdrawals[hash] 綁定某一局 game，finalizedWithdrawals[hash] 保證同一則 withdrawal 只放行一次。Game 被挑戰翻盤後必須重 prove。L1 應用合約被 messenger 呼叫時仍然要走 onlyFromCounterpart——Portal 不替你檢查「這則訊息是不是你的協議」。

finalize 時目標 revert，Portal 仍把這筆標成已 finalize（WithdrawalFinalized(..., false)），ETH 不會再走同一條 withdrawal hash 重放。這跟入金失敗不一樣：L1→L2 走 messenger 的訊息進 failedMessages，可以再 relayMessage；直接打 Portal 的任意 target 沒有這層。自己的 L1 合約被 messenger 呼叫時，要把「先記帳再轉 ETH」寫成可重試，不要假設 Portal 會幫你 replay。

OptimismMintableERC20 只有 L2StandardBridge 能 mint／burn。自己發「橋接代幣」卻把 mint 權交給 EOA 或任意 adapter，就不是 canonical 了。讀 l1Token() 對一下官方清單，不要只看 symbol。

Arbitrum 入金的經典坑是 retryable ticket：L1 交易成功不代表 L2 已執行。submission fee 或 L2 執行 gas 不足時，ticket 會留在 retryable 佇列，必須補費再 redeem。對使用者來說這很像「錢在橋裡消失」——其實卡在可重放的票。

// L1：Inbox.createRetryableTicket{value: l2CallValue + l2Gas + submissionFee}
// to, l2CallValue, maxSubmissionCost, excessFeeRefundAlias, callValueRefundAlias,
// gasLimit, maxFeePerGas, data
inbox.createRetryableTicket{value: msg.value}(
    l2App, 0, maxSubmissionCost,
    refundTo, refundTo, gasLimit, maxFeePerGas,
    abi.encodeCall(L2App.finalizeLock, (user, amount))
);

// L2 出金：ArbSys(0x64).sendTxToL1(l1Target, data)
// L1 收：msg.sender 是 Bridge，不是 Outbox，也不是 aliased L2 發送者
IBridge bridge = inbox.bridge();
require(msg.sender == address(bridge), "NOT_FROM_BRIDGE");
require(IOutbox(bridge.activeOutbox()).l2ToL1Sender() == l2Counterpart, "bad L2 sender");

Arbitrum 的 L1→L2 別名與 OP 同一常數。Retryable 的 excessFeeRefundAddress／callValueRefundAddress 若填 L1 合約，L2 入帳的是別名後的地址。那個門牌若沒有合約，ETH 會停在那——不要假設之後 CREATE2 部署就能救回。實務：refund 填 L2 上已存在的 EOA 或合約。這跟 zkSync 的 refundRecipient 是同一類 bug。

Canonical 橋 vs 快速橋

Across、Hop、官方 Fast Withdrawal 產品用的是流動性提供者先在目標鏈墊款，再自己去走 canonical 出金回收。使用者幾分鐘拿到資金，但對手方變成 LP 與那個協議的合約，不再是「只信任 L1 + 至少一個誠實 verifier」。

產品若顯示「L2 ETH」，要分清楚：是 canonical 鑄造／記帳的 ETH，還是 OFT、lock-mint 橋接代幣。後者的出金路徑與挑戰期無關，風險模型也完全不同——見 LayerZero 那則筆記。

開發者檢查清單

  • 所有跨域入口：msg.sender == messenger 且 xDomainMessageSender() == counterpart。Foundry 要測「假 messenger」「真 messenger + 假 sender」兩種攻擊。
  • 入金 ERC-20 只允許官方 token 對映；L2 側用 OptimismMintableERC20Factory 或官方清單，不要自己 mapping[l1] = l2 寫死未驗證地址。
  • 合約 sender 入金後，L2 msg.sender 是別名。退款／excess fee 的收款人若是 L1 合約，填 L2 上已存在的 EOA／合約；不要賭「之後部署到 aliased 位址就能救回」。
  • 出金合約不要在 L2 發起後立刻假設 L1 已解鎖。Portal 對 raw target 失敗不會 replay；messenger 路徑才有 failedMessages。L1 入口同樣要 onlyFromCounterpart（Arbitrum 則是 Bridge + l2ToL1Sender）。
  • 估 minGasLimit 含目標執行＋messenger overhead；測「gas 剛好不夠 → failedMessages → replay」。
  • 需要 L1 最終性的邏輯讀 L1Block，後端等 safe／finalized，不要用 L2 block.timestamp 或 sequencer receipt 當 L1 錨。
  • 監控 dispute game 狀態、WithdrawalProven／WithdrawalFinalized、Portal／Bridge 餘額是否覆蓋未決出金、failedMessages 堆積。
  • Sequencer 停機時，入金仍應能從 L1 推導；出金則仍受挑戰期約束。把這兩件事分開寫進 runbook。

Optimistic Rollup Deposits & Withdrawals

2026-09-11 · OP Stack · Arbitrum · Canonical bridge · Developer guide

Cross-chain movement on an optimistic rollup is not a bolt-on bridge. It is part of how L2 state is derived from L1. A deposit is written on L1 and turned into a special transaction by the L2 derivation pipeline. A withdrawal is an L2 commitment that a message exists; L1 releases funds only after the output root survives its challenge window. This note follows the OP Stack, contrasts Arbitrum, and is written for people shipping contracts on L1/L2: the parts you must get right are msg.sender, xDomainMessageSender, gas, and replay — not which bridge UI to click.

The security model first

Optimistic means a proposer posts an L2 output root to L1 and everyone assumes it is correct. Anyone may contradict it during the challenge period with a fraud / fault proof. Canonical withdrawals wait for that window — on the order of seven days on OP Mainnet and Arbitrum One — not because the transfer is slow, but because safety depends on someone watching and being able to challenge.

RoleWhat they doTrust boundary
SequencerOrders L2 transactions and issues soft confirmationsCan censor or reorder its unpublished queue; cannot permanently suppress L1 deposits
BatcherPublishes transaction data to L1 calldata or blobsData must be reconstructable from L1 or nodes cannot sync
ProposerPosts output roots / dispute games to L1A wrong root can be challenged; permissionless fault proofs remove a trusted proposer
Verifier / challengerReplays L2 and disputes bad outputsSafety assumption: at least one honest validator is live and can fund a challenge

A wallet saying "confirmed on L2" is the sequencer's soft confirmation. Assets are not L1-trusted until data is on L1 and the output root is finalized.

Deposits: lock on L1, derive a deposit tx on L2

The user gives ETH or ERC-20 to the canonical bridge on L1. On the OP Stack this reaches OptimismPortal.depositTransaction and emits TransactionDeposited. Every L2 node (including the sequencer) turns that event into a deposit transaction (type 0x7e): credit mint ETH to the L2 account, then execute data.

Two common paths:

  • Just receive ETH on L2: hit the Portal receive() or depositTransaction; the same address is credited on L2.
  • StandardBridge (ETH or ERC-20, optional recipient): L1 L1StandardBridge → L1CrossDomainMessenger → Portal. On L2 the messenger relayMessages into L2StandardBridge.finalizeBridgeETH / finalizeBridgeERC20.

Address aliasing

When the L1 sender is a contract, L2 from / msg.sender is shifted by a constant so an L1 contract and an L2 contract at the same address cannot share an identity. EOAs are not aliased. Arbitrum and zkSync use the same offset. The true remote sender lives in xDomainMessageSender — L2 app contracts must not treat the deposit tx msg.sender as the L1 user; that is usually the aliased messenger.

uint160 constant OFFSET = uint160(0x1111000000000000000000000000000000001111);

function applyL1ToL2Alias(address l1) internal pure returns (address) {
    unchecked { return address(uint160(l1) + OFFSET); }
}
function undoL1ToL2Alias(address l2) internal pure returns (address) {
    unchecked { return address(uint160(l2) - OFFSET); }
}

L2→L1 does not alias again: MessagePasser records the real L2 address, and L1 xDomainMessageSender() is that L2 contract. Paired apps therefore CREATE2 to the same address on both sides and each checks "sender == my counterpart" against the messenger, not msg.sender == counterpart.

Solidity: depositing

interface IL1StandardBridge {
    function bridgeETHTo(address to, uint32 minGasLimit, bytes calldata extraData) external payable;
    function bridgeERC20To(
        address localToken, address remoteToken, address to,
        uint256 amount, uint32 minGasLimit, bytes calldata extraData
    ) external;
}

// ETH: locked in the Portal; L2 credits the matching balance via derivation
L1_BRIDGE.bridgeETHTo{value: amount}(alice, 200_000, "");

// ERC-20: approve L1StandardBridge, then lock in the bridge
IERC20(usdc).approve(address(L1_BRIDGE), amount);
L1_BRIDGE.bridgeERC20To(usdc, l2Usdc, alice, amount, 200_000, "");

minGasLimit is the gas available to the target when relayed, not a cap on the whole deposit. The messenger also takes overhead; official guidance is to overestimate. Set it too low and the L2 call reverts, the message lands in failedMessages, and funds can sit in the messenger/bridge until relayMessage. For ERC-20, remoteToken must be the official mapping; a wrong address mints an L2 token nobody recognizes.

In Portal depositTransaction(to, value, gasLimit, isCreation, data), msg.value becomes L2 mint (credited to from first); the value argument is the inner callvalue. StandardBridge mints ETH to the aliased L1 messenger, then forwards it as callvalue to the L2 bridge — do not swap those two values if you build deposits yourself.

Your contracts: the cross-domain guard

The token bridge is just one client of the messenger. Your own protocol (locks, governors, NFT moves) uses the same pipe. L2 predeploys are identical on every OP Stack chain:

PredeployAddress
L2CrossDomainMessenger0x4200000000000000000000000000000000000007
L2StandardBridge0x4200000000000000000000000000000000000010
L2ToL1MessagePasser0x4200000000000000000000000000000000000016
L1Block0x4200000000000000000000000000000000000015
GasPriceOracle0x420000000000000000000000000000000000000F
 
ICrossDomainMessenger constant MESSENGER =
    ICrossDomainMessenger(0x4200000000000000000000000000000000000007);

address public immutable l1Counterpart; // paired L1 contract, set in the constructor

modifier onlyFromCounterpart() {
    require(msg.sender == address(MESSENGER), "not messenger");
    require(MESSENGER.xDomainMessageSender() == l1Counterpart, "bad sender");
    _;
}

// L1 → L2: only the counterpart, through the messenger
function finalizeLock(address user, uint256 amount) external onlyFromCounterpart {
    _credit(user, amount);
}

// L2 → L1: initiate a message; L1 sees it only after prove+finalize
function sendToL1(bytes calldata payload, uint32 minGas) external {
    MESSENGER.sendMessage(l1Counterpart, payload, minGas);
}

You need both checks. xDomainMessageSender is only meaningful while the messenger is relaying: skip msg.sender and an attacker can reenter you from another legitimate relay's callback, or point you at a fake messenger. Hardcode the predeploy; do not take the messenger as a free constructor argument.

The L1 side uses the same guard, with L1CrossDomainMessenger (one per L2, not 0x420…). After finalizeWithdrawalTransaction, the Portal calls the L1 messenger, which calls your L1 contract: msg.sender is the L1 messenger, xDomainMessageSender() is the L2 counterpart.

In Foundry, do not run derivation to test the L2 entrypoint — impersonate the messenger:

vm.prank(address(MESSENGER));
vm.mockCall(
    address(MESSENGER),
    abi.encodeCall(ICrossDomainMessenger.xDomainMessageSender, ()),
    abi.encode(l1Counterpart)
);
app.finalizeLock(user, amount);

vm.prank(address(MESSENGER));
vm.mockCall(..., abi.encode(attacker));
vm.expectRevert("bad sender");
app.finalizeLock(user, amount);

L1Block and confirmation

L2 block.number / block.timestamp are L2's own. To pin L1 state (short sequencer reorgs, an L1 TWAP, "the L1 block that included this deposit"), read the L1Block predeploy. Do not treat the L2 timestamp as L1 finality.

interface IL1Block {
    function number() external view returns (uint64);
    function timestamp() external view returns (uint64);
    function hash() external view returns (bytes32);
    function sequenceNumber() external view returns (uint64);
    function basefee() external view returns (uint256);
    function blobBaseFee() external view returns (uint256);
}
IL1Block constant L1_BLOCK = IL1Block(0x4200000000000000000000000000000000000015);

RPC latest on the sequencer is unsafe (soft confirm). safe means derived from L1 data; finalized follows L1 finality. Contracts cannot read those labels directly, but backends / keepers should wait for safe or finalized before proving a withdrawal or firing a cross-domain command — not a sequencer receipt.

Withdrawals: commit on L2, wait on L1

Withdrawal is three steps and cannot collapse into one L1 transaction:

  1. Initiate (L2): L2StandardBridge.bridgeETHTo / bridgeERC20To → messenger → L2ToL1MessagePasser.initiateWithdrawal. ETH leaves L2 circulation; the message hash is written to MessagePasser storage.
  2. Prove (L1): once an output root covering that L2 block is posted (today a FaultDisputeGame), prove to the Portal with a Merkle / storage proof that "this withdrawal is in that state."
  3. Finalize (L1): wait for the dispute game to resolve, plus the finalization delay (about a seven-day air gap). The Portal releases ETH, or StandardBridge unlocks ERC-20.

Withdrawals after fault proofs

The old L2OutputOracle.proposeL2Output used a permissioned proposer. OP Mainnet now opens a FaultDisputeGame via DisputeGameFactory (Cannon instruction proofs): anyone may claim an output root for an L2 block, and anyone may bisect and challenge. The Portal (OptimismPortal2) only accepts games that DEFENDER_WINS after proofMaturityDelay. The Guardian / Security Council can still blacklist a bad game or switch back to a permissioned game — fault proofs are not "no governance backdoor."

struct WithdrawalTransaction {
    uint256 nonce;
    address sender;
    address target;
    uint256 value;
    uint256 gasLimit;
    bytes data;
}

portal.proveWithdrawalTransaction(
    withdrawalTx,
    disputeGameIndex,
    outputRootProof,
    withdrawalProof          // storage proof against MessagePasser
);

// wait for the game to finish + proofMaturityDelay (~7 days)
portal.finalizeWithdrawalTransaction(withdrawalTx);

SDKs (successors of @eth-optimism/sdk, viem OP Stack actions, the official Superchain SDK) assemble the output and withdrawal proofs. Hand-rolled Merkle proofs are an easy way to hit the wrong slot.

The Portal anti-replays with two mappings: provenWithdrawals[hash] binds a game, finalizedWithdrawals[hash] pays each withdrawal once. If the game is overturned you must prove again. When the L1 app is called by the messenger it still needs onlyFromCounterpart — the Portal does not check "this message belongs to your protocol."

If the target reverts at finalize, the Portal still marks the withdrawal finalized (WithdrawalFinalized(..., false)). That hash will not pay again. This is not the deposit path: L1→L2 messenger failures land in failedMessages and can be relayMessaged; a raw Portal target has no such retry. When the messenger calls your L1 contract, make "book then transfer" retryable yourself — the Portal will not replay it for you.

Only L2StandardBridge may mint / burn an OptimismMintableERC20. A homegrown "bridged token" whose mint key is an EOA or a random adapter is not canonical. Read l1Token() against the official list; do not trust the symbol.

Arbitrum's classic deposit footgun is the retryable ticket: L1 success does not mean L2 executed. If the submission fee or L2 gas is short, the ticket sits in the retryable queue until someone tops up and redeems. To users this looks like "the bridge ate my funds" — they are stuck in a replayable ticket.

// L1: Inbox.createRetryableTicket{value: l2CallValue + l2Gas + submissionFee}
// to, l2CallValue, maxSubmissionCost, excessFeeRefundAlias, callValueRefundAlias,
// gasLimit, maxFeePerGas, data
inbox.createRetryableTicket{value: msg.value}(
    l2App, 0, maxSubmissionCost,
    refundTo, refundTo, gasLimit, maxFeePerGas,
    abi.encodeCall(L2App.finalizeLock, (user, amount))
);

// L2 exit: ArbSys(0x64).sendTxToL1(l1Target, data)
// L1 receive: msg.sender is the Bridge, not the Outbox, and not an aliased L2 sender
IBridge bridge = inbox.bridge();
require(msg.sender == address(bridge), "NOT_FROM_BRIDGE");
require(IOutbox(bridge.activeOutbox()).l2ToL1Sender() == l2Counterpart, "bad L2 sender");

Arbitrum's L1→L2 alias uses the same constant as OP. If excessFeeRefundAddress / callValueRefundAddress is an L1 contract, the L2 credit goes to the aliased address. If nothing is deployed there, ETH sits — do not assume a later CREATE2 deploy will recover it. In practice: refund an EOA or contract that already exists on L2. Same class of bug as zkSync refundRecipient.

Canonical vs fast bridges

Across, Hop, and official fast-withdrawal products work by having a liquidity provider pay you on the destination first, then recovering via the canonical withdrawal. Users get funds in minutes; the counterparty becomes the LP and that protocol, not "L1 plus one honest verifier."

If a product shows "L2 ETH," ask whether it is canonical credited ETH or an OFT / lock-mint wrapped token. The latter's exit path has nothing to do with the challenge period — see the LayerZero note.

Developer checklist

  • Every cross-domain entrypoint: msg.sender == messenger and xDomainMessageSender() == counterpart. Foundry should hit both "fake messenger" and "real messenger + fake sender."
  • Only allow official ERC-20 mappings; on L2 use OptimismMintableERC20Factory or the official list, never a hard-coded unverified mapping[l1] = l2.
  • After a contract-sender deposit, L2 msg.sender is aliased. If refund / excess-fee recipients are L1 contracts, use an L2 EOA/contract that already exists; do not bet on recovering later by deploying onto the aliased address.
  • Do not assume L1 has unlocked funds just because L2 initiated. A failed raw Portal target is not replayed; only the messenger path has failedMessages. The L1 entrypoint still needs onlyFromCounterpart (on Arbitrum: Bridge + l2ToL1Sender).
  • Size minGasLimit for the target plus messenger overhead; test "gas one unit short → failedMessages → replay."
  • Logic that needs L1 finality reads L1Block; backends wait for safe / finalized. Do not use L2 block.timestamp or a sequencer receipt as an L1 anchor.
  • Watch dispute-game status, WithdrawalProven / WithdrawalFinalized, Portal / Bridge balances vs pending exits, and failedMessages backlog.
  • If the sequencer is down, deposits should still derive from L1; withdrawals still wait out the challenge period. Split those two facts in the runbook.
