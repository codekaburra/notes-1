帳戶抽象：ERC-4337 與 EIP-7702

2026-09-06 · 以太坊

要解的問題

EOA 的驗證邏輯寫死在協議裡——一組 secp256k1 簽章，沒得改。所以沒有多簽、沒有 passkey、沒有社交恢復；沒 ETH 就什麼都動不了；一次只能做一件事。合約帳戶其實沒這些限制，但合約不能自己發起交易。

兩條路線

ERC-4337EIP-7702
做法不改協議，另開替代 mempool隨 Pectra 進協議（2025-05）
帳戶你部署的新合約既有 EOA 原地升級，地址不變
解的事代送交易、代付 gas上億個現存 EOA 不用遷移

一句話：7702 讓帳戶變聰明，4337 讓聰明的帳戶有人幫忙送交易跟付 gas。

4337 的流程

使用者送的是 UserOperation（9 個欄位）而不是交易 → Bundler 從替代 mempool 收集 → 打包成一筆 handleOps() 送給鏈上單例 EntryPoint → EntryPoint 先跑完整批的驗證迴圈，再跑執行迴圈。

你的帳戶只需要實作一個函式：

function validateUserOp(
    PackedUserOperation calldata userOp,
    bytes32 userOpHash,
    uint256 missingAccountFunds
) external returns (uint256 validationData);
// 0 = 通過，1 = 簽章錯（回傳 1，不要 revert）

簽章格式完全由這個函式自己定義——這就是「抽象」的所在。

7702 的機制

新交易型別 0x04，帶 authorization_list，每筆是 [chain_id, address, nonce, y_parity, r, s]。通過後協議把 23 bytes 寫進 EOA 的 code 欄位：

0xef0100 ‖ 實作合約地址

地址不變、私鑰照樣能用。簽 address(0) 可以撤銷。

三個會咬人的坑

  1. 委派合約要自己做重放保護。協議只保證授權本身不被重放，不管你的 execute()。
  2. 初始化不是原子的。7702 沒有 constructor，設定 owner 必須靠 ecrecover 驗簽，否則會被搶跑。
  3. 「Bundler 拒收但合約邏輯正確」通常是撞到 ERC-7562 的驗證範圍規則：禁用 TIMESTAMP、BLOCKHASH、BALANCE，且限制驗證階段能讀的 storage。

EntryPoint 地址

三版並存，整合前先確認 Bundler 支援哪一版——這是最常卡住的地方。

v0.60x5FF137D4b0FDCD49DcA30c7CF57E578a026d2789
v0.70x0000000071727De22E5E9d8BAf0edAc6f37da032
v0.80x4337084D9E255Ff0702461CF8895CE9E3b5Ff108

v0.7 生態支援最廣；v0.8 原生支援 7702，UserOp hash 改用 EIP-712。

Account Abstraction: ERC-4337 & EIP-7702

2026-09-06 · Ethereum

The problem

An EOA's validation logic is hardcoded into the protocol — one secp256k1 signature, take it or leave it. No multisig, no passkeys, no social recovery. No ETH means nothing moves. One action per transaction. Contract accounts have none of these limits, but a contract can't initiate a transaction.

Two approaches

ERC-4337EIP-7702
MethodNo protocol change; alt mempoolShipped in Pectra (May 2025)
AccountA new contract you deployExisting EOA, upgraded in place
SolvesRelaying and gas sponsorshipMigrating hundreds of millions of EOAs

In one line: 7702 makes the account smart; 4337 gets that smart account relayed and its gas paid.

The 4337 flow

The user submits a UserOperation (nine fields), not a transaction → a Bundler picks it up from the alt mempool → packs it into one handleOps() call to the on-chain singleton EntryPoint → EntryPoint runs the whole validation loop first, then the execution loop.

Your account implements exactly one function:

function validateUserOp(
    PackedUserOperation calldata userOp,
    bytes32 userOpHash,
    uint256 missingAccountFunds
) external returns (uint256 validationData);
// 0 = valid, 1 = SIG_VALIDATION_FAILED (return 1, don't revert)

The signature format is entirely up to that function. That is the abstraction.

How 7702 works

A new transaction type 0x04 carries an authorization_list; each entry is [chain_id, address, nonce, y_parity, r, s]. Once valid, the protocol writes 23 bytes into the EOA's code field:

0xef0100 ‖ implementation address

Same address, same private key, still works as a plain EOA. Sign address(0) to revoke.

Three traps

  1. The delegate must implement its own replay protection. The protocol only guards the authorization, not your execute().
  2. Initialization isn't atomic. There's no constructor, so setting an owner must go through ecrecover, or it gets front-run.
  3. "Bundler rejects it but my logic is fine" almost always means ERC-7562 validation scope rules: no TIMESTAMP, BLOCKHASH, BALANCE, and limited storage access during validation.

EntryPoint addresses

Three versions coexist. Check which one your Bundler supports before integrating — that's the usual snag.

v0.60x5FF137D4b0FDCD49DcA30c7CF57E578a026d2789
v0.70x0000000071727De22E5E9d8BAf0edAc6f37da032
v0.80x4337084D9E255Ff0702461CF8895CE9E3b5Ff108

v0.7 has the widest tooling support; v0.8 adds native 7702 and EIP-712 UserOp hashing.
