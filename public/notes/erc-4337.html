Account Abstraction 與 Smart Accounts

2026-09-09 · ERC-4337 · EIP-7702 · ERC-7579 · Developer guide

Smart Account 是帳戶合約；Account Abstraction 是讓帳戶自訂驗證、執行與 gas 支付規則的整套系統。本篇從協議一路走到工程實作：UserOperation、Bundler、EntryPoint、7702 delegation、Account／Factory、Paymaster、ERC-7579、viem、除錯與上線檢查。

三種帳戶模型

模型驗證／執行地址與部署適合情境
EOA協議固定 secp256k1；由私鑰直接送交易私鑰導出地址，沒有 code最簡單、工具相容性最高
4337 Contract Account合約自訂 validateUserOp 與 executeFactory／CREATE2 部署，可 counterfactual 使用新錢包、完整權限與恢復模型
7702 Delegated EOAEOA code 指向 delegate，程式在 EOA storage／address context 執行原地址不變；授權持續有效直到被替換或撤銷既有 EOA 原地加入 batching、sponsorship 等能力

4337 與 7702 可以獨立使用，也可以組合：7702 解決「哪個地址執行 smart-account code」，4337 提供 UserOperation、Bundler、EntryPoint、Paymaster 與共享 mempool 的交易管線。

ERC-4337 的參與者與信任邊界

  • Wallet／Client：建立、估 gas、簽署並送出 UserOperation。
  • Bundler：模擬驗證、套用 ERC-7562 規則、挑選 UserOps，並用自己的 EOA 支付 handleOps() 交易 gas。
  • EntryPoint：鏈上 singleton；部署 sender、驗證 account／paymaster、管理 deposits、執行 callData、計費並補償 Bundler。
  • Account：定義簽章、權限、時效與執行語義。
  • Paymaster：選用的 gas sponsor；先驗證是否願意付費，執行後可在 postOp 記帳。
  • Aggregator：選用的聚合簽章驗證器，例如把多個 BLS 簽章聚成一個。

Bundler 收到 UserOperation 不等於保證上鏈。它會重複模擬，且可以因 fee、reputation、mempool policy、狀態變動或 bundle 經濟性而延後或丟棄。

PackedUserOperation：鏈上真正驗證的資料

v0.7 之後，RPC 傳輸時可用較易讀的 unpacked 欄位，但進入 EntryPoint 時會壓成 9 欄的 PackedUserOperation：

struct PackedUserOperation {
    address sender;
    uint256 nonce;
    bytes initCode;
    bytes callData;
    bytes32 accountGasLimits;   // verificationGasLimit | callGasLimit
    uint256 preVerificationGas;
    bytes32 gasFees;            // maxPriorityFeePerGas | maxFeePerGas
    bytes paymasterAndData;
    bytes signature;
}
  • sender：已部署帳戶，或 initCode 將部署出的確定性地址。
  • nonce：不是單一計數器，而是 uint192 key | uint64 sequence；不同 key 可建立 session、批次或平行 nonce lane。
  • initCode：一般為 factory address + calldata；sender 已部署時的處理依 EntryPoint 版本而異。
  • callData：EntryPoint 原樣呼叫 account；其 ABI 是帳戶實作的一部分，不由 4337 統一。
  • preVerificationGas：補償 calldata、bundle 固定成本及無法在 EntryPoint 內觀察的成本；7702 authorization 成本也必須計入。
  • signature：由 account 解讀，可以是 ECDSA、P-256、multisig、session key 或聚合方案。

handleOps：驗證、執行與 gas 資金流

Bundler 送出一筆 handleOps(ops, beneficiary)。EntryPoint 對整批先完成驗證，再逐筆執行；其中任何一層的「成功」都不代表 target call 一定成功。

  1. Sender 建立：sender 沒有 code 時，EntryPoint 經 SenderCreator 呼叫 factory，並確認回傳地址等於 sender。
  2. Account validation：呼叫 validateUserOp(op, userOpHash, missingAccountFunds)；簽章錯應回傳 SIG_VALIDATION_FAILED = 1，其他結構性錯誤才 revert。
  3. Paymaster validation：有 sponsor 時呼叫 validatePaymasterUserOp，取得 context 與 validationData。
  4. Prefund：EntryPoint 鎖定 account 或 paymaster deposit，涵蓋 verification、execution、postOp 與 calldata 等上限。
  5. Execution：EntryPoint 呼叫 account 的 callData，account 再呼叫 target；target revert 通常只令該 UserOp 執行失敗，不必讓整批 bundle revert。
  6. Settlement：若 paymaster 回傳 context，EntryPoint 呼叫 postOp；最後按實際 gas 與規則扣 deposit、補償 Bundler beneficiary。

validationData 同時編碼 signature aggregator、validAfter 與 validUntil。v0.9 也可用最高 bit 表示 block-number validity。Account 與 Paymaster 的有效區間會取交集。

四條必須分清楚的 call path

  1. 已部署帳戶、自付 gas：validateUserOp → account deposit/prefund → account.execute → target。
  2. Counterfactual deployment：SenderCreator → factory → account，同一個 UserOp 再完成 validation 與首次執行。
  3. Paymaster sponsorship：account validation → paymaster validation → execution → postOp，gas 從 paymaster deposit 扣除。
  4. 7702 + 4337：Bundler 把 eip7702Auth 放入 type-4 bundle transaction 的 authorization list；EntryPoint 驗證 delegation 後，讓該 EOA 以 account code 驗證與執行 UserOp。

Smart Account 合約：validation 不等於 execution

IAccount 的最小協議介面只有 validateUserOp，但一個可用帳戶還需要執行入口、初始化、nonce 策略、ERC-1271、升級與恢復控制。validation 只回答「這筆 UserOp 是否獲授權」；真正的外部 call 由 account 的 execution surface 定義。

modifier onlyEntryPointOrSelf() {
    if (msg.sender != address(entryPoint) && msg.sender != address(this)) {
        revert UnauthorizedCaller();
    }
    _;
}

function execute(address target, uint256 value, bytes calldata data)
    external onlyEntryPointOrSelf returns (bytes memory result)
{
    (bool ok, bytes memory ret) = target.call{value: value}(data);
    if (!ok) assembly { revert(add(ret, 32), mload(ret)) }
    return ret;
}

self 分支讓獲授權的 batch 修改帳戶設定，但也意味任何能讓 account call 自己的路徑都可能取得管理權。支援 delegatecall、批次模式或 module executor 時，要逐一 allowlist mode、限制 target／value 並發出事件。

function validateUserOp(PackedUserOperation calldata op, bytes32 opHash, uint256 missingFunds)
    external returns (uint256 validationData)
{
    if (msg.sender != address(entryPoint)) revert UnauthorizedCaller();
    bool signatureOk = _checkUserOpSignature(opHash, op.signature);

    // EntryPoint 最後會驗 prefund；避免 transfer 的 2,300-gas 限制
    if (missingFunds != 0) {
        (bool funded,) = payable(msg.sender).call{value: missingFunds}("");
        funded; // 不要讓補款失敗掩蓋 signature validation 結果
    }
    return signatureOk ? 0 : 1;
}

高流量帳戶通常以 entryPoint.depositTo(account) 預存，而不是每次 validation 傳 ETH。若 account 使用多個 EntryPoint、validator 或 session，簽章 domain 必須明確綁定版本與入口。

Factory + CREATE2：先有地址，後有 code

Counterfactual account 可在部署前收款與簽 UserOp。第一次操作帶 factory／factoryData，SenderCreator 呼叫 factory 後，實際地址必須等於 sender。salt、implementation、proxy init code、初始化參數或 compiler 設定任一改變，都可能改變地址。

function accountSalt(address owner, uint256 userSalt) public pure returns (bytes32) {
    return keccak256(abi.encode(owner, userSalt));
}

function createAccount(address owner, uint256 userSalt) external returns (Account account) {
    bytes32 salt = accountSalt(owner, userSalt);
    address predicted = getAddress(owner, userSalt);
    if (predicted.code.length != 0) return Account(payable(predicted)); // idempotent
    account = new Account{salt: salt}(entryPoint, owner);
}
  • 初始化須與部署原子完成；implementation contract 必須鎖住 initializer。
  • Factory 重試應具冪等性，並驗證 owner、salt、EntryPoint、implementation 與預測地址。
  • 正式產品多使用 proxy；地址計算必須 hash 真正的 proxy creation code，不可套用 implementation 的公式。

ERC-1271：UserOp 以外的簽章相容面

validateUserOp 服務 EntryPoint；ERC-1271 的 isValidSignature 則讓 dApp、permit 與訂單協議驗證 contract signature。兩者可以共用 validator，但必須保留各自的 domain separation、有效期與撤銷語義。

bytes4 constant MAGIC = 0x1626ba7e;

function isValidSignature(bytes32 hash, bytes calldata sig) external view returns (bytes4) {
    return _check1271Signature(hash, sig) ? MAGIC : bytes4(0xffffffff);
}

EIP-7702：委派 code，不是搬移資產

Pectra 引入 type 0x04 set-code transaction；每個 authorization tuple 是 [chain_id, address, nonce, y_parity, r, s]。協議將 delegation indicator 寫入 authority EOA：

0xef0100 ‖ delegate implementation address

之後 CALL 該 EOA 時，會載入 delegate 的 code，但在 EOA 自己的 address、balance 與 storage context 執行，類似固定於帳戶地址的 delegation。它不是單筆交易後自動消失的暫時授權；要更換 delegate 必須再授權另一地址，授權 address(0) 則清除 delegation。

  • chain_id = 0 可跨鏈重播同一 authorization；除非刻意需要，應綁定實際 chain ID。
  • authorization nonce 保護「設定 code」不被重放，但 delegate 的 execute、session 與簽章仍要自行做 domain separation 和 replay protection。
  • delegate 沒有 constructor；初始化必須防搶跑。與 4337 組合時，初始化呼叫必須只接受 entryPoint.senderCreator()。
  • delegate implementation 被銷毀或行為改變會直接影響 EOA；不要把未固定、可任意升級的 implementation 當成無信任基礎。

EntryPoint v0.8+ 的 7702 UserOp 使用 initCode = 0x7702 || optional initialization payload，RPC 額外帶 eip7702Auth。authorization 只在更換 delegation 時需要；已設定後的後續 UserOps 不必重送相同 tuple。

Paymaster 與 Aggregator

Paymaster 不是「免費 gas API」，而是一個必須 deposit、可能需要 stake、會被惡意使用者消耗資金的鏈上風險引擎。簽章式 sponsor 至少應綁定 sender、chain、EntryPoint、nonce／UserOp hash、gas 上限、有效期與 sponsorship policy；postOp 必須能處理 target revert，且不可假設外部 token 報價永遠可用。

Aggregator 讓多個 UserOps 共用聚合簽章驗證，但增加獨立的 reputation／stake 與 bundle 驗證路徑。除非確實需要 BLS 或大量聚合收益，普通 account 不必引入。

ERC-7579：模組化帳戶

ERC-7579 定義四種基礎模組：validator 決定授權、executor 可代表帳戶執行、fallback handler 擴張外部介面、hook 在執行前後攔截。onInstall／onUninstall 只是 module callbacks，不是權限邊界；帳戶必須限制誰能安裝、卸載以及使用哪些初始化資料。

function installModule(uint256 moduleType, address module, bytes calldata initData)
    external onlyEntryPointOrSelf
{
    if (module.code.length == 0) revert InvalidModule();
    if (!IERC7579Module(module).isModuleType(moduleType)) revert WrongModuleType();
    _modules[moduleType][module] = true; // state first，防止 onInstall 重入
    IERC7579Module(module).onInstall(initData);
    emit ModuleInstalled(moduleType, module);
}
  • Validator 可批准 UserOp；executor 可直接移動資產；hook 可阻斷所有執行；fallback 擴張 attack surface——四者都視為高權限程式碼。
  • 測試重複安裝、重入、卸載殘留 storage／allowance、hook ordering、惡意 module 與 emergency recovery。
  • Delegatecall module 還耦合 storage layout 與 upgrade authority；優先使用成熟、經審計且有 registry／attestation 策略的實作。

Web3 client：viem 與 Bundler RPC

SDK 會幫忙 pack、estimate 和簽 UserOperation，但 RPC 邊界仍應被明確監控。啟動時先確認 Bundler 支援 account 使用的 EntryPoint：

import { createBundlerClient } from "viem/account-abstraction";
import { http } from "viem";

const bundler = createBundlerClient({
  client: publicClient,
  transport: http(BUNDLER_URL),
});

const supported = await bundler.getSupportedEntryPoints();
if (!supported.includes(account.entryPoint.address)) {
  throw new Error("EntryPoint mismatch");
}

const userOpHash = await bundler.sendUserOperation({
  account,
  calls: [
    { to: token, data: approveData },
    { to: dex, data: swapData },
  ],
  paymaster: paymasterClient, // optional
});

const receipt = await bundler.waitForUserOperationReceipt({ hash: userOpHash });
if (!receipt.success) throw new Error(`execution reverted: ${receipt.reason ?? "unknown"}`);
RPC用途
eth_supportedEntryPoints確認 Bundler 的版本／地址
eth_estimateUserOperationGas觸發 validation simulation；保存完整 error data
eth_sendUserOperation回傳 UserOp hash，不是 transaction hash
eth_getUserOperationByHash查詢狀態及 bundling transaction
eth_getUserOperationReceipt確認 included、success 與 logs

ERC-7562：為什麼本機成功，Bundler 卻拒收

Bundler 必須確保 validation 在模擬與上鏈時可重現，且不會讓未質押實體任意依賴外部狀態。因此 ERC-7562 對 account、factory、paymaster、aggregator 的 opcode、storage access、code creation 與 unstaked entity 行為設限。這不是一句「所有 validation 都不能用 TIMESTAMP／BALANCE」可以概括；規則會依實體、stake 與存取槽位分類。

典型除錯順序：

  1. eth_supportedEntryPoints：先確認版本和地址。
  2. 重新計算 sender、chain ID、nonce key／sequence、UserOp hash 與 signature domain。
  3. eth_estimateUserOperationGas：保存完整 RPC error data，不只顯示 message。
  4. 區分 account validation、paymaster validation、execution 與 postOp；解析 FailedOp／AAxx 與 account revert data。
  5. 對實際 handleOps transaction 做 trace，並解析 UserOperationEvent；UserOp hash 不是 transaction hash。

EntryPoint 版本與地址

版本不能只看 ABI：Bundler 必須加入對應 EntryPoint 的 mempool，Account／Paymaster 也必須按該版本的 hash、packing 與 gas 規則實作。部署前應再向官方 release 與 audit 核對 chain、address 和 code hash。

測試、上線與監控清單

Contract tests

  • Direct call、錯 EntryPoint、錯簽、過期簽章、跨鏈／跨帳戶 replay 都失敗；ERC-1271 回傳精確 magic value。
  • CREATE2 預測地址等於部署地址；Factory 重試冪等；未初始化 implementation 不可被接管。
  • 每個 nonce key 內有序、不同 key 可平行；batch 中途 revert 的 atomicity 符合產品承諾。
  • 測試 prefund 不足、target revert、paymaster 過期／低 deposit／postOp 失敗。
  • 模組重入、重複安裝、惡意 validator／executor／hook、卸載殘留及 recovery path 均有 adversarial tests。

Production

  • 固定 chain ID、EntryPoint、Factory、implementation code hash 與 salt schema；至少對兩個 Bundler 做相容測試。
  • 設定 RPC timeout、idempotent retry、receipt timeout、stuck-op replacement 與 sponsor budget hard cap。
  • 監控 inclusion latency、UserOp success rate、validation failures、Paymaster deposit／stake 與 module-change events。
  • 準備 upgrade delay、暫停 sponsorship、撤銷 session／module、owner recovery 與事件索引重建 runbook。

協議層安全清單

  • UserOp signature 必須綁定 chain ID、EntryPoint、account 與完整操作語義；session key 另外限制 target、selector、value、期限與額度。
  • 只允許 EntryPoint 呼叫 validation，只允許 EntryPoint／self 或明確 executor 進入執行入口。
  • Account、Paymaster、Factory 與 module 初始化必須原子化或具不可重放的簽章授權。
  • 監控 EntryPoint deposits、Paymaster stake、sponsor budget、Bundler inclusion latency 與 UserOperationEvent 失敗率。
  • 不要把 AAxx 字串當永久 API；v0.9 release 已明確說明未來可能改良錯誤格式。

Account Abstraction & Smart Accounts

2026-09-09 · ERC-4337 · EIP-7702 · ERC-7579 · Developer guide

A Smart Account is the account contract; Account Abstraction is the system that lets accounts define validation, execution, and gas-payment rules. This guide runs from protocol to production engineering: UserOperations, Bundlers, EntryPoint, 7702 delegation, account/factory contracts, paymasters, ERC-7579, viem, debugging, and launch checks.

Three account models

ModelValidation / executionAddress and deploymentBest fit
EOAProtocol-fixed secp256k1; private key sends transactionsKey-derived address, no codeSimplicity and maximum tooling compatibility
4337 Contract AccountContract-defined validateUserOp and executionFactory/CREATE2 deployment; counterfactual useNew wallets with custom authority and recovery
7702 Delegated EOAEOA points to delegate code executing in the EOA's storage/address contextAddress stays; authorization persists until replaced or revokedAdding batching and sponsorship to existing EOAs

4337 and 7702 can work independently or together. 7702 answers which address executes smart-account code; 4337 supplies the UserOperation, Bundler, EntryPoint, Paymaster, and shared-mempool transaction pipeline.

ERC-4337 actors and trust boundaries

  • Wallet/client: builds, estimates, signs, and submits a UserOperation.
  • Bundler: simulates validation, enforces ERC-7562, selects UserOps, and pays for the handleOps() transaction from its own EOA.
  • EntryPoint: the on-chain singleton; deploys senders, validates accounts/paymasters, holds deposits, executes callData, meters gas, and reimburses the Bundler.
  • Account: defines signature, authority, time bounds, and execution semantics.
  • Paymaster: optional gas sponsor, validating willingness to pay and optionally accounting in postOp.
  • Aggregator: optional shared signature verifier, for example aggregating multiple BLS signatures.

A Bundler accepting a UserOperation does not guarantee inclusion. It may re-simulate, delay, replace, or drop it because of fee, reputation, mempool policy, state changes, or bundle economics.

PackedUserOperation: what EntryPoint verifies on-chain

Since v0.7, RPC transport may use readable unpacked fields, but EntryPoint receives the nine-field PackedUserOperation:

struct PackedUserOperation {
    address sender;
    uint256 nonce;
    bytes initCode;
    bytes callData;
    bytes32 accountGasLimits;   // verificationGasLimit | callGasLimit
    uint256 preVerificationGas;
    bytes32 gasFees;            // maxPriorityFeePerGas | maxFeePerGas
    bytes paymasterAndData;
    bytes signature;
}
  • sender: an existing account or the deterministic address that initCode will deploy.
  • nonce: a two-dimensional uint192 key | uint64 sequence, enabling separate session, batch, or parallel lanes.
  • initCode: normally factory address plus calldata; handling when sender already exists is version-specific.
  • callData: called verbatim on the account; its ABI belongs to the account implementation, not ERC-4337.
  • preVerificationGas: pays for calldata, bundle overhead, and costs EntryPoint cannot observe; 7702 authorization cost belongs here too.
  • signature: account-defined ECDSA, P-256, multisig, session-key, or aggregate data.

handleOps: validation, execution, and gas flow

A Bundler submits handleOps(ops, beneficiary). EntryPoint validates the batch before executing each operation; success at one layer does not imply the target call succeeds.

  1. Sender creation: for an undeployed sender, EntryPoint calls the factory through SenderCreator and requires the deployed address to equal sender.
  2. Account validation: calls validateUserOp(op, userOpHash, missingAccountFunds). Bad signatures should return SIG_VALIDATION_FAILED = 1; structural failures revert.
  3. Paymaster validation: when sponsored, calls validatePaymasterUserOp and receives context plus validationData.
  4. Prefund: reserves account or paymaster deposit for worst-case verification, execution, postOp, and calldata costs.
  5. Execution: calls account callData; the account calls the target. A target revert usually marks that UserOp failed without reverting the whole bundle.
  6. Settlement: invokes postOp when needed, deducts actual gas under version rules, and pays the Bundler beneficiary.

validationData combines a signature aggregator with validAfter and validUntil. v0.9 may use the top bit to express block-number validity. Account and paymaster validity windows are intersected.

Four call paths to distinguish

  1. Deployed account, self-funded: validateUserOp → account deposit/prefund → account.execute → target.
  2. Counterfactual deployment: SenderCreator → factory → account, followed by validation and first execution in the same UserOp.
  3. Paymaster sponsorship: account validation → paymaster validation → execution → postOp, charged to paymaster deposit.
  4. 7702 + 4337: Bundler includes eip7702Auth in the type-4 bundle transaction authorization list; EntryPoint verifies delegation and the EOA validates and executes as an account.

Smart Account contracts: validation is not execution

IAccount has one minimal protocol method, validateUserOp, but a usable account also needs execution, initialization, nonce strategy, ERC-1271, upgrades, and recovery controls. Validation answers whether a UserOp is authorized; the account's execution surface defines the actual external calls.

modifier onlyEntryPointOrSelf() {
    if (msg.sender != address(entryPoint) && msg.sender != address(this)) {
        revert UnauthorizedCaller();
    }
    _;
}

function execute(address target, uint256 value, bytes calldata data)
    external onlyEntryPointOrSelf returns (bytes memory result)
{
    (bool ok, bytes memory ret) = target.call{value: value}(data);
    if (!ok) assembly { revert(add(ret, 32), mload(ret)) }
    return ret;
}

The self branch lets an authorized batch update account configuration, but every path that can make the account call itself may therefore become administrative. For delegatecall, batch modes, or module executors, allowlist modes, constrain target/value, and emit events.

function validateUserOp(PackedUserOperation calldata op, bytes32 opHash, uint256 missingFunds)
    external returns (uint256 validationData)
{
    if (msg.sender != address(entryPoint)) revert UnauthorizedCaller();
    bool signatureOk = _checkUserOpSignature(opHash, op.signature);

    // EntryPoint checks prefund later; avoid transfer's 2,300-gas constraint
    if (missingFunds != 0) {
        (bool funded,) = payable(msg.sender).call{value: missingFunds}("");
        funded; // do not mask signature validation when funding fails
    }
    return signatureOk ? 0 : 1;
}

High-volume accounts often pre-deposit with entryPoint.depositTo(account) instead of sending ETH during each validation. Accounts supporting multiple EntryPoints, validators, or sessions must bind version and entry point in the signature domain.

Factory + CREATE2: address before code

A counterfactual account can receive assets and sign a UserOp before deployment. Its first operation carries factory/factoryData; after SenderCreator invokes the factory, the deployed address must equal sender. Changing salt, implementation, proxy init code, initialization parameters, or compiler settings may change the address.

function accountSalt(address owner, uint256 userSalt) public pure returns (bytes32) {
    return keccak256(abi.encode(owner, userSalt));
}

function createAccount(address owner, uint256 userSalt) external returns (Account account) {
    bytes32 salt = accountSalt(owner, userSalt);
    address predicted = getAddress(owner, userSalt);
    if (predicted.code.length != 0) return Account(payable(predicted)); // idempotent
    account = new Account{salt: salt}(entryPoint, owner);
}
  • Initialize atomically with deployment and lock the implementation initializer.
  • Factory retries should be idempotent and validate owner, salt, EntryPoint, implementation, and predicted address.
  • Production accounts commonly use proxies; address calculation must hash the real proxy creation code, not the implementation formula.

ERC-1271: signature compatibility beyond UserOps

validateUserOp serves EntryPoint. ERC-1271 isValidSignature lets dApps, permits, and order protocols verify contract signatures. They may share a validator but need separate domain separation, validity, and revocation semantics.

bytes4 constant MAGIC = 0x1626ba7e;

function isValidSignature(bytes32 hash, bytes calldata sig) external view returns (bytes4) {
    return _check1271Signature(hash, sig) ? MAGIC : bytes4(0xffffffff);
}

EIP-7702: delegate code, not assets

Pectra introduced type 0x04 set-code transactions. Each authorization tuple is [chain_id, address, nonce, y_parity, r, s]; the protocol writes a delegation indicator to the authority EOA:

0xef0100 ‖ delegate implementation address

A CALL to that EOA loads delegate code but executes in the EOA's own address, balance, and storage context. This is not a temporary one-transaction authorization: it persists until another delegate is authorized or address(0) clears the delegation.

  • chain_id = 0 permits cross-chain replay of the authorization; bind the actual chain unless that is explicitly intended.
  • The authorization nonce protects setting code, not delegate execute, sessions, or signatures; those still require domain separation and replay protection.
  • There is no delegate constructor. Initialization must resist front-running; with 4337 it must only accept entryPoint.senderCreator().
  • Destroyed or mutable delegate implementations directly affect the EOA; do not treat an arbitrarily upgradeable implementation as trustless.

For EntryPoint v0.8+, a 7702 UserOp uses initCode = 0x7702 || optional initialization payload and the RPC carries eip7702Auth. That tuple is only needed when changing delegation, not on every later UserOp.

Paymasters and aggregators

A Paymaster is not a "free gas API"; it is an on-chain risk engine with deposits, possible stake requirements, and capital exposed to adversarial users. A signed sponsorship should bind sender, chain, EntryPoint, nonce/UserOp hash, gas limits, validity, and policy. postOp must handle target reverts and avoid assuming an external token price remains valid.

An Aggregator shares signature validation across multiple UserOps but adds reputation, stake, and bundle-validation paths. Ordinary accounts should not add one unless BLS or aggregation savings justify it.

ERC-7579: modular accounts

ERC-7579 defines four base module types: validators authorize, executors act for the account, fallback handlers expand the external surface, and hooks intercept execution. onInstall/onUninstall are module callbacks, not authorization boundaries; the account must restrict who can install/remove modules and validate initialization data.

function installModule(uint256 moduleType, address module, bytes calldata initData)
    external onlyEntryPointOrSelf
{
    if (module.code.length == 0) revert InvalidModule();
    if (!IERC7579Module(module).isModuleType(moduleType)) revert WrongModuleType();
    _modules[moduleType][module] = true; // state first against onInstall reentrancy
    IERC7579Module(module).onInstall(initData);
    emit ModuleInstalled(moduleType, module);
}
  • A validator approves UserOps; an executor can move assets; a hook can block all execution; a fallback expands attack surface. Treat all as privileged code.
  • Test duplicate installation, reentrancy, residual storage/allowance after removal, hook ordering, malicious modules, and emergency recovery.
  • Delegatecall modules also couple storage layout and upgrade authority. Prefer audited implementations with a registry or attestation policy.

Web3 clients: viem and Bundler RPC

An SDK can pack, estimate, and sign UserOperations, but the RPC boundary still needs explicit monitoring. Check that the Bundler supports the account's EntryPoint at startup:

import { createBundlerClient } from "viem/account-abstraction";
import { http } from "viem";

const bundler = createBundlerClient({
  client: publicClient,
  transport: http(BUNDLER_URL),
});

const supported = await bundler.getSupportedEntryPoints();
if (!supported.includes(account.entryPoint.address)) {
  throw new Error("EntryPoint mismatch");
}

const userOpHash = await bundler.sendUserOperation({
  account,
  calls: [
    { to: token, data: approveData },
    { to: dex, data: swapData },
  ],
  paymaster: paymasterClient, // optional
});

const receipt = await bundler.waitForUserOperationReceipt({ hash: userOpHash });
if (!receipt.success) throw new Error(`execution reverted: ${receipt.reason ?? "unknown"}`);

ERC-7562: why Bundlers reject locally valid code

Bundlers need validation to be reproducible between simulation and inclusion. ERC-7562 therefore constrains opcode, storage, code-creation, and unstaked-entity behavior for accounts, factories, paymasters, and aggregators. It is more nuanced than saying validation can never use TIMESTAMP or BALANCE: rules vary by entity, stake, and storage relationship.

A practical debugging order:

  1. Call eth_supportedEntryPoints and confirm version/address.
  2. Recompute sender, chain ID, nonce key/sequence, UserOp hash, and signature domain.
  3. Call eth_estimateUserOperationGas and preserve complete RPC error data.
  4. Separate account validation, paymaster validation, execution, and postOp; decode FailedOp/AAxx and account revert data.
  5. Trace the actual handleOps transaction and parse UserOperationEvent. A UserOp hash is not a transaction hash.

Testing, launch, and monitoring checklist

Contract tests

  • Direct calls, wrong EntryPoint, bad/expired signatures, and cross-chain/account replay fail; ERC-1271 returns the exact magic value.
  • CREATE2 prediction equals deployment; Factory retries are idempotent; an uninitialized implementation cannot be captured.
  • Every nonce key is ordered while separate keys run in parallel; batch revert atomicity matches the product promise.
  • Cover low prefund, target revert, expired/underfunded Paymaster, and postOp failure.
  • Adversarial tests cover module reentrancy, duplicate installs, malicious validators/executors/hooks, removal residue, and recovery.

Production

  • Pin chain ID, EntryPoint, Factory, implementation code hash, and salt schema; test compatibility with at least two Bundlers.
  • Define RPC timeout, idempotent retry, receipt timeout, stuck-op replacement, and sponsor-budget hard caps.
  • Monitor inclusion latency, UserOp success, validation failures, Paymaster deposit/stake, and module-change events.
  • Write runbooks for upgrade delay, sponsorship pause, session/module revocation, owner recovery, and event-index rebuilds.

Protocol security checklist

  • Bind UserOp signatures to chain ID, EntryPoint, account, and full action semantics; constrain session keys by target, selector, value, expiry, and spend limits.
  • Only EntryPoint may call validation; only EntryPoint/self or an explicit executor may enter execution.
  • Initialize accounts, paymasters, factories, and modules atomically or through non-replayable signed authorization.
  • Monitor EntryPoint deposits, paymaster stake, sponsor budget, Bundler inclusion latency, and UserOperationEvent failure rate.
  • Do not treat AAxx strings as a permanent API; v0.9 release notes explicitly anticipate future error-format improvements.
