交易與跨鏈封包是兩個層次

接續 Ethereum 與 Solana。本篇以一般 Cosmos SDK 帳戶、Protobuf SIGN_MODE_DIRECT 和 IBC classic 的 ICS-20 代幣轉帳為例。Cosmos 是多鏈生態：實際 chain ID、denom、簽署模式、費用與 IBC 版本必須對目標鏈核對。

使用者先在來源鏈送出一筆 Cosmos 交易，裡面有 MsgTransfer。IBC 模組產生 packet；relayer 之後在目的鏈送另一筆交易提交證明，接著再把 acknowledgement 或 timeout 證明送回來源鏈。來源鏈交易成功，只代表跨鏈流程開始。

Cosmos 交易：TxBody、AuthInfo、SignDoc、TxRaw

TxBody
├─ messages[]：例如 MsgSend、MsgDelegate、MsgTransfer
├─ memo
└─ timeout_height（交易層高度限制，與 IBC packet timeout 分開）

AuthInfo
├─ signer_infos[]：公鑰、sign mode、sequence
└─ fee：amount、gas_limit、payer / granter（依設定）

SignDoc (SIGN_MODE_DIRECT)
├─ body_bytes
├─ auth_info_bytes
├─ chain_id
└─ account_number
        ↓ 簽章
TxRaw = body_bytes + auth_info_bytes + signatures[]

Protobuf Any 承載各種 Msg。直接簽署模式簽的是由確切 body/auth bytes 與 chain ID、account number 組成的 SignDoc；廣播的是序列化的 TxRaw。簽完後改 memo、fee、gas limit、sequence 或任一 message，都要重簽。SignerInfos 與 signatures 的順序必須符合該交易的 signer 規則。

一般 secp256k1 帳戶的簽章常為 64-byte r || s，不帶 Ethereum 的 v；驗證使用對應公鑰。帳戶類型、multisig、sign mode 與 Cosmos EVM Ethereum-format 交易可不同，不能硬套單一解碼器。詳見 簽章對照。

一筆 IBC 轉帳的 JSON 長怎樣？

下方是教學用、已解碼的 Protobuf JSON 形狀，地址、channel、數額和 timeout 都是示意，不能直接廣播。這裡有三個層次：人類可讀的 Tx、簽署時的 SignDoc，以及實際廣播的 TxRaw。不要把這份 JSON 文字直接當成要簽的 bytes。

{
  "body": {
    "messages": [{
      "@type": "/ibc.applications.transfer.v1.MsgTransfer",
      "source_port": "transfer",
      "source_channel": "channel-7",
      "token": { "denom": "uatom", "amount": "1000000" },
      "sender": "cosmos1...example",
      "receiver": "osmo1...example",
      "timeout_height": { "revision_number": "0", "revision_height": "0" },
      "timeout_timestamp": "1790000000000000000",
      "memo": ""
    }],
    "memo": "IBC transfer example",
    "timeout_height": "0"
  },
  "auth_info": {
    "signer_infos": [{
      "mode_info": { "single": { "mode": "SIGN_MODE_DIRECT" } },
      "sequence": "12"
    }],
    "fee": {
      "amount": [{ "denom": "uatom", "amount": "5000" }],
      "gas_limit": "200000"
    }
  },
  "signatures": ["BASE64_SIGNATURE_BYTES"]
}

token.amount 是最小單位的字串；若該 denom 有 6 decimals，1000000 可顯示為 1 顆，但 decimals 與 denom trace 要依來源鏈查證。auth_info.fee.amount 是來源交易費，與跨鏈 token amount 分開。sequence 是來源帳戶交易序號。外層 body.timeout_height 是交易限制；訊息內 timeout_height／timeout_timestamp 是 IBC packet 限制。上例以 timestamp 指定 packet timeout，零高度表示未以高度設限；timestamp 是 Unix nanoseconds，正式值要依目的鏈情況設定。

body.memo 是來源交易備註；MsgTransfer.memo 是 IBC transfer 訊息內的備註，可能供 middleware 使用。兩者不同，不應把任意 memo 內容當成可信指令。source_channel 需在來源鏈查；不能用目的鏈自己的 channel ID 替代。receiver 要用目的鏈正確的地址格式。

上方 signatures 的值只是占位文字，且省略了可選公鑰與預設欄位。實際 TxRaw 先把 body、auth_info 編成 Protobuf bytes；JSON 中的 bytes 通常顯示為 Base64，再連同真正簽章編碼：

SignDoc {
  body_bytes:      protobuf(TxBody),
  auth_info_bytes: protobuf(AuthInfo),
  chain_id:        "source-chain-id",
  account_number: "42"
}

TxRaw {
  body_bytes:      同一份 body bytes,
  auth_info_bytes: 同一份 auth info bytes,
  signatures:     [實際簽章 bytes]
}

這是結構示意，不是 JSON literal 或可簽署的範例資料。SignDoc 的 chain ID 與 account number 參與簽署，但不以同名頂層欄位出現在上述 TxRaw。SDK 要以確切的 Protobuf bytes 組合並簽署；修改 fee、memo、sequence 或 MsgTransfer 後，都必須重簽。

從簽署到結果：不要只看 tx hash

  1. 查 chain ID、account number、sequence 與 spendable balance；建立 Msg 和 fee。
  2. 模擬 gas，再依鏈的 fee token 與 gas price 決定 fee；確認 signer 授權。
  3. 依支援的 sign mode 編碼並簽署；廣播 TxRaw。
  4. 檢查交易是否收錄、code 是否成功、events 與實際餘額。RPC 接受或拿到 hash 不是執行成功。

sequence 是帳戶防重放的一部分，與 ECDSA 的秘密 k 不同。並行送單、逾時重試與替換費用時要重新讀鏈上狀態。gas_wanted 是要求上限，gas_used 是實際消耗；具體扣費與失敗處理按鏈的應用規則。跨鏈前還需確認發送者有來源鏈的 fee denom，不要只看要轉出的 token。

IBC 如何建立可信的跨鏈通道

IBC 的核心物件包括 client、connection、channel、packet。client 讓一條鏈驗證另一條鏈的共識狀態；connection 與 channel 連接應用端點；packet 承載資料與來源／目的 port、channel、sequence、timeout。Relayer 負責傳遞 header、packet 與證明，但不應靠 relayer 自稱「已到帳」作為真相；接收鏈驗證證明與通道狀態。

IBC 的安全取決於 client 對遠端鏈狀態的驗證和相關信任假設；活性還取決於 relayer、channel 與鏈本身的可用性。不同 IBC client 或 middleware 的風險不應一概視為相同。

ICS-20 轉帳：來源、目的、確認

來源鏈 A：使用者 MsgTransfer
  → 若 A 是資產源鏈方向：鎖定／escrow 原生資產
  → 若 voucher 正沿返回路徑：銷毀 voucher
  → 寫入 packet commitment（含 sequence 與 timeout）
        ↓ relayer 提交 packet 與證明
目的鏈 B：驗證 client／channel／proof，執行 OnRecvPacket
  → 依 denom trace 發行 voucher 或解鎖原資產
  → 寫入 acknowledgement（成功或應用錯誤）
        ↓ relayer 回傳 acknowledgement 與證明
來源鏈 A：處理 acknowledgement，清理 packet commitment
  → 成功：流程結束；錯誤：依 ICS-20 規則退款

denom trace 決定資產來源與回程行為。使用者介面常顯示 ibc/... hash，但只看 ticker 或畫面顯示名稱無法確認底層來源。需要核對 path、base denom、channel 與真正可回程的路徑。錯 channel 可能產生另一種 voucher，流動性與可退出性不同。

概念例：Alice 在 A 把 10 個 A 原生 token 經正確 channel 送到 B。A 鎖定 10，B 發行對應 voucher；回原路時可在 B 銷毀 voucher、於 A 解鎖原資產。這不是 B 上出現了額外 10 個無抵押的 A 原生 token。

Timeout、退款與 pending：最容易誤判的地方

觀察代表什麼下一步
來源鏈 tx 成功、SendPacket eventpacket 已發出記錄 port／channel／sequence／timeout，追蹤目的鏈
目的鏈 RecvPacket 成功且 ack 成功目的鏈應用已接受核對接收者資產與來源鏈 ack
目的鏈 ack 為錯誤目的鏈應用拒絕等待錯誤 ack 回到來源鏈後的退款處理
packet timeout 到期可能可提交 timeout 證明確認目的鏈未接收，提交／追蹤來源鏈 timeout；不能只看時鐘認定已退款
Relayer 暫停封包可能仍 pending查 commitment、receipt／ack、client 和 channel 狀態；避免直接重送新轉帳

Timeout 是協議邊界，不是「時間到自動返還」的產品保證。退款由目的鏈錯誤 acknowledgement 或已證明的 timeout 在來源鏈觸發；流程可能需要 relayer 提交交易。若目的鏈已成功接收，不能再合法地把同一 packet 當未接收退款。產品需要獨立追蹤每個 packet，而非只存來源交易 hash。

整合與安全驗收

  • 對每一條路徑固定並驗證 source／destination chain ID、port、channel、receiver 編碼、base denom 與 denom trace。
  • 分別測來源交易失敗、目的鏈拒絕、ack 遺失或延後、timeout、relayer 中斷、client 過期或凍結、channel 關閉。
  • 用 port／channel／sequence 定位 packet；避免因 UI timeout 而重送另一筆新轉帳。重試 relayer 提交與重做使用者轉帳是不同操作。
  • 在接收鏈核對實際到帳 denom 和 amount，再允許下游 swap／存款；來源鏈扣款不等於目的鏈可用餘額。
  • 監控 ack 與 timeout 的資金責任，設計客服可查的 pending、成功、退款狀態及證據。

PM 應把跨鏈延遲、費用、relayer／client／channel 可用性、voucher 流動性與退出路徑列入市場風險。路由可達不代表該資產可安全當抵押品，也不代表任何時間都有回程流動性。

Transaction versus packet

Following Ethereum and Solana, this note uses a conventional Cosmos SDK account, Protobuf SIGN_MODE_DIRECT and classic IBC ICS-20 transfers. Confirm chain-specific fees, denominations, signing support and IBC version.

The user submits a source-chain transaction containing MsgTransfer. A relayer later submits a separate destination-chain transaction with a packet proof, then relays acknowledgement or timeout evidence back. Source transaction success starts the cross-chain process.

TxBody, AuthInfo, SignDoc, TxRaw

TxBody: messages[], memo, transaction timeout_height
AuthInfo: signer_infos[] (key, sign mode, sequence), fee
SignDoc DIRECT: body_bytes, auth_info_bytes,
                chain_id, account_number
TxRaw: body_bytes, auth_info_bytes, signatures[]

Messages are encoded as Protobuf Any. The signer signs exact body/auth bytes plus chain and account context; serialized TxRaw is broadcast. Change memo, fee, gas, sequence or message and signatures must be redone. Signature order follows signer rules. Ordinary secp256k1 accounts commonly use 64-byte r || s without Ethereum v; other account types, multisig, sign modes and Cosmos EVM transactions differ. See the signature comparison.

What does an IBC transfer JSON object look like?

This is a teaching example of the decoded Protobuf JSON shape. Addresses, channel, amounts and timeout are illustrative and cannot be broadcast. Distinguish readable Tx, the SignDoc to sign, and the TxRaw bytes to broadcast. Do not sign the JSON text.

{
  "body": {
    "messages": [{
      "@type": "/ibc.applications.transfer.v1.MsgTransfer",
      "source_port": "transfer",
      "source_channel": "channel-7",
      "token": { "denom": "uatom", "amount": "1000000" },
      "sender": "cosmos1...example",
      "receiver": "osmo1...example",
      "timeout_height": { "revision_number": "0", "revision_height": "0" },
      "timeout_timestamp": "1790000000000000000",
      "memo": ""
    }],
    "memo": "IBC transfer example",
    "timeout_height": "0"
  },
  "auth_info": {
    "signer_infos": [{
      "mode_info": { "single": { "mode": "SIGN_MODE_DIRECT" } },
      "sequence": "12"
    }],
    "fee": {
      "amount": [{ "denom": "uatom", "amount": "5000" }],
      "gas_limit": "200000"
    }
  },
  "signatures": ["BASE64_SIGNATURE_BYTES"]
}

Token amount is an integer string in base units; check denomination and decimals before displaying it. Fee amount pays for the source transaction, separate from transferred tokens. Sequence is the source account transaction sequence. Outer body.timeout_height limits the transaction; the timeout fields inside MsgTransfer limit the IBC packet. Here the packet uses a timestamp and zero height; timestamp units are Unix nanoseconds. Choose real values for the destination chain.

The outer body memo and MsgTransfer memo serve different purposes. Middleware may interpret the latter, so do not treat arbitrary memo input as trusted instructions. Check the source chain's channel ID and the destination chain's receiver format.

The signature above is placeholder text; optional public key and default fields are omitted. In practice, serialize TxBody and AuthInfo to Protobuf bytes, then construct:

SignDoc {
  body_bytes: protobuf(TxBody),
  auth_info_bytes: protobuf(AuthInfo),
  chain_id: "source-chain-id",
  account_number: "42"
}
TxRaw {
  body_bytes: same exact body bytes,
  auth_info_bytes: same exact auth info bytes,
  signatures: [real signature bytes]
}

This is a structure sketch, not literal JSON or signable data. SignDoc chain ID and account number are signed but are not identically named top-level fields in TxRaw. SDKs must sign the exact Protobuf bytes; changing fee, memo, sequence or MsgTransfer requires new signatures.

Signing and execution

  1. Fetch chain ID, account number, sequence and spendable balances.
  2. Build messages, simulate gas and set fees in the chain's supported fee denom.
  3. Encode with a supported sign mode, sign and broadcast TxRaw.
  4. Check inclusion, response code, events and actual balances; a hash is not execution success.

Account sequence prevents transaction replay and is distinct from secret ECDSA k. Concurrent submissions and retries need chain-state checks. Gas wanted and gas used differ; fee behavior follows the application. Cross-chain transfers also need source-chain fee funds.

IBC trust and routing

IBC uses clients, connections, channels and packets. A client verifies another chain's state; connections and channels link application endpoints. Packets carry source and destination ports/channels, sequence, data and timeout. Relayers transmit headers, packets and proofs; destination chains verify proofs rather than trusting a relayer's claim. Safety depends on client assumptions, while liveness also depends on relayers, channels and chains.

ICS-20 lifecycle

A: MsgTransfer → escrow native asset or burn returning voucher
   → write packet commitment and timeout
Relayer: submit packet + proof
B: verify proof → mint voucher or unescrow native asset
   → write success/error acknowledgement
Relayer: submit acknowledgement + proof back to A
A: clear commitment; on error, apply ICS-20 refund rules

Denom trace identifies origin and return path; an ibc/... display hash or ticker alone does not. A wrong channel can produce a distinct voucher with different liquidity. For an A-native token, sending 10 to B locks 10 on A and creates a corresponding voucher on B. Returning by the valid path burns the voucher and unlocks the original asset.

Timeouts, refunds, and pending state

A successful source transaction and SendPacket event mean the packet was sent. Destination RecvPacket and successful acknowledgement establish destination acceptance. An application error acknowledgement can trigger a source refund when relayed. Expired timeout makes a timeout proof possible; it does not itself guarantee an automatic refund at a wall-clock instant. A relayer may need to submit the timeout transaction. If the destination already accepted the packet, the same packet cannot validly be refunded as unreceived.

Track port/channel/sequence, commitment, destination receipt and acknowledgement or timeout. A user-facing timeout is not grounds to create another transfer blindly.

Developer and product acceptance

  • Validate source and destination chains, ports/channels, receiver encoding and denomination trace.
  • Test source failure, destination rejection, delayed acknowledgement, timeout, relayer outage, expired/frozen client and closed channel.
  • Identify packets by port/channel/sequence; distinguish relayer retry from a new user transfer.
  • Check actual destination denomination and balance before downstream swaps or deposits.
  • Expose pending, success and refund states with evidence for support and operations.

PM risk includes delays, fees, relayer/client/channel liveness, voucher liquidity and exits. Route availability does not imply collateral suitability or guaranteed return liquidity.
