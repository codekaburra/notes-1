Smart Account 全貌

2026-09-09 · 帳戶抽象 · 開發者視角

smart account 就是「用一個合約當錢包」取代 EOA：合約持有資產，合約裡寫明誰有權動、依何規則動。本則從整合者角度講清楚三件事——UserOperation 怎麼在各合約間流動、帳戶合約要實作什麼、以及模組化怎麼運作。

設計理念：不改協議，另開一條路

EOA 的驗證邏輯寫死在協議裡（一組 secp256k1 簽章）。要突破它有兩條路，另一則筆記談 EIP-7702；本則談 ERC-4337：完全不改以太坊，改在鏈下開一條替代 mempool，讓使用者送出的不是交易，而是 UserOperation，由 Bundler 打包成真正的交易，經鏈上單例 EntryPoint 驗證與執行。

帳戶合約要實作什麼

只有一個必要函式。EntryPoint 這樣呼叫你，你只需回傳「這筆算不算數」：

function validateUserOp(PackedUserOperation calldata op, bytes32 opHash, uint256 missingFunds)
    external returns (uint256 validationData)
{
    require(msg.sender == ENTRY_POINT, "only EntryPoint");
    bool ok = _checkSig(opHash, op.signature);   // 換成 ECDSA / P256 / 多簽都在這

    // 回傳 0 = 通過；1 = 簽章失敗（用回傳值，別 revert，bundler 才能分辨）
    // 高位還能打包時效：validationData = authorizer | (validUntil << 160) | (validAfter << 208)
    if (missingFunds > 0) { (bool s,) = msg.sender.call{value: missingFunds}(""); s; }
    return ok ? 0 : 1;
}

另一個關鍵介面是 ERC-1271：合約沒有私鑰，dApp 要驗「這個合約帳戶的簽名」時，會呼叫它、期待拿到一個 magic value。缺了它，smart account 無法登入 dApp、簽 permit：

bytes4 constant MAGIC = 0x1626ba7e;              // isValidSignature 的 selector
function isValidSignature(bytes32 hash, bytes calldata sig) external view returns (bytes4) {
    return _checkSig(hash, sig) ? MAGIC : bytes4(0xffffffff);
}

模組化：ERC-7579

與其把邏輯寫死，不如做成可插拔模組。ERC-7579 定義四種型別，都實作 onInstall / onUninstall / isModuleType：

// 每個模組都要有這三個函式
function onInstall(bytes calldata data) external;        // 種入初始狀態
function onUninstall(bytes calldata data) external;      // 清除狀態
function isModuleType(uint256 t) external pure returns (bool);   // 1/2/3/4

常見成熟實作：Safe、Kernel（ZeroDev）、Coinbase Smart Wallet、Alchemy Modular Account、Biconomy Nexus。別自己從零寫。

前端：用 viem 送 UserOperation

viem 自 2.18 起內建帳戶抽象，Bundler 互動直接用它（permissionless.js 的 bundler client 已淘汰）：

import { createBundlerClient } from "viem/account-abstraction";

const bundler = createBundlerClient({ client: publicClient, transport: http(BUNDLER_URL) });

// calls 可以一次多筆 → 這就是「批次交易」的來源
const opHash = await bundler.sendUserOperation({
  account,                                   // 你的 smart account 物件
  calls: [{ to: token, data: approveData }, { to: dex, data: swapData }],
  // paymaster: {...}   // 要代付 gas 就帶 paymaster
});
const receipt = await bundler.waitForUserOperationReceipt({ hash: opHash });

EntryPoint 版本

三版並存；整合前先確認 Bundler 支援哪一版（可呼叫 eth_supportedEntryPoints 問）：

安全風險

開發者：

  • validateUserOp 必須 require(msg.sender == entryPoint)，且簽章錯要回傳 1 而非 revert。
  • 驗證階段受 ERC-7562 範圍規則限制（禁 TIMESTAMP／BALANCE 等、限制讀 storage）；踩到會被 Bundler 拒收，症狀是「邏輯對但收不進去」。
  • Paymaster 的 postOp 即使主流程 revert 仍會被呼叫（mode = opReverted），代付方仍要付錢——常見漏洞。

使用者（資產安全，非投資風險）：

  • 安裝模組＝授予權力。一個惡意或有 bug 的 validator／executor 模組，等於把帳戶整個交出去。只裝來源可信、經審計的模組。
  • 盲簽。smart account 常一次簽批次動作；看不懂內容就簽，等於簽空白支票。
  • 恢復設定。social recovery 的守護者名單設錯或被攻陷，帳戶可能被他人奪走。

三層關係

smart account 是合約錢包本身 → ERC-4337 讓它能被代送交易與代付 gas → ERC-7579 讓它的功能可如插件般拼裝。

Smart Accounts, End to End

2026-09-09 · Account Abstraction · Developer view

A smart account is "a contract as your wallet" in place of an EOA: the contract holds the assets and encodes who may move them and under what rules. This note covers three things from an integrator's angle — how a UserOperation flows between contracts, what the account contract must implement, and how modularity works.

Design idea: don't change the protocol, open a new lane

An EOA's validation is hardcoded into the protocol (one secp256k1 signature). There are two ways past it; another note covers EIP-7702, this one covers ERC-4337: change Ethereum not at all, and instead open an off-chain alternative mempool where users submit a UserOperation rather than a transaction, which a Bundler packs into a real transaction, validated and executed by the on-chain singleton EntryPoint.

What the account contract implements

Just one required function. EntryPoint calls you like this; you only return "does this op count":

function validateUserOp(PackedUserOperation calldata op, bytes32 opHash, uint256 missingFunds)
    external returns (uint256 validationData)
{
    require(msg.sender == ENTRY_POINT, "only EntryPoint");
    bool ok = _checkSig(opHash, op.signature);   // swap in ECDSA / P256 / multisig here

    // return 0 = valid; 1 = bad signature (return it, don't revert — bundlers rely on this)
    // the high bits also pack time bounds: validationData = authorizer | (validUntil << 160) | (validAfter << 208)
    if (missingFunds > 0) { (bool s,) = msg.sender.call{value: missingFunds}(""); s; }
    return ok ? 0 : 1;
}

The other key interface is ERC-1271: a contract has no private key, so when a dApp verifies "this contract account's signature" it calls this and expects a magic value. Without it, a smart account cannot sign into dApps or sign a permit:

bytes4 constant MAGIC = 0x1626ba7e;              // the isValidSignature selector
function isValidSignature(bytes32 hash, bytes calldata sig) external view returns (bytes4) {
    return _checkSig(hash, sig) ? MAGIC : bytes4(0xffffffff);
}

Modularity: ERC-7579

Rather than hardcoding logic, make it pluggable. ERC-7579 defines four module types, all implementing onInstall / onUninstall / isModuleType:

// every module implements these three
function onInstall(bytes calldata data) external;        // seed initial state
function onUninstall(bytes calldata data) external;      // clean up state
function isModuleType(uint256 t) external pure returns (bool);   // 1/2/3/4

Common mature implementations: Safe, Kernel (ZeroDev), Coinbase Smart Wallet, Alchemy Modular Account, Biconomy Nexus. Don't roll your own.

Front end: sending a UserOperation with viem

viem has native account abstraction since 2.18, so bundler interaction goes straight through it (permissionless.js's bundler client is deprecated):

import { createBundlerClient } from "viem/account-abstraction";

const bundler = createBundlerClient({ client: publicClient, transport: http(BUNDLER_URL) });

// calls can be several at once → this is where "batched transactions" come from
const opHash = await bundler.sendUserOperation({
  account,                                   // your smart account object
  calls: [{ to: token, data: approveData }, { to: dex, data: swapData }],
  // paymaster: {...}   // add a paymaster to sponsor gas
});
const receipt = await bundler.waitForUserOperationReceipt({ hash: opHash });

Security risk

Developers:

  • validateUserOp must require(msg.sender == entryPoint), and return 1 on a bad signature rather than revert.
  • Validation is bound by ERC-7562 scope rules (no TIMESTAMP/BALANCE etc., limited storage reads); breaking them makes the Bundler reject the op — the "logic is right but it won't go in" symptom.
  • A paymaster's postOp is called even if the main flow reverts (mode = opReverted); the sponsor still pays — a common bug.

Users (asset safety, not investment risk):

  • Installing a module grants power. A malicious or buggy validator/executor module hands over the whole account. Install only trusted, audited modules.
  • Blind signing. Smart accounts often sign a batch at once; signing what you can't read is a blank cheque.
  • Recovery config. A mis-set or compromised social-recovery guardian list can let someone take the account.

Three layers

A smart account is the contract wallet itself → ERC-4337 gets it relayed and its gas sponsored → ERC-7579 lets its features be assembled like plugins.
