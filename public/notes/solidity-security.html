Solidity 安全漏洞圖鑑

2026-09-18 · SOLIDITY · 安全 · 攻擊流程 · 開發者指南

八類真正會讓錢消失的漏洞：每一類都給攻擊流程、易受攻擊的程式碼、以及修好的版本。重點不是背名詞，而是建立一種直覺——看到某種寫法就本能地警覺。

三句話版本
  • 絕大多數合約漏洞可以歸到一句話：你在狀態還沒更新完之前，把控制權交給了別人——重入、預言機、簽章重放都是這個形狀。
  • 但要先認清一個殘酷的統計：2026 上半年約 76% 的失竊金額來自金鑰與營運層面的外洩，不是巧妙的 Solidity bug。程式碼漏洞貢獻的是事件數，不是金額。
  • 所以真正的防禦順序是：先把權限與金鑰管好，再談程式碼技巧。一個 onlyOwner 寫漏，比任何精妙的重入都致命。

誰讀哪裡：初學者 → 先讀「重入」與「存取控制」兩節，這兩類佔了大部分事故；有經驗的 Solidity 工程師 → 直接看「價格操縱」「精度與四捨五入」「storage collision」；PM／技術主管 → 市場背景與最後的「流程比技巧重要」。

市場背景：錢實際上是怎麼丟的

這節的數字會改變你分配安全預算的方式。2026 上半年的事故次數創了新高，金額卻明顯下降——意思是：小型、新上線、未經審計的協議被打爆得更頻繁，但大額損失的來源另有其人。

指標數字
2026 H1 總失竊金額約 $0.97B–1.32B（各來源口徑不一）
2026 H1 事件數約 207–224 起（歷史新高）
對照：2025 H1 金額約 $2.3B
基礎設施／營運類佔失竊金額約 76%（僅約 15% 的事件數）
私鑰外洩佔歷史總損失約 24.4%
釣魚佔歷史總損失約 19.5%
存取控制失誤佔歷史總損失約 12.8%（約 $994M）
價格操縱攻擊中使用閃電貸的比例約 62.1%

數據為約略值，各來源統計口徑與期間不一；以 2026-09 查得為準。

把前三項加起來：私鑰外洩 + 釣魚 + 存取控制 ≈ 總損失的 57%。這三者沒有一項需要攻擊者懂組合語言，它們考驗的是誰能動什麼、鑰匙放哪裡。2026 年最大的兩起（Drift 約 $280M、KelpDAO 約 $293M）也都不是經典的演算法漏洞——Drift 是升級機制出問題。

結論很直白：先做對權限設計、多簽與升級流程，再去研究重入的精妙變體。順序反了，等於在紙門上裝三道鎖。

一、重入（Reentrancy）

最經典、也最能說明核心直覺的一類。問題不在「轉帳」，而在轉帳這個動作會把控制權交給對方，而你的帳還沒記完。

// ✗ 易受攻擊：先轉錢，後歸零
mapping(address => uint256) public balances;

function withdraw() external {
    uint256 amount = balances[msg.sender];
    (bool ok, ) = msg.sender.call{value: amount}("");   // ← 控制權在此交出去
    require(ok, "transfer failed");
    balances[msg.sender] = 0;                            // ← 太晚了
}

攻擊者只要是一個合約，在收款的 receive() 裡再呼叫一次 withdraw()，此時 balances 尚未歸零，於是又領一次：

contract Attacker {
    Victim victim;
    receive() external payable {
        if (address(victim).balance >= 1 ether) victim.withdraw();  // 再進去一次
    }
}

修法：CEI 順序

把狀態更新排到外部呼叫之前，攻擊者重入時讀到的就是新值：

function withdraw() external {
    uint256 amount = balances[msg.sender];        // Checks
    require(amount > 0, "nothing to withdraw");
    balances[msg.sender] = 0;                     // Effects  ← 提前
    (bool ok, ) = msg.sender.call{value: amount}(""); // Interactions ← 最後
    require(ok, "transfer failed");
}

唯讀重入：容易被忽略的變體

即使你的合約自己不受影響，別人讀你的 view 函式時可能拿到中間狀態。經典情境：某池在轉帳回呼期間，內部餘額已扣、總量尚未更新，此時 getPrice() 回傳的是失真的值；另一個協議剛好在這瞬間讀它來估值，就被騙了。

  • 防禦方：不要相信任何可在單筆交易內被改動的 view 報價，讀之前先確認對方沒有處於鎖定狀態。
  • 提供方：把 reentrancy guard 也套在 view 函式上（或提供一個可供外部查詢鎖狀態的介面）。

二、存取控制（損失金額的最大宗）

最不炫技、卻造成最多損失的一類。三種典型寫法：

// ✗ 忘記加修飾器 —— 任何人都能改 owner
function setOwner(address newOwner) external { owner = newOwner; }

// ✗ 用 tx.origin 驗身份 —— 使用者被釣到惡意合約就失守
require(tx.origin == owner, "not owner");

// ✗ 初始化沒有保護 —— 部署後被搶先呼叫，攻擊者變 owner
function initialize(address _owner) external { owner = _owner; }
// ✓ 用修飾器，並且驗 msg.sender 而非 tx.origin
function setOwner(address newOwner) external onlyOwner {
    require(newOwner != address(0), "zero address");
    owner = newOwner;
}

// ✓ 初始化只能跑一次，且部署與初始化應在同一筆交易完成
function initialize(address _owner) external initializer { owner = _owner; }

tx.origin 為何危險：它是「這筆交易的最初發起人」。使用者若被誘導呼叫攻擊者的合約，該合約再去呼叫你的合約時，tx.origin 仍是使用者本人——驗證就這樣被繞過。身份驗證一律用 msg.sender。

另外兩個實務重點：

  • 單一 owner 是單點風險。關鍵權限（升級、提領、參數）應由多簽持有，並加時間鎖，讓社群有機會看到即將發生的變更。
  • 權限要能列舉。寫下「哪些函式受保護、被誰持有」的清單並定期核對；漏掉修飾器多半不是不懂，而是新增函式時忘了。

三、價格操縱：閃電貸的主戰場

約 62% 的價格操縱攻擊用到閃電貸。原因很簡單：閃電貸讓攻擊者在不需要本金的情況下，於單筆交易內取得足以撼動市場的資金。

// ✗ 直接讀現貨池的即時價 —— 單筆交易內即可被推歪
(uint160 sqrtPriceX96,,,,,,) = pool.slot0();
uint256 price = _priceFromSqrt(sqrtPriceX96);
uint256 collateralValue = amount * price;          // 以被操縱的價格估值
// ✓ 方案 A：TWAP（時間加權），拉長操縱所需的成本與時間
(int24 meanTick, ) = OracleLibrary.consult(pool, 1800);   // 30 分鐘均價

// ✓ 方案 B：外部預言機，並且務必檢查新鮮度與合理性
(, int256 answer, , uint256 updatedAt, ) = feed.latestRoundData();
require(answer > 0, "bad price");
require(block.timestamp - updatedAt < 3600, "stale price");   // 別忘了這行

兩個常見的半吊子防禦：只檢查 answer > 0 卻不檢查 updatedAt（預言機停更時你會用到過期價格），以及用單一來源的 TWAP 卻設得太短（幾個區塊的 TWAP 在低流動性池仍可被操縱）。

四、簽章：重放與驗證

// ✗ 沒有 nonce、沒綁 chainId、沒綁合約位址 → 可無限重放、跨鏈重放
bytes32 h = keccak256(abi.encodePacked(to, amount));
require(ECDSA.recover(h, sig) == owner, "bad sig");

// ✗ 直接用 ecrecover：驗證失敗時回傳 address(0)
//    若 owner 剛好未初始化（也是 0），任何壞簽章都會通過
require(ecrecover(h, v, r, s) == owner);
// ✓ EIP-712：綁定 chainId 與 verifyingContract，並用 nonce 防重放
bytes32 structHash = keccak256(abi.encode(TYPEHASH, to, amount, nonces[owner]++));
bytes32 digest = _hashTypedDataV4(structHash);   // 內含 domain separator
address signer = ECDSA.recover(digest, sig);     // OZ 版本失敗會 revert，不回 0
require(signer == owner && signer != address(0), "bad sig");

檢查清單：nonce（防同鏈重放）、chainId（防跨鏈重放）、verifyingContract（防跨合約重放）、deadline（限制有效期）。四項缺一，就存在對應的重放面。

五、外部呼叫與回傳值

ERC-20 的實作分歧是長年的坑：有些代幣（如 USDT）不回傳 bool，有些失敗時只回 false 而不 revert。

// ✗ 對 USDT 這類代幣會因為沒有回傳值而 revert
require(token.transfer(to, amount), "transfer failed");

// ✗ 忽略回傳值 —— 失敗了你也不知道
token.transfer(to, amount);

// ✓ 用 SafeERC20 統一處理兩種行為
using SafeERC20 for IERC20;
token.safeTransfer(to, amount);
// ✓ fee-on-transfer 代幣：實收金額不等於你要求的金額
uint256 balBefore = token.balanceOf(address(this));
token.safeTransferFrom(msg.sender, address(this), amount);
uint256 received = token.balanceOf(address(this)) - balBefore;
_credit(msg.sender, received);      // 用實收，不要用 amount

低階呼叫也要記得：call 對不存在的位址會回傳 success = true。若目標可能不是合約，需額外檢查 code.length。

六、精度與四捨五入：ERC-4626 通膨攻擊

整數除法一律向下取整，這個看似無害的性質是金庫類合約的經典破口。

三種修法，建議一起用：

  • 虛擬股數／資產偏移：OpenZeppelin 的 ERC-4626 預設加入虛擬 offset，讓首存者無法把每股淨值推到極端。這是最省事且有效的一層。
  • 部署時預先注入：部署者自己先存一筆並燒掉那些 share，使金庫永不為空。
  • 取整方向要對自己不利：鑄造 share 時向下取整、贖回時也向下取整，讓誤差永遠留在金庫而非使用者身上。

七、delegatecall 與 storage collision

delegatecall 用呼叫方的儲存空間執行對方的程式碼。代理模式靠它運作，也因此對 slot 排列極度敏感。

  • 只在尾端追加，永不刪除或重排既有變數；或直接採用 ERC-7201 命名空間儲存，把每個模組的變數放進以雜湊算出的獨立區段，從根本避免碰撞。
  • 代理自身的變數要放特殊槽位：EIP-1967 規定 implementation 與 admin 的槽位由特定字串雜湊而來，就是為了不跟應用層變數撞在一起。
  • 絕不 delegatecall 到不可信的位址——那等於把自己的儲存空間交給對方任意改寫。

八、拒絕服務與 griefing

// ✗ push 付款 + 無界迴圈：一個收款人 revert，全部人都領不到
for (uint256 i = 0; i < recipients.length; i++) {
    payable(recipients[i]).transfer(amounts[i]);   // 對方是合約且 receive revert → 整批失敗
}
// ✓ pull 模式：只記帳，讓各自來領；單一失敗不影響其他人
function allocate(address to, uint256 amount) internal { credits[to] += amount; }

function claim() external {
    uint256 amount = credits[msg.sender];
    require(amount > 0, "nothing to claim");
    credits[msg.sender] = 0;                       // Effects 先行
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok, "transfer failed");
}

同理，任何長度由使用者控制的迴圈都是風險：攻擊者只要把陣列灌到超過區塊 gas 上限，該函式就永遠無法執行。

流程比技巧重要

回到市場背景那個數字——大部分的錢不是被精妙的漏洞拿走的。以下依投報率排序：

  1. 權限盤點：列出所有特權函式與持有者。關鍵權限交多簽 + 時間鎖，不要單一 EOA。
  2. 金鑰管理：硬體錢包、簽署流程、離職交接。這一項的期望損失高於所有程式碼技巧的總和。
  3. 測試：fuzz 與 invariant testing 找得到人眼看不到的邊界；fork 測試用真實狀態驗證整合假設。
  4. 審計：但要知道審計不是保證。研究顯示公開審計發現與實際事故之間存在明顯落差——審計是降低機率，不是消除風險。
  5. 監控與應變：異常提領告警、暫停開關、事故劇本。假設它總有一天會發生。

使用者風險

風險說明
無限授權多數 dApp 預設請求無上限的 approve。合約若被攻破，你的代幣會依該授權被搬走。定期到授權管理工具檢視並撤銷。
釣魚簽章約 19.5% 的歷史損失來自釣魚。看不懂的簽章一律不簽——尤其 Permit 與 setApprovalForAll。
新協議風險最高事件數集中在新上線、未經審計的協議。高 APY 通常反映的是風險，不是效率。
升級權限可升級合約代表有人能改寫規則。進場前確認誰持有升級權、是否多簽、有無時間鎖。
審計不等於安全「已審計」只代表某時點的某個版本被看過；升級後的程式碼未必在範圍內。

Solidity Security: A Field Guide

2026-09-18 · SOLIDITY · SECURITY · ATTACK FLOWS · DEVELOPER GUIDE

Eight classes of bug that actually make money disappear: each with the attack flow, the vulnerable code, and the fixed version. The goal is not memorising names but building an instinct — seeing a shape of code and flinching.

In three lines
  • Most contract bugs reduce to one sentence: you handed control to someone else before your state was finished updating — reentrancy, oracles and signature replay are all that shape.
  • But face a blunt statistic first: about 76% of funds stolen in H1 2026 came from key and operational compromise, not clever Solidity bugs. Code bugs drive the incident count, not the money.
  • So the real defence order is: get permissions and keys right first, then worry about code technique. One missing onlyOwner is deadlier than any elegant reentrancy.

Where to start: beginners → read "Reentrancy" and "Access control", which account for most incidents; experienced Solidity engineers → go straight to "Price manipulation", "Rounding" and "Storage collision"; PMs and tech leads → market background and "Process beats technique".

Market background: how the money actually goes

These numbers should change how you allocate a security budget. H1 2026 set a record for incident count while losses fell sharply — meaning small, newly launched, unaudited protocols get hit more often, while the large losses come from somewhere else entirely.

Add the first three: key compromise + phishing + access control ≈ 57% of total losses. None of them requires the attacker to understand assembly; they test who can do what, and where the keys live. The two largest incidents of 2026 (Drift ~$280M, KelpDAO ~$293M) were not classic algorithmic bugs either — Drift's was an upgrade mechanism.

The conclusion is plain: get permission design, multisig and upgrade process right before studying exotic reentrancy variants. Reversed, it is three locks on a paper door.

1. Reentrancy

The classic, and the best illustration of the core instinct. The problem is not "transferring" but that transferring hands control to the recipient while your books are still open.

// x Vulnerable: send first, zero the balance afterwards
mapping(address => uint256) public balances;

function withdraw() external {
    uint256 amount = balances[msg.sender];
    (bool ok, ) = msg.sender.call{value: amount}("");   // control leaves here
    require(ok, "transfer failed");
    balances[msg.sender] = 0;                            // too late
}

The attacker only has to be a contract: in its receive() it calls withdraw() again, while balances is still un-zeroed, and withdraws once more:

contract Attacker {
    Victim victim;
    receive() external payable {
        if (address(victim).balance >= 1 ether) victim.withdraw();  // go in again
    }
}

The fix: CEI ordering

Move the state update before the external call, so a reentrant caller reads the new value:

function withdraw() external {
    uint256 amount = balances[msg.sender];        // Checks
    require(amount > 0, "nothing to withdraw");
    balances[msg.sender] = 0;                     // Effects  ← moved up
    (bool ok, ) = msg.sender.call{value: amount}(""); // Interactions ← last
    require(ok, "transfer failed");
}

Read-only reentrancy: the overlooked variant

Even if your own contract is safe, someone reading your view function may get mid-update state. The classic case: during a transfer callback a pool has debited internal balances but not yet updated totals, so getPrice() returns a distorted value — and another protocol reading it at that instant is fooled.

  • As a consumer: never trust a view quote that can be moved within one transaction; check the source is not mid-operation.
  • As a provider: apply the reentrancy guard to view functions too, or expose a way to query the lock state.

2. Access control (the largest share of losses)

The least clever class, and the most costly. Three typical forms:

// x Missing modifier — anyone can take ownership
function setOwner(address newOwner) external { owner = newOwner; }

// x tx.origin for identity — phish the user into a malicious contract and it falls
require(tx.origin == owner, "not owner");

// x Unprotected initialiser — front-run after deployment, attacker becomes owner
function initialize(address _owner) external { owner = _owner; }
// OK Use a modifier, and check msg.sender rather than tx.origin
function setOwner(address newOwner) external onlyOwner {
    require(newOwner != address(0), "zero address");
    owner = newOwner;
}

// OK Initialise once, and deploy + initialise in the same transaction
function initialize(address _owner) external initializer { owner = _owner; }

Why tx.origin is dangerous: it is the transaction's original sender. If a user is lured into calling an attacker's contract, which then calls yours, tx.origin is still the user — and the check is bypassed. Always authenticate with msg.sender.

  • A single owner is a single point of failure. Critical rights (upgrade, withdraw, parameters) belong to a multisig with a timelock, so changes are visible before they land.
  • Permissions must be enumerable. Keep a list of which functions are protected and by whom, and review it — a missing modifier is almost never ignorance, it is a function added later.

3. Price manipulation: the flash loan's home ground

About 62% of price-manipulation attacks use a flash loan, for a simple reason: it gives the attacker enough capital to move a market without any of their own, inside one transaction.

// x Reading the live spot price — movable within a single transaction
(uint160 sqrtPriceX96,,,,,,) = pool.slot0();
uint256 price = _priceFromSqrt(sqrtPriceX96);
uint256 collateralValue = amount * price;          // valued at a manipulated price
// OK Option A: a TWAP, which raises the cost and duration of manipulation
(int24 meanTick, ) = OracleLibrary.consult(pool, 1800);   // 30-minute mean

// OK Option B: an external oracle — but always check freshness and sanity
(, int256 answer, , uint256 updatedAt, ) = feed.latestRoundData();
require(answer > 0, "bad price");
require(block.timestamp - updatedAt < 3600, "stale price");   // don't skip this

Two common half-defences: checking answer > 0 but not updatedAt (you will happily use a stale price when the feed stops updating), and a single-source TWAP set too short (a few blocks is still manipulable in a thin pool).

4. Signatures: replay and verification

// x No nonce, no chainId, no contract address → replayable, including cross-chain
bytes32 h = keccak256(abi.encodePacked(to, amount));
require(ECDSA.recover(h, sig) == owner, "bad sig");

// x Raw ecrecover returns address(0) on failure
//   if owner happens to be uninitialised (also 0), every bad signature passes
require(ecrecover(h, v, r, s) == owner);
// OK EIP-712: binds chainId and verifyingContract, with a nonce against replay
bytes32 structHash = keccak256(abi.encode(TYPEHASH, to, amount, nonces[owner]++));
bytes32 digest = _hashTypedDataV4(structHash);   // includes the domain separator
address signer = ECDSA.recover(digest, sig);     // the OZ version reverts, never returns 0
require(signer == owner && signer != address(0), "bad sig");

The checklist: nonce (same-chain replay), chainId (cross-chain replay), verifyingContract (cross-contract replay), deadline (validity window). Miss one and you have the matching replay surface.

5. External calls and return values

ERC-20 implementations diverge: some tokens (USDT among them) return no bool, and some return false instead of reverting on failure.

// x Reverts on USDT-style tokens because there is no return value to decode
require(token.transfer(to, amount), "transfer failed");

// x Ignoring the return value — a silent failure
token.transfer(to, amount);

// OK SafeERC20 normalises both behaviours
using SafeERC20 for IERC20;
token.safeTransfer(to, amount);
// OK Fee-on-transfer tokens: what arrives is not what you asked for
uint256 balBefore = token.balanceOf(address(this));
token.safeTransferFrom(msg.sender, address(this), amount);
uint256 received = token.balanceOf(address(this)) - balBefore;
_credit(msg.sender, received);      // credit what arrived, not `amount`

Low-level calls need care too: call to an address with no code returns success = true. If the target might not be a contract, check code.length as well.

6. Rounding: the ERC-4626 inflation attack

Integer division always rounds down. That innocuous property is the classic break in vault contracts.

Three fixes, best used together:

  • Virtual shares / asset offset: OpenZeppelin's ERC-4626 adds a virtual offset by default so a first depositor cannot push value-per-share to an extreme. The cheapest effective layer.
  • Seed at deployment: the deployer makes the first deposit and burns those shares, so the vault is never empty.
  • Round against the user: round down when minting shares and when redeeming, so the residue always stays in the vault rather than leaking out.

7. delegatecall and storage collision

delegatecall runs someone else's code against your storage. Proxies depend on it, which makes them acutely sensitive to slot layout.

  • Append only; never delete or reorder existing variables. Or adopt ERC-7201 namespaced storage, which places each module's variables in a hashed, independent region and removes collisions by construction.
  • The proxy's own variables belong in special slots: EIP-1967 derives the implementation and admin slots from specific string hashes precisely so they cannot clash with application storage.
  • Never delegatecall an untrusted address — that is handing over your storage to be rewritten at will.

8. Denial of service and griefing

// x Push payments in an unbounded loop: one reverting recipient blocks everyone
for (uint256 i = 0; i < recipients.length; i++) {
    payable(recipients[i]).transfer(amounts[i]);   // a contract whose receive reverts kills the batch
}
// OK Pull pattern: record credit, let each party claim; one failure affects nobody else
function allocate(address to, uint256 amount) internal { credits[to] += amount; }

function claim() external {
    uint256 amount = credits[msg.sender];
    require(amount > 0, "nothing to claim");
    credits[msg.sender] = 0;                       // Effects first
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok, "transfer failed");
}

The same logic applies to any loop whose length a user controls: an attacker only has to grow the array past the block gas limit and the function becomes permanently uncallable.

Process beats technique

Back to that market figure — most of the money is not taken by elegant bugs. In order of return on effort:

  1. Audit your permissions: list every privileged function and its holder. Critical rights go to a multisig with a timelock, never a lone EOA.
  2. Key management: hardware wallets, signing procedure, offboarding. Expected loss here exceeds every code technique combined.
  3. Testing: fuzz and invariant tests find edges eyes cannot; fork tests validate integration assumptions against real state.
  4. Audits: but know their limits. Research shows a clear gap between public audit findings and real incidents — an audit lowers probability, it does not remove risk.
  5. Monitoring and response: withdrawal alerts, a pause switch, an incident runbook. Assume it happens eventually.
