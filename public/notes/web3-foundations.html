Web3 入門：帳戶、資產與交易

先建立一個心智模型：wallet 是管理權限與簽署請求的工具；資產在鏈上的帳目裡。連 wallet 不代表授權 spender，簽名不代表已完成交易，而 tx hash 不代表資產已到帳。

帳戶與資產在哪？

EOA 由私鑰控制；smart account 由合約定義授權，可能有 owner、guardian、session key 與 upgrade admin。多個角色不能簡化成「誰握 private key 就擁有一切」。原生 ETH balance 由鏈維護，ERC-20 的 balanceOf(address) 則由各 token 合約記帳。相同 address 在不同鏈有獨立餘額與權限。

Token symbol 不是身份。紀錄 chain ID + contract address + decimals，例如 6 位小數的 1.25 token 是 1,250,000 base units。不要用浮點 Number 做金額運算。代理 token 的升級或管理權也能改變風險，地址相同不表示 code 永遠相同。

連線、簽名、授權、交易：四種不同能力

動作改變什麼先看哪裡
Connect wallet提供地址／連線狀態；本身不搬資產網站、chain、請求權限
Sign message / typed data通常不立即改鏈上 state，但簽章可被提交以執行 permit／訂單等授權domain、chain、spender、amount、expiry、nonce
approve(spender, amount)給特定 spender transferFrom 的額度；approve 不等於已存入協議真正會拉款的合約與額度
Send transaction執行 calldata/value 並花 gas；可能成功或 reverttarget、方法、參數、value、fee、simulation

一筆操作的邏輯流

使用者意圖 → 校驗 chain/地址/amount → RPC 讀 state → 模擬 → wallet 顯示並簽署 → submission → mempool/排序 → included receipt → 所需 finality → UI/indexer 更新。RPC 是讀寫入口，不是資產託管方；它可以延遲、錯誤或不一致。

同鏈單筆交易通常原子完成：內部失敗向外傳播會回滾狀態，但 gas 已花。合約可刻意 catch/recover，batch 也可容許部分失敗，因此先讀該入口的語意。跨鏈則由多筆交易組成，source 成功不保證 destination 成功。

初學者最容易混淆的五件事

Receipt status success 只描述該交易，不等於協議後續工作完成；包含多個 UserOp 的 bundle 需逐個看結果。Simulation 是當下 state 的預演，不是未來保證。Confirmations、safe、finalized 是不同層級；L2 wallet 的綠勾常只是 sequencer 確認。

Approval 留在鏈上，斷開網站不會撤銷；撤 delegation 也不自動撤 token allowance。Bridged token 與 native token 即使名稱相同，也有不同 backing/exit。APY、TVL 與 auditor 名稱不等於可提款或安全。

學習與驗收任務

只用測試環境：查看某地址的 native balance 與 token balance，解析 decimals，讀 allowance；模擬一次 transfer，再讀 receipt 與兩方餘額。嘗試 amount 超過 balance、錯 chain 和沒有 gas，分辨 wallet rejection、RPC failure 與 on-chain revert。

接著讀 gas、AMM、借貸、整合流程。PM 要先回答資產在哪、誰能動、收益哪來、失敗怎麼退出；工程師把同樣四題變成可測的 invariant。

Web3 Foundations: Accounts, Assets, and Transactions

2026-10-08 · FOUNDATIONS · DEVELOPMENT · PRODUCT · RISK

In this note

  3. One operation’s logic flow
  4. Five common misconceptions
  5. Learning and acceptance exercise
  6. References

A wallet manages authority and signing requests; assets live in on-chain accounting. Connecting does not grant spending authority, a signature does not mean execution, and a transaction hash does not mean funds arrived.

Where do accounts and assets live?

An EOA is key-controlled; a smart account defines authority in code and may have owners, guardians, session keys, and upgrade admins. These powers cannot always be reduced to one private key. The chain tracks native ETH balances; each ERC-20 contract tracks balanceOf(address). The same address on another chain has independent balances and authority.

A symbol is not identity. Record chain ID, contract address, and decimals: 1.25 tokens at six decimals equals 1,250,000 base units. Use integers, not floating-point Number. Proxy upgrades and token admin powers matter even when the token address stays unchanged.

Connection, signature, approval, and transaction

ActionWhat changesWhat to inspect
Connect walletExposes an address/connection; does not itself move fundsWebsite, chain, requested permissions
Sign message / typed dataOften no immediate state change; may authorize later permits/ordersDomain, chain, spender, amount, expiry, nonce
approve(spender, amount)Creates transferFrom allowance; does not deposit into a protocolActual pulling contract and allowance
Send transactionExecutes calldata/value and consumes gas; can succeed or revertTarget, method, parameters, value, fee, simulation

One operation’s logic flow

Intent → validate chain/address/amount → RPC state read → simulation → wallet review/signature → submission → mempool/ordering → included receipt → required finality → UI/indexer reconciliation. RPCs provide access, not asset custody; responses can lag, fail, or disagree.

A same-chain transaction typically rolls state back when an uncaught failure propagates, while gas remains spent. Contracts may catch failures and batches may allow partial execution: read the actual entrypoint semantics. Cross-chain actions use multiple transactions; source success does not guarantee destination success.

Five common misconceptions

Receipt success describes that transaction, not every downstream job; a UserOp bundle requires per-operation results. Simulation previews current state rather than guaranteeing future execution. Confirmations, safe, and finalized differ; an L2 wallet checkmark may only be sequencer confirmation.

Disconnecting a website does not revoke allowances. Clearing delegation does not revoke token approvals. Native and bridged tokens with the same name can have different backing and exits. APY, TVL, and auditor names do not prove withdrawal liquidity or safety.

Learning and acceptance exercise

Use a test environment: read native/token balances, decimals, and allowance. Simulate a transfer, inspect its receipt, and reconcile both balances. Try insufficient balance, wrong chain, and no gas; distinguish wallet rejection, RPC failure, and an on-chain revert.

Continue with gas, AMMs, lending, and integration. PMs should answer where assets live, who can move them, where yield comes from, and how failure exits work; developers turn those questions into invariants.
