閃電貸

2026-09-19 · DEFI · 原子性 · AAVE · 開發者指南

無需抵押、金額不限、費用極低——條件只有一個：在同一筆交易結束前還清。這則講它為什麼能成立、怎麼寫、以及為什麼它同時是最有用的工具與最危險的攻擊載體。

三句話版本
  • 閃電貸不是「信任你會還」，而是還不出來就整筆交易 revert，等於借款從未發生。它是區塊鏈原子性的直接產物，傳統金融做不到。
  • 因此它徹底廢除了「資本」這道門檻：任何人都能在一瞬間調動數億美元。套利者用它，攻擊者也用它。
  • 它本身不是漏洞。約 62% 的價格操縱攻擊用到閃電貸，但真正的漏洞是「協議讀了可被單筆交易推動的價格」——閃電貸只是讓攻擊變便宜。

誰讀哪裡：初學者 → 先看「為什麼能不用抵押」；Solidity 工程師 → 直接看實作與抵押品置換範例；PM／風控 → 市場背景與「它如何改變威脅模型」。

市場背景

閃電貸的經濟規模不在「借出多少」（因為借完就還，未平倉永遠是零），而在它改變了誰能發動大額操作。

指標數字
Aave V3 閃電貸費率（預設）0.05%（FLASHLOAN_PREMIUM_TOTAL，可治理調整）
其中歸協議的部分約 4 bps；其餘歸存款人
價格操縱攻擊中使用閃電貸的比例約 62.1%
Aave 佔借貸類 TVL約 35.1%（類別總額約 $51.96B）
攻擊者所需自有資金僅 gas

數據為約略值，以 2026-09 查得為準；費率由治理決定，使用前請讀鏈上實際值。

最後一列才是重點。傳統金融的風控有一個隱含假設：能動用一億美元的人不多，且他們有身份、有聲譽、有法律責任。閃電貸讓這個假設徹底失效——攻擊者匿名、零成本、失敗不罰。所有「因為攻擊者沒那麼多錢所以不會發生」的風險評估，在 2020 年之後都作廢了。

為什麼可以不用抵押

關鍵是原子性：一筆以太坊交易要嘛全部成功，要嘛全部回滾。借款合約的邏輯其實很笨：

  1. 把錢轉給你。
  2. 呼叫你的回呼函式，讓你愛做什麼做什麼。
  3. 回來檢查餘額：有沒有還夠？
  4. 沒還夠就 revert——連同第 1 步的轉帳一起撤銷，彷彿從未發生。

所以放款方不需要信任你，也不需要抵押品。它唯一承擔的風險是 gas，而那由你付。

實作：Aave V3

兩個入口：flashLoanSimple（單一資產，較省 gas）與 flashLoan（多資產）。以 simple 版為例，你的合約只需實作一個回呼：

contract MyFlashLoan is IFlashLoanSimpleReceiver {
    IPool public immutable POOL;

    // ① 發起：Pool 會先轉錢給我，再回呼下面的 executeOperation
    function start(address asset, uint256 amount) external {
        POOL.flashLoanSimple(
            address(this),   // receiver
            asset,
            amount,
            "",              // params：會原封不動傳進回呼
            0                // referralCode
        );
    }

    // ② Pool 回呼這裡；此刻 asset 已經在本合約餘額中
    function executeOperation(
        address asset,
        uint256 amount,
        uint256 premium,     // 手續費，約 amount 的 0.05%
        address initiator,
        bytes calldata params
    ) external override returns (bool) {
        require(msg.sender == address(POOL), "only pool");      // ← 絕不可少
        require(initiator == address(this), "bad initiator");   // ← 也絕不可少

        // ===== 你的邏輯寫在這裡：套利、置換抵押品、自我清算… =====

        // ③ 授權 Pool 把 本金 + 手續費 拉回去（Pool 用 transferFrom 收款）
        IERC20(asset).approve(address(POOL), amount + premium);
        return true;
    }
}

那兩行 require 是最常被漏掉、後果最嚴重的部分。少了它們，任何人都能直接呼叫你的 executeOperation，用假參數觸發合約內的邏輯與授權。這正是安全筆記裡「回呼必須驗證呼叫者」那一條的實例。

正當用途：抵押品置換

閃電貸最常見的合法用途不是套利，而是做一件本來需要先有錢才能做的事。例如：你在 Aave 用 ETH 抵押借了 USDC，現在想把抵押品換成 wstETH，但你沒有多餘資金先還款。

它如何改變威脅模型

閃電貸本身沒有漏洞，但它把兩類風險從「理論上可能」變成「每天都在發生」：

被放大的弱點為什麼
用現貨價當預言機攻擊者能在單筆交易內把池子價格推到任意位置。任何讀 slot0、getReserves() 的估值都不可信。
用即時餘額或總量計算金庫每股淨值、代幣總供給、池子深度——只要能在一筆交易內被改動，就能被操縱。
以代幣餘額計票的治理借入大量治理代幣 → 投票 → 還款。防禦是用快照（snapshot）而非即時餘額計票。
「資金門檻」型假設任何「要操縱需要 X 百萬美元，不划算」的推論都失效了——攻擊者不需要擁有那筆錢。

常見但不可靠的防禦：偵測「這筆交易是否來自閃電貸」。做不乾淨——攻擊者可以拆成多個合約、或用自有資金達到同樣效果。正確的防禦是讓被讀取的數值本身無法在單筆交易內被操縱（TWAP、外部預言機、快照），而不是試圖辨認攻擊者的資金來源。

開發者安全清單

  • 回呼要驗身份：msg.sender == POOL 與 initiator == address(this)，兩者都要。
  • 不要留下殘餘授權：回呼結束前把多餘的 approve 歸零，避免被後續交易利用。
  • 估算手續費：amount + premium 必須備齊；別忘了 0.05% 也是實際成本，套利利潤要能覆蓋它與 gas。
  • 不要用閃電貸資金充當自有資金證明：任何「持有 X 代幣即可…」的檢查都應改用時間加權或快照。
  • 重入：回呼期間你的合約處於中間狀態，若同時提供對外 view 介面，要考慮唯讀重入。

使用者風險

風險說明
你間接承擔了它的存在即使你從不使用閃電貸，你存錢的協議若用了可操縱的價格來源，仍可能被閃電貸攻擊而產生壞帳。
套利與清算是零和的閃電貸讓清算與套利競爭極度高效。對一般使用者而言，這意味著健康度一破線幾乎立刻被清算，沒有寬限時間。
高 APY 常伴隨可操縱設計新協議為了快速上線，常直接讀現貨價。收益越高，越該確認它的價格來源。
治理代幣的閃電貸攻擊若你持有的協議用即時餘額計票，攻擊者可短暫借票通過惡意提案。

Flash Loans

2026-09-19 · DEFI · ATOMICITY · AAVE · DEVELOPER GUIDE

No collateral, no size limit, negligible fee — on one condition: repay before the same transaction ends. Here is why that works, how to write one, and why it is simultaneously the most useful tool and the most dangerous attack vehicle in DeFi.

In three lines
  • A flash loan does not trust you to repay. If you cannot, the whole transaction reverts and the loan never happened. It is a direct consequence of blockchain atomicity, impossible in traditional finance.
  • So it abolishes capital as a barrier: anyone can command hundreds of millions for one instant. Arbitrageurs use it; so do attackers.
  • It is not itself a vulnerability. About 62% of price-manipulation attacks use one, but the actual bug is "the protocol read a price movable within a single transaction" — the flash loan just made the attack cheap.

Where to start: beginners → "Why no collateral is needed"; Solidity engineers → the implementation and the collateral-swap example; PMs and risk → market background and "How it changes the threat model".

Market background

The economic weight of flash loans is not in volume lent (it is borrowed and repaid instantly, so outstanding balance is always zero) but in who is now able to move size.

MetricFigure
Aave V3 flash loan fee (default)0.05% (FLASHLOAN_PREMIUM_TOTAL, governable)
Protocol's share of that~4 bps; the rest goes to depositors
Price-manipulation attacks using flash loans~62.1%
Aave's share of lending TVL~35.1% (category ~$51.96B)
Attacker's own capital requiredgas only

Figures are approximate, current as of 2026-09; the fee is set by governance — read the on-chain value before relying on it.

That last row is the point. Traditional risk management carries an implicit assumption: few people can move $100M, and those who can have identities, reputations and legal exposure. Flash loans void it — the attacker is anonymous, costless, and unpunished on failure. Every risk assessment resting on "an attacker would not have that much money" expired in 2020.

Why no collateral is needed

The key is atomicity: an Ethereum transaction either fully succeeds or fully reverts. The lender's logic is almost naive:

  1. Send you the money.
  2. Call your callback; do whatever you like.
  3. On return, check the balance: did enough come back?
  4. If not, revert — undoing step 1 along with everything else, as if it never happened.

So the lender need not trust you and needs no collateral. Its only exposure is gas, and you pay that.

Implementation: Aave V3

Two entry points: flashLoanSimple (one asset, cheaper) and flashLoan (several). With the simple form your contract implements one callback:

contract MyFlashLoan is IFlashLoanSimpleReceiver {
    IPool public immutable POOL;

    // ① Kick off: the Pool sends funds, then calls executeOperation below
    function start(address asset, uint256 amount) external {
        POOL.flashLoanSimple(
            address(this),   // receiver
            asset,
            amount,
            "",              // params: passed through to the callback verbatim
            0                // referralCode
        );
    }

    // ② The Pool calls back here; the asset is already in this contract's balance
    function executeOperation(
        address asset,
        uint256 amount,
        uint256 premium,     // the fee, ~0.05% of amount
        address initiator,
        bytes calldata params
    ) external override returns (bool) {
        require(msg.sender == address(POOL), "only pool");      // ← never omit
        require(initiator == address(this), "bad initiator");   // ← never omit

        // ===== your logic here: arbitrage, collateral swap, self-liquidation… =====

        // ③ Approve the Pool to pull principal + fee back (it uses transferFrom)
        IERC20(asset).approve(address(POOL), amount + premium);
        return true;
    }
}

Those two require lines are the most commonly omitted and most damaging part. Without them anyone can call your executeOperation directly with forged arguments and drive whatever logic and approvals live inside. This is exactly the "authenticate the callback" rule from the security note.

A legitimate use: swapping collateral

The most common honest use is not arbitrage but doing something that would otherwise require having the money first. Say you borrowed USDC against ETH on Aave and now want wstETH as collateral instead, with no spare funds to repay first.

How it changes the threat model

Flash loans contain no bug, but they moved two risk classes from "theoretically possible" to "happens weekly":

Weakness amplifiedWhy
Spot price as an oracleAn attacker can push a pool to any price within one transaction. Any valuation reading slot0 or getReserves() is untrustworthy.
Instantaneous balances or totalsVault value-per-share, token supply, pool depth — anything mutable within one transaction is manipulable.
Governance weighted by token balanceBorrow governance tokens → vote → repay. The defence is snapshots, not live balances.
"Capital barrier" assumptionsAny reasoning of the form "manipulating this costs $X million, so it is uneconomic" is void — the attacker need not own the money.

A common but unreliable defence is detecting "is this transaction using a flash loan". It cannot be done cleanly — attackers split across contracts, or simply use their own capital for the same effect. The correct defence is making the value you read unmanipulable within one transaction (TWAP, external oracle, snapshot), not trying to identify where the attacker's funds came from.

Developer checklist

  • Authenticate the callback: both msg.sender == POOL and initiator == address(this).
  • Leave no residual approval: zero out any excess approve before the callback ends, so later transactions cannot exploit it.
  • Budget the fee: amount + premium must be on hand; 0.05% is a real cost that arbitrage profit must clear, alongside gas.
  • Never treat flash-loaned funds as proof of holdings: any "holding X tokens entitles you to…" check should use time-weighting or a snapshot.
  • Reentrancy: during the callback your contract is mid-state; if you also expose view functions, consider read-only reentrancy.

User risk

RiskWhat it is
You are exposed even if you never use oneIf a protocol holding your deposits reads a manipulable price, it can be flash-loan attacked into bad debt that depositors absorb.
Liquidation is now instantFlash loans make liquidation and arbitrage brutally efficient. In practice, crossing the health threshold means near-immediate liquidation, with no grace period.
High APY often signals manipulable designNew protocols frequently read spot prices to ship faster. The higher the yield, the more you should check the price source.
