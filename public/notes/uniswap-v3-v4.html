Uniswap v2、v3 與 v4

2026-09-09 · DeFi / AMM · 開發者視角

本則從整合者的角度切入：不只講概念，而是「你要呼叫哪個合約的哪個函式、誰回呼誰、代幣在哪一步移動」。主線是三代協議如何演進：v2 用最小的 Pair 實作固定乘積，v3 用集中流動性提升資本效率，v4 再用 singleton、flash accounting 與 hooks 提升組合性。

v2：最小可行的 AMM

v2 的核心刻意保持極小：Factory 為每一組 ERC-20 token 建立一個 Pair，Pair 同時保存兩邊儲備、執行 swap，並鑄造可互換的 ERC-20 LP token；使用者通常透過 Router 處理路徑、滑點與加減流動性。Pair 地址可由 Factory、token0、token1 與 init code hash 透過 CREATE2 確定性算出。

元件責任
Factory建立並查詢 Pair；每組 token 只有一個官方 Pair。
Pair保存 reserves、驗證 invariant、執行 swap／mint／burn，並累積價格。
Router計算路徑與金額、檢查 deadline／slippage，再串接一個或多個 Pair。

若儲備是 x 與 y，交易後必須滿足固定乘積。輸入會先扣 0.30% swap fee，再計算輸出：

amountInWithFee = amountIn * 997;
amountOut = amountInWithFee * reserveOut
          / (reserveIn * 1000 + amountInWithFee);

例如池中有 100 ETH 與 200,000 USDC，送入 10 ETH 並不會按現價直接得到 20,000 USDC；扣費並沿曲線移動後約得到 18,132 USDC。成交均價低於交易前現價的差距是 price impact；而 slippage tolerance 是使用者願意接受、用來設定 amountOutMinimum 的額外界線。

Pair 的 swap(..., data) 還支援 flash swap：它先送出資產，若 data 非空便回呼 uniswapV2Call；callback 結束時只要還款並滿足含費用的 invariant，資產中途可被拿去套利、清算或換成另一種 token。v2 也在 Pair 中累積 price0CumulativeLast／price1CumulativeLast，讓整合者以兩個時間點的差值建立 TWAP，而不是把容易被單區塊操縱的即時 reserve ratio 當預言機。

v3：集中流動性的心智模型

v2 把流動性平均攤在 0 → ∞（x·y=k）；v3 讓 LP 選定區間 [Pa, Pb] 集中投入，區間內深度極高，價格離開區間則轉為單一資產且停止收費。價格在合約內以 sqrtPriceX96 儲存（Q64.96 定點數，即 √price × 2⁹⁶），tick 以 1.0001^tick 離散化。

區間內可把部位理解為帶有虛擬儲備的固定乘積曲線：相同真實資金支撐更大的有效深度，所以小額交易的滑點更低。價格跨過 tick 時，該 tick 的 liquidityNet 會加入或移出 active liquidity；到達上、下界後，部位逐步完全轉成其中一種資產。

v3 整合：兩種呼叫路徑

你有兩種方式跟 v3 互動。多數應用走周邊合約（periphery）的 SwapRouter，它把細節包好：

ISwapRouter.ExactInputSingleParams memory p = ISwapRouter.ExactInputSingleParams({
    tokenIn: WETH, tokenOut: USDC, fee: 500,        // 0.05% 費率層，決定用哪個池
    recipient: msg.sender, deadline: block.timestamp,
    amountIn: 1 ether, amountOutMinimum: minOut,     // minOut 是你的滑點保護
    sqrtPriceLimitX96: 0
});
uint256 out = router.exactInputSingle(p);

若要極致省 gas 或做 flash swap，則直接呼叫核心池的 swap()。這裡藏著 v3 最重要的模式：池會在交易中途回呼你，要你把欠它的代幣付清。

// 觸發：直接對核心池下單
pool.swap(recipient, zeroForOne, amountSpecified, sqrtPriceLimitX96, data);

// 池在計算完成後、回傳前，回呼這個函式向你討錢
function uniswapV3SwapCallback(
    int256 amount0Delta, int256 amount1Delta, bytes calldata data
) external {
    require(msg.sender == pool, "only pool");        // 只有池能呼叫
    // 正的 delta = 你欠池的那一邊，必須在這裡轉給它
    if (amount0Delta > 0) IERC20(token0).transfer(pool, uint256(amount0Delta));
    if (amount1Delta > 0) IERC20(token1).transfer(pool, uint256(amount1Delta));
}

流動性部位則透過 NonfungiblePositionManager 管理（mint / increaseLiquidity / decreaseLiquidity / collect）。因為每個部位的區間不同，故以 NFT 表示，而非 v2 的可互換 LP 代幣。

v4：Singleton 與 flash accounting

v4 的原生池沿用 v3 集中流動性數學，但把所有池收進單一 PoolManager 合約；若 hook 使用 custom accounting，也可以繞過原生曲線並實作不同定價。每個池不再是一份合約，而由 PoolKey(currency0, currency1, fee, tickSpacing, hooks) 識別。

任何低階操作前必須先 unlock()；PoolManager 隨即回呼你的 unlockCallback()，你在這個 callback 之內完成一切，過程主要記錄各 currency 的 deltas，直到最後才結算淨額。這套機制建立在 EIP-1153 暫時性儲存之上，並原生支援 ETH；ERC-6909 claims 還能把餘額留在 PoolManager 內供後續使用。

// 1) 進場：unlock 一次，把你要做的事編碼帶進去
manager.unlock(abi.encode(key, params));

// 2) PoolManager 回呼到這裡；所有動作都在 callback 內
function unlockCallback(bytes calldata raw) external returns (bytes memory) {
    require(msg.sender == address(manager), "only manager");
    (PoolKey memory key, SwapParams memory params) = abi.decode(raw, (PoolKey, SwapParams));

    BalanceDelta delta = manager.swap(key, params, "");   // 只動 delta，尚未搬幣

    // 負 delta = 欠款；正 delta = 應得。兩種 currency 都要分別處理。
    _resolve(key.currency0, delta.amount0());
    _resolve(key.currency1, delta.amount1());
    // _resolve: 負值走 sync/transfer/settle，正值走 take（或 ERC-6909 claim）
    // 回傳前，每一種 currency 的 delta 都必須個別歸零，不能跨幣抵銷。
    return "";
}

v4 Hooks：把邏輯插進池的生命週期

hook 是你在建池時綁定的合約。此後 PoolManager 可在 initialize、增減流動性、swap 與 donate 的前後回呼它：共有 10 個生命週期 callback，再加上 4 個 return-delta 權限，合計 14 個 address permission flags。動態費率、鏈上限價單、白名單、MEV 內化甚至自訂曲線，都可寫在這裡，無須分叉核心。

contract MyHook is BaseHook {
    // 宣告要哪些 callback；必須與合約「地址的位元」一致
    function getHookPermissions() public pure override
        returns (Hooks.Permissions memory)
    {
        return Hooks.Permissions({ beforeSwap: true, afterSwap: true /* 其餘 false */ });
    }

    // BaseHook 外層有 onlyPoolManager 守衛：只有 PoolManager 進得來
    function _beforeSwap(address, PoolKey calldata, SwapParams calldata, bytes calldata)
        internal override returns (bytes4, BeforeSwapDelta, uint24)
    {
        // 你的邏輯：改費率、擋交易、記錄預言機…
        return (BaseHook.beforeSwap.selector, BeforeSwapDeltaLibrary.ZERO_DELTA, 0);
    }
}

最反直覺的一點：權限編碼在 hook 合約地址的最低 14 bits。例如 BEFORE_SWAP_FLAG = 1 << 7、AFTER_SWAP_FLAG = 1 << 6。PoolManager 執行時直接讀地址旗標決定是否 callback；常用的 v4-periphery BaseHook 則在 constructor 內以 validateHookPermissions 檢查地址是否符合 getHookPermissions()。因此部署前通常要挖礦 CREATE2 salt，直到地址位元符合預期。

前端：用 viem 呼叫（full-stack 視角）

合約之外，前端完整流程通常是：用 QuoterV2 或路由服務取得報價與路徑，依 token 的實際 decimals 建立金額，再設定 amountOutMinimum；approval 可透過 Permit2 管理，最後由 UniversalRouter 組合 v2／v3／v4、多跳與 wrap／unwrap。以下只示範較容易理解的 v3 單池「先模擬、再送出」：

import { parseEther } from "viem";

// 1) 先模擬——失敗會在這裡丟錯，不會白花 gas
const { request, result } = await publicClient.simulateContract({
  address: SWAP_ROUTER, abi: swapRouterAbi, functionName: "exactInputSingle",
  args: [{ tokenIn, tokenOut, fee: 500, recipient, deadline,
           amountIn: parseEther("1"), amountOutMinimum, sqrtPriceLimitX96: 0n }],
  account,
});

// 2) 模擬過了才真的送交易
const hash = await walletClient.writeContract(request);

v4 因為要走 unlock → callback，前端通常不直接對 PoolManager 下單，而是呼叫官方的 UniversalRouter / V4Router，由它在鏈上完成 unlock 與結算。UniswapX 則是另一層 intent／filler 執行系統，不是新的 AMM 版本。

設計理念與取捨

每一代都是一次刻意的取捨；看懂取捨，才看得懂 API 為何長這樣。

版本換到什麼付出的代價
v2極簡、被動、部位可互換（ERC-20）流動性分散於全價格範圍，同資金下滑點通常較高
v3資本效率（集中流動性）需主動管理；部位變 NFT、不可互換；無常損失放大
v4省 gas（singleton + flash accounting）＋ 可程式化（hooks）整合更複雜；池的安全取決於它掛的 hook

hooks 的威力用「動態費率」最能說明——平時收 0.05%，波動大時自動調高：

// 需在 getHookPermissions 開 beforeSwap，且池以 DYNAMIC_FEE_FLAG 建立
function _beforeSwap(address, PoolKey calldata, SwapParams calldata, bytes calldata)
    internal override returns (bytes4, BeforeSwapDelta, uint24)
{
    uint24 fee = _isVolatile() ? 10_000 : 500;              // 1% / 0.05%
    uint24 withFlag = fee | LPFeeLibrary.OVERRIDE_FEE_FLAG;  // 告訴池「這筆用這個費率」
    return (BaseHook.beforeSwap.selector, BeforeSwapDeltaLibrary.ZERO_DELTA, withFlag);
}

智慧合約安全風險（開發者）

回呼一定要驗證呼叫者。v3 的 callback 與 v4 的 unlockCallback 都是 external 函式，忘了綁定合法來源，任何人都能直接呼叫、把你合約的代幣搬走：

// ✗ 危險：沒驗證來源，任何人都能觸發、掏空本合約
function uniswapV3SwapCallback(int256 a0, int256 a1, bytes calldata) external {
    IERC20(token0).transfer(msg.sender, uint256(a0));
}
// ✓ 正確：只認事先算好的那個 pool
require(msg.sender == expectedPool, "unauthorized callback");
  • 不要拿現貨池價格當預言機。slot0 的即時價可被閃電貸在單一區塊內拉動；要用 TWAP 或外部預言機（Chainlink）。
  • 滑點與時效。amountOutMinimum、deadline 一定要設；設 0 等於任人宰割。
  • fee-on-transfer / rebasing 代幣會打破「收到＝預期」的假設，實務上多半直接不支援。
  • v4 特有：hook 可重入，也可使用 return delta 改變金額；settle／take 記帳寫錯會讓整筆 revert 或資金卡住。只整合可信、經審計的 hook。

使用者投資風險

當 LP（提供流動性）不是無風險收租，尤其在 v3：

風險說明
無常損失兩資產價格背離時，LP 的價值低於單純持有；v3 因集中而放大。
區間外歸零收益價格離開 [Pa, Pb] 後停止賺費並成為單一資產；突破上界時 token0 轉為 token1，跌破下界時則相反。
JIT 流動性專業者在大單前一刻注入、成交後立刻撤走，吃走本該屬於被動 LP 的手續費。
MEV／三明治你的 swap 會被搶跑夾擊；務必設滑點，或走私有 mempool。
v4 hook 風險惡意或有 bug 的 hook 可擋單、額外抽費、甚至鎖死池子。進池前務必確認 hook 是誰、是否審計。

一句話：v2／v3 當 LP 的主要敵人是無常損失與MEV；v4 多了一個——你信不信任這個池的 hook。

一句話區分

v2 用每對一個 Pair 與固定乘積建立最小 AMM；v3 用集中流動性提升資本效率，並以 pool callback 收款；v4 把原生集中流動性池收進單一 PoolManager，以 flash accounting 淨額結算，再用 hooks 開放自訂行為與定價。

Uniswap v2, v3 & v4

2026-09-09 · DeFi / AMM · Developer view

This note takes the integrator's angle: not just concepts, but which contract and function you call, who calls back whom, and where tokens move at each step. The thread is how the protocol evolved: v2 implements constant product with minimal Pair contracts, v3 concentrates liquidity for capital efficiency, and v4 adds a singleton, flash accounting, and hooks for composability.

v2: the minimum viable AMM

v2 deliberately keeps its core small. The Factory creates one Pair for each ERC-20 token pair. A Pair stores both reserves, executes swaps, and mints fungible ERC-20 LP tokens; users normally go through a Router for paths, slippage checks, and liquidity operations. A Pair address can be computed deterministically from the Factory, token0, token1, and init code hash via CREATE2.

ComponentResponsibility
FactoryCreates and indexes Pairs; each token pair has one canonical Pair.
PairStores reserves, enforces the invariant, executes swap/mint/burn, and accumulates prices.
RouterComputes paths and amounts, checks deadline/slippage, then connects one or more Pairs.

For reserves x and y, the post-trade balances must satisfy constant product. Input is first charged the 0.30% swap fee:

amountInWithFee = amountIn * 997;
amountOut = amountInWithFee * reserveOut
          / (reserveIn * 1000 + amountInWithFee);

For example, sending 10 ETH into a pool with 100 ETH and 200,000 USDC does not return 20,000 USDC at the displayed spot price. After the fee and curve movement it returns about 18,132 USDC. The difference in execution caused by your own trade is price impact; slippage tolerance is the extra boundary you accept when setting amountOutMinimum.

A Pair's swap(..., data) also enables flash swaps: it sends assets first and, when data is non-empty, calls uniswapV2Call. Before the callback returns, the caller must repay and satisfy the fee-adjusted invariant. v2 Pairs also accumulate price0CumulativeLast and price1CumulativeLast, allowing integrators to construct a TWAP from two observations instead of treating the manipulable current reserve ratio as an oracle.

v3: a mental model for concentrated liquidity

v2 spreads liquidity evenly across 0 → ∞ (x·y=k); v3 lets an LP pick a range [Pa, Pb] and concentrate capital in it — very deep inside the range, single-asset and fee-less once price leaves it. Price is stored on-chain as sqrtPriceX96 (Q64.96 fixed point, i.e. √price × 2⁹⁶); ticks discretise it as 1.0001^tick.

Within its range, a position behaves like a constant-product curve with larger virtual reserves: the same real capital supports greater effective depth and lower slippage for small trades. When price crosses a tick, that tick's liquidityNet enters or leaves active liquidity. At either boundary the position progressively becomes entirely one asset.

Integrating v3: two call paths

You interact with v3 two ways. Most apps use the periphery SwapRouter, which wraps the details:

ISwapRouter.ExactInputSingleParams memory p = ISwapRouter.ExactInputSingleParams({
    tokenIn: WETH, tokenOut: USDC, fee: 500,        // 0.05% tier picks the pool
    recipient: msg.sender, deadline: block.timestamp,
    amountIn: 1 ether, amountOutMinimum: minOut,     // minOut is your slippage guard
    sqrtPriceLimitX96: 0
});
uint256 out = router.exactInputSingle(p);

For maximum gas savings or flash swaps you call the core pool's swap() directly. Here is v3's most important pattern: the pool calls you back mid-swap to collect what you owe.

// Trigger: order straight against the core pool
pool.swap(recipient, zeroForOne, amountSpecified, sqrtPriceLimitX96, data);

// After computing, before returning, the pool calls back to collect
function uniswapV3SwapCallback(
    int256 amount0Delta, int256 amount1Delta, bytes calldata data
) external {
    require(msg.sender == pool, "only pool");        // only the pool may call
    // A positive delta is the side you owe; pay it here
    if (amount0Delta > 0) IERC20(token0).transfer(pool, uint256(amount0Delta));
    if (amount1Delta > 0) IERC20(token1).transfer(pool, uint256(amount1Delta));
}

Liquidity positions are managed through NonfungiblePositionManager (mint / increaseLiquidity / decreaseLiquidity / collect). Because each range differs, positions are NFTs, not v2's fungible LP tokens.

v4: singleton and flash accounting

v4's native pools retain v3 concentrated-liquidity maths but gather every pool into one PoolManager. A hook using custom accounting can instead bypass the native curve and implement different pricing. A pool is no longer a contract; it is identified by PoolKey(currency0, currency1, fee, tickSpacing, hooks).

Low-level operations begin with unlock(); PoolManager calls your unlockCallback(), inside which actions primarily update per-currency deltas and settle only the net at the end. This rests on EIP-1153 transient storage. v4 also supports native ETH, while ERC-6909 claims can retain balances inside PoolManager for later use.

// 1) Enter: unlock once, carrying your encoded intent
manager.unlock(abi.encode(key, params));

// 2) PoolManager calls back here; everything happens in the callback
function unlockCallback(bytes calldata raw) external returns (bytes memory) {
    require(msg.sender == address(manager), "only manager");
    (PoolKey memory key, SwapParams memory params) = abi.decode(raw, (PoolKey, SwapParams));

    BalanceDelta delta = manager.swap(key, params, "");   // touches deltas only, no transfer yet

    // Negative means you owe; positive means you are owed. Resolve both currencies.
    _resolve(key.currency0, delta.amount0());
    _resolve(key.currency1, delta.amount1());
    // _resolve: negative uses sync/transfer/settle; positive uses take (or a claim)
    // Every currency delta must individually reach zero; currencies cannot offset each other.
    return "";
}

v4 Hooks: inject logic into the pool's lifecycle

A hook is a contract bound at pool creation. PoolManager can call it around initialize, liquidity changes, swaps, and donations: there are 10 lifecycle callbacks plus 4 return-delta permissions, for 14 address permission flags in total. Dynamic fees, range orders, allowlists, MEV internalisation, and even custom curves can live here without forking the core.

contract MyHook is BaseHook {
    // Declare which callbacks you want; must match the ADDRESS bits
    function getHookPermissions() public pure override
        returns (Hooks.Permissions memory)
    {
        return Hooks.Permissions({ beforeSwap: true, afterSwap: true /* rest false */ });
    }

    // BaseHook wraps this with onlyPoolManager: only PoolManager gets in
    function _beforeSwap(address, PoolKey calldata, SwapParams calldata, bytes calldata)
        internal override returns (bytes4, BeforeSwapDelta, uint24)
    {
        // your logic: adjust fee, block a trade, record an oracle...
        return (BaseHook.beforeSwap.selector, BeforeSwapDeltaLibrary.ZERO_DELTA, 0);
    }
}

The most counter-intuitive part is that permissions are encoded in the lowest 14 bits of the hook address. For example, BEFORE_SWAP_FLAG = 1 << 7 and AFTER_SWAP_FLAG = 1 << 6. PoolManager reads those flags at runtime to decide whether to call a hook. The commonly used v4-periphery BaseHook validates the address against getHookPermissions() in its constructor. Deployment therefore usually requires mining a CREATE2 salt whose resulting address has the intended bits.

Front end: calling with viem (full-stack view)

A complete front-end flow normally uses QuoterV2 or a routing service for a quote and route, parses amounts with the token's actual decimals, and derives amountOutMinimum. Permit2 can manage approvals, while UniversalRouter composes v2/v3/v4 swaps, multi-hop routes, and wrapping. This smaller example shows the easier-to-read v3 single-pool "simulate, then send" flow:

import { parseEther } from "viem";

// 1) Simulate — a failure throws here, before you spend gas
const { request, result } = await publicClient.simulateContract({
  address: SWAP_ROUTER, abi: swapRouterAbi, functionName: "exactInputSingle",
  args: [{ tokenIn, tokenOut, fee: 500, recipient, deadline,
           amountIn: parseEther("1"), amountOutMinimum, sqrtPriceLimitX96: 0n }],
  account,
});

// 2) Only send once the simulation passed
const hash = await walletClient.writeContract(request);

Because v4 goes through unlock → callback, front ends rarely hit PoolManager directly; they call the official UniversalRouter / V4Router, which performs the unlock and settlement on-chain. UniswapX is a separate intent-and-filler execution system, not another AMM version.

Design ideas and trade-offs

Each version is a deliberate trade-off; grasp the trade-off and the API shape makes sense.

VersionGainsCost
v2Simple, passive, fungible positions (ERC-20)Liquidity spans the full price range, usually producing more slippage for the same capital
v3Capital efficiency (concentrated liquidity)Active management; positions become non-fungible NFTs; amplified impermanent loss
v4Gas (singleton + flash accounting) and programmability (hooks)More complex to integrate; a pool's safety depends on its hook

The power of hooks is clearest with a dynamic fee — 0.05% normally, higher when volatile:

// requires beforeSwap in getHookPermissions and a pool built with DYNAMIC_FEE_FLAG
function _beforeSwap(address, PoolKey calldata, SwapParams calldata, bytes calldata)
    internal override returns (bytes4, BeforeSwapDelta, uint24)
{
    uint24 fee = _isVolatile() ? 10_000 : 500;              // 1% / 0.05%
    uint24 withFlag = fee | LPFeeLibrary.OVERRIDE_FEE_FLAG;  // tell the pool "use this fee now"
    return (BaseHook.beforeSwap.selector, BeforeSwapDeltaLibrary.ZERO_DELTA, withFlag);
}

Smart-contract security (for developers)

Always authenticate the callback. Both v3's callback and v4's unlockCallback are external functions; forget to bind the legitimate caller and anyone can invoke them and drain your contract:

// x Dangerous: no source check — anyone can trigger this and drain the contract
function uniswapV3SwapCallback(int256 a0, int256 a1, bytes calldata) external {
    IERC20(token0).transfer(msg.sender, uint256(a0));
}
// OK Correct: accept only the pool you computed in advance
require(msg.sender == expectedPool, "unauthorized callback");
  • Never use spot pool price as an oracle. slot0 can be pushed within a single block by a flash loan; use a TWAP or an external oracle (Chainlink).
  • Slippage and deadline. Always set amountOutMinimum and deadline; zero leaves you at anyone's mercy.
  • Fee-on-transfer / rebasing tokens break the "received == expected" assumption; most integrations simply refuse them.
  • v4-specific: a hook can re-enter and can change amounts through return deltas; a settle/take bookkeeping mistake reverts the whole call or strands funds. Integrate only trusted, audited hooks.

User investment risk

Being an LP is not risk-free rent, especially in v3:

RiskWhat it is
Impermanent lossWhen the two assets diverge in price, the LP is worth less than simply holding; v3 amplifies it through concentration.
Zero earnings out of rangeOnce price leaves [Pa, Pb], fees stop and the position becomes one asset: above the upper bound token0 has converted to token1; below the lower bound, the reverse.
JIT liquidityPros add liquidity just before a large swap and pull it right after, taking fees that would have gone to passive LPs.

v4 hook riskA malicious or buggy hook can block trades, skim extra fees, or brick the pool. Check who the hook is and whether it's audited before entering.

In short: an LP's main enemies in v2/v3 are impermanent loss and MEV; v4 adds one more — whether you trust the pool's hook.

One-line distinction

v2 builds a minimal AMM from one constant-product Pair per token pair; v3 adds concentrated liquidity and collects payment through a pool callback; v4 gathers native concentrated-liquidity pools into one PoolManager, settles net changes through flash accounting, and opens behavior and pricing to hooks.
