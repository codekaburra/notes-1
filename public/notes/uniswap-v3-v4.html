Uniswap v3 與 v4

2026-09-09 · DeFi / AMM · 開發者視角

本則從整合者的角度切入：不只講概念，而是「你要呼叫哪個合約的哪個函式、誰回呼誰、代幣在哪一步移動」。v3 與 v4 的定價數學相同（集中流動性），差別在合約如何互相呼叫——這正是三張流程圖要說清楚的事。

先建立心智模型：集中流動性

v2 把流動性平均攤在 0 → ∞（x·y=k）；v3 讓 LP 選定區間 [Pa, Pb] 集中投入，區間內深度極高，價格離開區間則轉為單一資產且停止收費。價格在合約內以 sqrtPriceX96 儲存（Q64.96 定點數，即 √price × 2⁹⁶），tick 以 1.0001^tick 離散化。

v3 整合：兩種呼叫路徑

你有兩種方式跟 v3 互動。多數應用走周邊合約（periphery）的 SwapRouter，它把細節包好：

ISwapRouter.ExactInputSingleParams memory p = ISwapRouter.ExactInputSingleParams({
    tokenIn: WETH, tokenOut: USDC, fee: 500,        // 0.05% 費率層，決定用哪個池
    recipient: msg.sender, deadline: block.timestamp,
    amountIn: 1 ether, amountOutMinimum: minOut,     // minOut 是你的滑點保護
    sqrtPriceLimitX96: 0
});
uint256 out = router.exactInputSingle(p);

若要極致省 gas 或做 flash swap，則直接呼叫核心池的 swap()。這裡藏著 v3 最重要的模式：池會在交易中途回呼你，要你把欠它的代幣付清。

// 觸發：直接對核心池下單
pool.swap(recipient, zeroForOne, amountSpecified, sqrtPriceLimitX96, data);

// 池在計算完成後、回傳前，回呼這個函式向你討錢
function uniswapV3SwapCallback(
    int256 amount0Delta, int256 amount1Delta, bytes calldata data
) external {
    require(msg.sender == pool, "only pool");        // 只有池能呼叫
    // 正的 delta = 你欠池的那一邊，必須在這裡轉給它
    if (amount0Delta > 0) IERC20(token0).transfer(pool, uint256(amount0Delta));
    if (amount1Delta > 0) IERC20(token1).transfer(pool, uint256(amount1Delta));
}

流動性部位則透過 NonfungiblePositionManager 管理（mint / increaseLiquidity / decreaseLiquidity / collect）。因為每個部位的區間不同，故以 NFT 表示，而非 v2 的可互換 LP 代幣。

v4：Singleton 與 flash accounting

v4 的定價沿用 v3，但把所有池收進單一 PoolManager 合約。任何操作前必須先 unlock()；PoolManager 隨即回呼你的 unlockCallback()，你在這個 callback 之內完成一切，過程只改記帳（deltas），不搬代幣，直到最後才結算淨額。這套機制建立在 EIP-1153 暫時性儲存之上。

// 1) 進場：unlock 一次，把你要做的事編碼帶進去
manager.unlock(abi.encode(key, params));

// 2) PoolManager 回呼到這裡；所有動作都在 callback 內
function unlockCallback(bytes calldata raw) external returns (bytes memory) {
    require(msg.sender == address(manager), "only manager");
    (PoolKey memory key, SwapParams memory params) = abi.decode(raw, (PoolKey, SwapParams));

    BalanceDelta delta = manager.swap(key, params, "");   // 只動 delta，尚未搬幣

    // 負 delta = 欠款（付進去）；正 delta = 應得（提出來）
    if (delta.amount0() < 0) _settle(key.currency0);       // 轉入 tokenIn 後呼叫 settle()
    if (delta.amount1() > 0) _take(key.currency1);          // take() 提出 tokenOut
    // 回傳前，PoolManager 強制檢查此 caller 的所有 delta == 0，否則整筆 revert
}

v4 Hooks：把邏輯插進池的生命週期

hook 是你在建池時綁定的合約。此後 PoolManager 會在每個動作的前後回呼它——beforeSwap / afterSwap / beforeAddLiquidity 等共 14 個切入點。動態費率、鏈上限價單、白名單、MEV 內化，都寫在這裡，無須分叉 Uniswap。

contract MyHook is BaseHook {
    // 宣告要哪些 callback；必須與合約「地址的位元」一致
    function getHookPermissions() public pure override
        returns (Hooks.Permissions memory)
    {
        return Hooks.Permissions({ beforeSwap: true, afterSwap: true /* 其餘 false */ });
    }

    // BaseHook 外層有 onlyPoolManager 守衛：只有 PoolManager 進得來
    function _beforeSwap(address, PoolKey calldata, SwapParams calldata, bytes calldata)
        internal override returns (bytes4, BeforeSwapDelta, uint24)
    {
        // 你的邏輯：改費率、擋交易、記錄預言機…
        return (BaseHook.beforeSwap.selector, ZERO_DELTA, 0);
    }
}

最反直覺的一點：「要哪些 callback」不是寫在 storage，而是編碼在 hook 合約的地址裡。地址的低位元決定哪些切入點生效（BEFORE_SWAP_FLAG = 1 << 7、AFTER_SWAP_FLAG = 1 << 6…）。部署時 PoolManager 會核對地址位元是否等於 getHookPermissions()，不符即 revert。因此你得挖礦 CREATE2 的 salt，直到算出的地址位元剛好符合宣告的權限。

前端：用 viem 呼叫（full-stack 視角）

合約之外，前端典型做法是「先模擬、再送出」，用模擬預先抓 revert、也拿到回傳值：

import { parseEther } from "viem";

// 1) 先模擬——失敗會在這裡丟錯，不會白花 gas
const { request, result } = await publicClient.simulateContract({
  address: SWAP_ROUTER, abi: swapRouterAbi, functionName: "exactInputSingle",
  args: [{ tokenIn, tokenOut, fee: 500, recipient, deadline,
           amountIn: parseEther("1"), amountOutMinimum, sqrtPriceLimitX96: 0n }],
  account,
});

// 2) 模擬過了才真的送交易
const hash = await walletClient.writeContract(request);

v4 因為要走 unlock → callback，前端通常不直接對 PoolManager 下單，而是呼叫官方的 UniversalRouter / V4Router，由它在鏈上完成 unlock 與結算。

一句話區分

v3 解決資本效率——集中流動性，並用「池回呼 caller」的模式收款。v4 沿用 v3 定價，改成單一 PoolManager + 「unlock 一次、只結算淨額」的 flash accounting，並開放 hooks 讓任何人把邏輯插進池的生命週期。

Uniswap v3 & v4

2026-09-09 · DeFi / AMM · Developer view

This note takes the integrator's angle: not just concepts, but which contract and function you call, who calls back whom, and where tokens move at each step. v3 and v4 share the same pricing maths (concentrated liquidity); what differs is how the contracts call each other — which is exactly what the three flow diagrams make concrete.

Mental model first: concentrated liquidity

v2 spreads liquidity evenly across 0 → ∞ (x·y=k); v3 lets an LP pick a range [Pa, Pb] and concentrate capital in it — very deep inside the range, single-asset and fee-less once price leaves it. Price is stored on-chain as sqrtPriceX96 (Q64.96 fixed point, i.e. √price × 2⁹⁶); ticks discretise it as 1.0001^tick.

Integrating v3: two call paths

You interact with v3 two ways. Most apps use the periphery SwapRouter, which wraps the details:

ISwapRouter.ExactInputSingleParams memory p = ISwapRouter.ExactInputSingleParams({
    tokenIn: WETH, tokenOut: USDC, fee: 500,        // 0.05% tier picks the pool
    recipient: msg.sender, deadline: block.timestamp,
    amountIn: 1 ether, amountOutMinimum: minOut,     // minOut is your slippage guard
    sqrtPriceLimitX96: 0
});
uint256 out = router.exactInputSingle(p);

For maximum gas savings or flash swaps you call the core pool's swap() directly. Here is v3's most important pattern: the pool calls you back mid-swap to collect what you owe.

// Trigger: order straight against the core pool
pool.swap(recipient, zeroForOne, amountSpecified, sqrtPriceLimitX96, data);

// After computing, before returning, the pool calls back to collect
function uniswapV3SwapCallback(
    int256 amount0Delta, int256 amount1Delta, bytes calldata data
) external {
    require(msg.sender == pool, "only pool");        // only the pool may call
    // A positive delta is the side you owe; pay it here
    if (amount0Delta > 0) IERC20(token0).transfer(pool, uint256(amount0Delta));
    if (amount1Delta > 0) IERC20(token1).transfer(pool, uint256(amount1Delta));
}

Liquidity positions are managed through NonfungiblePositionManager (mint / increaseLiquidity / decreaseLiquidity / collect). Because each range differs, positions are NFTs, not v2's fungible LP tokens.

v4: singleton and flash accounting

v4 keeps v3's pricing but gathers every pool into one PoolManager. Any operation must first unlock(); PoolManager then calls back your unlockCallback(), inside which you do everything — and the process only moves deltas, not tokens, settling the net at the very end. It rests on EIP-1153 transient storage.

// 1) Enter: unlock once, carrying your encoded intent
manager.unlock(abi.encode(key, params));

// 2) PoolManager calls back here; everything happens in the callback
function unlockCallback(bytes calldata raw) external returns (bytes memory) {
    require(msg.sender == address(manager), "only manager");
    (PoolKey memory key, SwapParams memory params) = abi.decode(raw, (PoolKey, SwapParams));

    BalanceDelta delta = manager.swap(key, params, "");   // touches deltas only, no transfer yet

    // negative delta = you owe (pay in); positive = you're owed (take out)
    if (delta.amount0() < 0) _settle(key.currency0);       // transfer tokenIn, then settle()
    if (delta.amount1() > 0) _take(key.currency1);          // take() the tokenOut
    // before returning, PoolManager requires all deltas for this caller == 0, else revert
}

v4 Hooks: inject logic into the pool's lifecycle

A hook is a contract you bind at pool creation. Thereafter PoolManager calls it before and after each action — beforeSwap / afterSwap / beforeAddLiquidity and 14 entry points in total. Dynamic fees, on-chain limit orders, allowlists, MEV internalisation all live here, without forking Uniswap.

contract MyHook is BaseHook {
    // Declare which callbacks you want; must match the ADDRESS bits
    function getHookPermissions() public pure override
        returns (Hooks.Permissions memory)
    {
        return Hooks.Permissions({ beforeSwap: true, afterSwap: true /* rest false */ });
    }

    // BaseHook wraps this with onlyPoolManager: only PoolManager gets in
    function _beforeSwap(address, PoolKey calldata, SwapParams calldata, bytes calldata)
        internal override returns (bytes4, BeforeSwapDelta, uint24)
    {
        // your logic: adjust fee, block a trade, record an oracle...
        return (BaseHook.beforeSwap.selector, ZERO_DELTA, 0);
    }
}

The most counter-intuitive part: which callbacks fire is not stored in state — it is encoded in the hook contract's address. The low bits of the address decide which entry points are active (BEFORE_SWAP_FLAG = 1 << 7, AFTER_SWAP_FLAG = 1 << 6…). At deployment PoolManager checks the address bits equal getHookPermissions(), reverting on mismatch. So you must mine the CREATE2 salt until the resulting address bits match your declared permissions.

Front end: calling with viem (full-stack view)

Beyond the contracts, the front end typically "simulates, then sends" — the simulation catches reverts up front and returns the result:

import { parseEther } from "viem";

// 1) Simulate — a failure throws here, before you spend gas
const { request, result } = await publicClient.simulateContract({
  address: SWAP_ROUTER, abi: swapRouterAbi, functionName: "exactInputSingle",
  args: [{ tokenIn, tokenOut, fee: 500, recipient, deadline,
           amountIn: parseEther("1"), amountOutMinimum, sqrtPriceLimitX96: 0n }],
  account,
});

// 2) Only send once the simulation passed
const hash = await walletClient.writeContract(request);

Because v4 goes through unlock → callback, front ends rarely hit PoolManager directly; they call the official UniversalRouter / V4Router, which performs the unlock and settlement on-chain.

One-line distinction

v3 solves capital efficiency — concentrated liquidity, collecting payment via the "pool calls the caller back" pattern. v4 keeps v3's pricing but moves to a single PoolManager plus "unlock once, settle only the net" flash accounting, and opens hooks so anyone can inject logic into the pool's lifecycle.
