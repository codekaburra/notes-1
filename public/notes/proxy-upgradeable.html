Proxy 與可升級合約

合約部署後不可變，但產品需要修 bug、加功能。代理模式是整個產業的解法——代價是引入了一組全新的、而且安靜失敗的錯誤類型。這則講三種主流模式、儲存佈局怎麼對齊，以及升級本身為何已成為頂級攻擊面。

三句話版本
  • 原理只有一句：proxy 持有儲存與地址，implementation 只提供程式碼，兩者靠 delegatecall 接起來。升級＝換掉那個程式碼地址。
  • 最大的風險不是寫錯邏輯，而是儲存佈局錯位——它不會 revert，只會安靜地把某個欄位讀成另一個欄位的值。
  • 而且「可升級」本身就是一種中心化：誰握有升級權，誰就能重寫規則。升級風險應依實際管理權與驗證流程評估。

誰讀哪裡：初學者 → 「delegatecall 到底做了什麼」與三種模式對照；Solidity 工程師 → 儲存佈局、ERC-7201、初始化與升級清單；PM／風控 → 市場背景與使用者風險。

市場背景

可升級在生產環境幾乎是預設值——主流 DeFi 協議大多跑在代理之後。這帶來一個常被低估的事實：你評估一個協議的安全性時，實際上是在評估「誰能升級它」。

指標狀態
OpenZeppelin v5 的儲存方案改用 ERC-7201 命名空間儲存，取代 __gap
OZ v5 的介面變動upgradeTo 已移除，只剩 upgradeToAndCall
OZ v5 的 Transparent proxyadmin 改為 immutable，升級權改由 ProxyAdmin 的 ownership 控制
學術關注度代理碰撞偵測已是獨立研究主題（Proxion、USCSA 等）

狀態查詢日期：2026-10-08，之後未再更新。函式庫介面變動頻繁，實作前請對照你實際安裝的版本。

如果你讀的教學還在教 __gap 與 upgradeTo，它寫在 OZ v5 之前。v4 與 v5 的儲存模型不相容——從 v4 的順序儲存升級到 v5 的命名空間儲存若沒處理好，已有回報造成無法復原的鎖死。跨大版本升級前務必先驗證佈局。

delegatecall 到底做了什麼

一般的 call 是「去對方家、用對方的東西」；delegatecall 是「把對方的程式碼搬來、用自己的東西執行」。所以：

  • 執行的是 implementation 的程式碼。
  • 讀寫的是 proxy 的儲存。
  • msg.sender 與 msg.value 維持原本的呼叫者與金額。
  • address(this) 是 proxy，不是 implementation。
// proxy 的核心就這一段——所有未匹配的呼叫都轉給 implementation
fallback() external payable {
    address impl = _implementation();          // 從 EIP-1967 固定槽位讀出
    assembly {
        calldatacopy(0, 0, calldatasize())     // 原封不動複製 calldata
        // 用「本合約的 storage」執行 impl 的 code
        let ok := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch ok
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

三種主流模式

EIP-1967：為什麼需要固定槽位

proxy 自己也要存東西（implementation 位址、admin），但它的儲存跟 implementation 共用同一個空間。如果 proxy 把 implementation 位址放在 slot 0，而 implementation 的第一個變數剛好也在 slot 0——兩者會互相覆蓋。

EIP-1967 的解法是把這些值放到幾乎不可能被一般變數佔用的位置：取一個字串的 keccak256 再減 1。

// 三個標準槽位（直接背起來也無妨，debug 時很常用）
implementation : 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
admin          : 0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103
beacon         : 0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50

// 推導方式：bytes32(uint256(keccak256('eip1967.proxy.implementation')) - 1)
// 減 1 是為了讓這個值不等於任何已知 preimage 的雜湊，進一步降低碰撞可能

實務用途：想知道任何一個代理合約現在指向哪個 implementation，讀取上方的 EIP-1967 implementation 槽（不是 slot 0）；Beacon 代理另讀 beacon 的 implementation——區塊瀏覽器的「Read as Proxy」就是這樣做的。

儲存佈局：最大的坑

升級只換程式碼，不動資料。所以新版對儲存佈局的理解必須與舊版完全相容，否則欄位含義會整排位移——而且不會 revert。

// ERC-7201 的實際寫法（OZ v5 內部全面採用）
/// @custom:storage-location erc7201:myapp.main
struct MainStorage {
    address owner;
    uint256 total;
}

// 槽位 = keccak256(abi.encode(uint256(keccak256("myapp.main")) - 1)) & ~bytes32(uint256(0xff))
// 實際數值請用工具算（forge script 或 OZ 的 helper），不要手寫
bytes32 private constant MAIN_STORAGE = 0x…由上式計算…;

function _main() private pure returns (MainStorage storage $) {
    assembly { $.slot := MAIN_STORAGE }
}

function setTotal(uint256 v) external {
    _main().total = v;        // namespace 內仍須保留相容的欄位順序
}

初始化：constructor 不能用

constructor 在部署時執行，而且寫進的是 implementation 自己的儲存——proxy 根本看不到。所以可升級合約改用 initialize()，但這就產生了新問題：它是一個誰都能呼叫的普通函式。

contract MyApp is UUPSUpgradeable, OwnableUpgradeable {
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();          // ★ 鎖死 implementation 自身，必寫
    }

    function initialize(address owner_) public initializer {
        __Ownable_init(owner_);          // initializer 修飾器保證只跑一次
        __UUPSUpgradeable_init();
    }

    // 首次升級若需要 migration，可使用初始化版本 2
    function initializeV2(uint256 migratedTotal_) public onlyOwner reinitializer(2) {
        _main().total = migratedTotal_; // illustrative migration of existing state
    }

    // UUPS 的升級守衛——這是唯一的權限檢查，漏了等於任何人都能升級
    function _authorizeUpgrade(address newImpl) internal override onlyOwner {}
}

標準 OpenZeppelin UUPS 會在升級時檢查新版 proxiableUUID，不相容的 implementation 通常會 revert。這不是完整安全驗證：惡意但相容的新版仍可能移除未來升級能力。需同時驗證授權、儲存佈局與新版行為，並用 upgradeToAndCall 原子執行已授權的 migration。reinitializer 只限制版本執行次數，不提供存取控制。

版本號到底代表什麼？

initializeV2 只是函式名稱；真正限制執行的是 reinitializer(2)。OpenZeppelin 在 proxy 的 storage 記錄已初始化的最高版本。一般首次 initializer 成功後是 1；reinitializer(2) 成功後是 2。同版本再呼叫會 revert。升級 implementation 不會重設這個紀錄，也不會自動呼叫初始化函式。

操作用途注意
initializer首次建立 proxy 的 owner、角色與基本狀態升級時不能重跑來「更新 owner」
reinitializer(n)新增模組或一次性資料 migrationn 必須大於已用版本；仍需權限控制
onlyInitializing讓內部初始化 helper 只能在初始化期間執行不是獨立的一次性或管理員檢查
_disableInitializers()在 implementation constructor 鎖住其自身的初始化不會鎖住 proxy；兩者 storage 分開

版本可以跳號，但不會自動補跑：從 1 直接執行 reinitializer(3) 後，版本 2 就不能再執行。如果 V3 依賴 V2 的設定，必須安排依序 migration，或寫一個包含所有必要步驟的 migration。不要把兩個外部 reinitializer 互相巢狀呼叫；可抽出 onlyInitializing 的內部 helper。implementation 的產品版本與初始化版本可以不同；純邏輯修正未必需要 migration。

實際操作：升級 + 初始化放在同一筆交易

假設 V1 已初始化 owner，V2 在相容的 storage 尾端新增 feeBps。下面是接在既有 V1 上的示意，沿用原本 owner 與升級權限，不重新呼叫 __Ownable_init：

// V2 fragment: append only after validating the V1 layout
uint256 public feeBps;

function initializeV2(uint256 feeBps_)
    external onlyOwner reinitializer(2)
{
    require(feeBps_ <= 1_000, "fee too high");
    feeBps = feeBps_;
}

先部署並驗證 V2 implementation，再由已授權帳戶透過 proxy 地址 提交升級。以下是 OpenZeppelin 5.x UUPS 的呼叫示意，需配合實際 ABI、相依版本與 signer：

bytes memory data = abi.encodeCall(MyAppV2.initializeV2, (100));
// executed by the authorized owner; 100 bps = 1%
MyAppV1(proxyAddress).upgradeToAndCall(v2Implementation, data);

交易內順序是：V1 驗證升級權限 → 更新 implementation 指向 V2 → delegatecall 執行 V2 的 initializeV2(100) → 寫入 proxy 的 fee 與初始化版本。若 migration revert，整筆交易回滾，implementation 指向也回到 V1。若只換 implementation、之後另送初始化交易，中間可能暴露未設定好的 V2，或讓未受保護的 migration 被搶先呼叫。

Transparent 的 caller 有差別：OpenZeppelin 5.x 通常由 ProxyAdmin 的 owner 呼叫 ProxyAdmin.upgradeAndCall；migration 裡的 msg.sender 是 ProxyAdmin，不是其 owner。因此上面的 onlyOwner 例子適用於 owner 直接呼叫的 UUPS，不能原樣搬到 Transparent。應依實際升級路徑設計 migration 授權，並用 fork 模擬真實 multisig／timelock／ProxyAdmin caller。

升級後要驗收什麼？

  • 確認 implementation 地址、Upgraded 與 Initialized(2) 事件，以及新參數的讀值；事件需在 proxy 執行的交易中檢查。
  • 確認 owner、角色、餘額、債務等 V1 狀態維持預期；重複初始化及未授權呼叫都必須失敗。
  • 模擬 migration 失敗，確認整筆升級回滾；確認未來 V3 的升級權限仍能正常運作。
  • 不要假設換回 V1 就會回復資料：migration 已改動的 storage 和已使用的初始化版本不會隨程式碼回退。大型 migration 若無法一筆完成，需設計暫停、分批游標與完成前的功能限制。

新 proxy 若直接部署 V2，也需要完整的首次初始化路徑；不能只呼叫依賴既有 owner 的 initializeV2。此外 Upgrades 工具預設不將 reinitializer 當成首次 initializer 驗證；需要此驗證時可使用 @custom:oz-upgrades-validate-as-initializer，但應用在確實包含完整首次初始化的函式，而非盲目標註所有 migration。參考 Initializable API 與 初始化驗證說明。

新手如何避免升級踩坑：把經驗變成發布門檻

不要只靠記住注意事項。把常見錯誤交給固定模板、相容性驗證、測試與部署腳本攔截；人工 review 則確認需求與經濟邏輯。工具通過不代表沒有漏洞，但能降低每次操作都依賴記憶的風險。

容易踩的坑預防方法驗收證據
proxy 部署後才初始化，被搶先設定 owner部署時直接帶 initializer calldata；implementation constructor 鎖住自身初始化部署交易完成即有正確 owner；implementation 直接初始化失敗
reinitializer 有版本限制卻沒有權限依 UUPS／Transparent 的實際 caller 設計 migration 授權未授權 migration 失敗；正式管理路徑成功；同版本不能重跑
改 storage 排列，舊資料遭錯讀固定相依套件版本與 lockfile；對正確的舊版執行 layout 驗證，不任意略過警告CI 驗證通過；有資料的 V1 升級後仍符合預期
呼叫 implementation 而非 proxy，或使用錯鏈地址部署 manifest 分別記錄 chain ID、proxy、implementation、ProxyAdmin／治理地址；腳本核對鏈與目前 implementation提交前核對地址與 bytecode；交易後從 proxy 讀回設定
升級成功，新增參數卻未設定需要 migration 時用原子 upgrade + call；明訂新增欄位的合法值新參數正確；刻意令 migration revert 時，implementation 與狀態一起回滾
EOA 測試通過，正式治理操作失敗fork 模擬實際 multisig／timelock／ProxyAdmin 呼叫鏈與準備提交的 calldata正式 caller 的權限、等待條件與 migration 都能完成

最小可用的開發流程

  1. 寫驗收規則：例如 owner 不變、使用者餘額與債務不變、新 fee 為 100 bps、提款仍可用。若資料需要轉換，寫清楚轉換前後應成立的關係。
  2. 建立有資料的 V1 fixture：包含不同角色、使用者、餘額和邊界值。只測空合約升級，容易漏掉 storage 與業務問題。
  3. CI 設定阻擋條件：相容性驗證、資料保留、權限負面測試、重複初始化、migration 失敗回滾，都必須通過。
  4. fork 演練：以正式權限路徑模擬確切交易；記錄區塊、implementation bytecode 與 calldata。模擬後若版本、參數或鏈上狀態有重要改動，重新評估並模擬。
  5. 提交後驗收：核對 receipt、implementation、owner、角色、新參數與關鍵操作；不能只看交易狀態成功。
V1 有資料的測試狀態
  → V2 相容性驗證
  → upgrade + migration 測試
  → 未授權／重複呼叫／失敗回滾測試
  → 正式治理路徑 fork 模擬
  → 提交交易與讀回驗收

工具無法替你決定的事：withdrawLimit = 0 是禁止提款還是無上限？新增 fee 對既有使用者是否生效？這些需先定義需求，再寫成測試。回退 implementation 也不等於復原資料，必須事前設計復原或後續修正 migration。

此處是建議的發布流程，不表示本筆記已提供可執行的 CI 或完成鏈上模擬。可依 OpenZeppelin 開發指南建立自己的模板；前文已說明 reinitializer 的驗證限制。

選擇器衝突：Transparent 的由來

如果 proxy 自己有 upgradeTo(address)，而 implementation 剛好也有同名或相同四位元組選擇器的函式，那麼這個呼叫會被 proxy 攔截，永遠到不了 implementation。這就是 function selector clash。

Transparent 模式的解法是依呼叫者分流：admin 呼叫走 proxy 的管理邏輯，其他人一律直接轉給 implementation。代價是每次呼叫都要讀一次 admin 做判斷（OZ v5 把 admin 改成 immutable 就是為了省掉這次讀取）。

UUPS 的解法更乾淨：proxy 身上根本沒有管理函式，升級邏輯放在 implementation 裡，自然不可能衝突。這也是 UUPS 成為主流的原因之一。

升級前的檢查清單

  1. 用工具比對儲存佈局。OpenZeppelin Upgrades（Hardhat／Foundry 皆有）會自動擋下不相容的變更。不要靠肉眼看 diff。
  2. 確認新版仍保有升級能力（UUPS 必須繼續繼承 UUPSUpgradeable）。
  3. implementation 的 constructor 要有 _disableInitializers()。
  4. 新增的初始化邏輯用 reinitializer(n)，不要重用 initializer。
  5. 在 fork 上演練升級：用主網狀態跑一次 upgradeToAndCall，再驗證關鍵欄位的值沒有跑掉。
  6. 升級權交多簽 + 時間鎖，讓使用者有時間觀察與退出。
  7. 注意 OZ v4 → v5：順序儲存與命名空間儲存不相容，跨版本升級要特別驗證。

智慧合約安全風險（開發者）

  • 儲存錯位不會 revert：它安靜地回傳錯誤的值。這是代理模式最危險的特性——測試若只檢查「有沒有成功」會完全漏掉。
  • 不可變數不存在儲存裡：immutable 與 constant 被編進 bytecode，升級換掉 implementation 就等於換掉它們的值，而且 proxy 的儲存毫無記錄。
  • 絕不 delegatecall 到不可信位址：等同於把自己的儲存交出去任意改寫。
  • 繼承順序會改變佈局：在順序佈局下，調整父合約的繼承次序就足以讓所有欄位位移。
  • Beacon 的影響範圍是全部實例：一次錯誤的 beacon 升級會同時打壞所有 proxy。
  • 驗證與開源：proxy 與 implementation 都要在區塊瀏覽器驗證，否則使用者無從得知自己在跟什麼程式碼互動。

使用者風險

風險說明
規則可被重寫你審過的程式碼隨時可能被換掉。「這個協議安全嗎」實質上是「誰能升級它」。
單一金鑰的升級權若升級權在一個 EOA 手上，該私鑰外洩即等同整個協議被接管。進場前確認是否多簽。
沒有時間鎖 = 沒有退出窗口有時間鎖時，惡意升級至少會先公開排隊，你有機會撤資；沒有的話，變更在一個區塊內生效。
審計的範圍「已審計」通常指某個版本的 implementation。升級後的新版未必在審計範圍內。
怎麼自己查在區塊瀏覽器讀 proxy 的 0x3608… 槽位可看出目前的 implementation；讀 admin 槽位可看出誰有權升級。

延伸閱讀：Solidity 安全漏洞圖鑑的 delegatecall 與存取控制兩節。

升級實作：V1 → V2 的驗收

本篇 assembly 與 namespace snippet 是原理示意，帶 placeholder 的 slot 不能直接部署。使用固定版 OpenZeppelin 與 upgrades 工具：部署 implementation → proxy constructor 帶 initializer calldata → 建 V1 state → validate V2 layout → 經授權 upgradeToAndCall → 讀回所有 state。不要為 migration 隨意 reinterpret 舊欄位；新增 fee 時應在相容的 namespace struct 尾端新增欄位並 validate。

測 implementation 無法 initialize、proxy 無法二次 initialize、非 owner 無法 upgrade/reinitialize、所有 balance/role 保留、migration revert 時整個 upgrade rollback。Runtime UUPS compatibility 不會替你判斷 storage compatibility 或 business logic。OpenZeppelin storage validation說明 namespace 內也必須保留相容佈局。

PM：誰能在什麼時間改規則？

列 implementation、ProxyAdmin/beacon、owner、多簽 signer、timelock、emergency bypass 的關係。比較 upgrade notice 與真實 exit latency；通知 24 小時、退出需 7 天，就不構成完整退出窗口。Audit coverage 應綁 implementation bytecode、compiler、library 與 configuration，不只列 auditor logo。

Proxies and Upgradeable Contracts

Deployed contracts are immutable, but products need bug fixes and new features. Proxies are the industry's answer — at the cost of a whole new category of errors that fail silently. Here are the three mainstream patterns, how to keep storage aligned, and why the upgrade mechanism is now a first-class attack surface.

In three lines
  • One sentence covers the mechanism: the proxy owns the storage and the address, the implementation only supplies code, joined by delegatecall. Upgrading swaps that code address.
  • The biggest risk is not buggy logic but storage layout drift — it does not revert, it quietly reads one field as another field's value.
  • And "upgradeable" is itself a form of centralisation: whoever holds the upgrade key can rewrite the rules. Assess upgrade risk through the actual authority and validation process.

Where to start: beginners → "What delegatecall actually does" and the pattern comparison; Solidity engineers → storage layout, ERC-7201, initialisers and the upgrade checklist; PMs and risk → market background and user risk.

Market background

Upgradeability is effectively the default in production — most major DeFi protocols run behind a proxy. That makes an under-appreciated point: when you assess a protocol's safety, you are really assessing who can upgrade it.

If the tutorial you are reading still teaches __gap and upgradeTo, it predates OZ v5. The v4 and v5 storage models are incompatible — upgrading from v4's sequential storage to v5's namespaced storage has been reported to cause unrecoverable deadlock when mishandled. Validate the layout before any major-version upgrade.

What delegatecall actually does

A normal call means "go to their house and use their things"; delegatecall means "bring their code here and run it on my things". So:

  • The code executed belongs to the implementation.
  • The storage read and written belongs to the proxy.
  • msg.sender and msg.value stay as the original caller and amount.
  • address(this) is the proxy, not the implementation.
// The core of a proxy is this one block — every unmatched call is forwarded
fallback() external payable {
    address impl = _implementation();          // read from the fixed EIP-1967 slot
    assembly {
        calldatacopy(0, 0, calldatasize())     // copy calldata verbatim
        // run impl's code against THIS contract's storage
        let ok := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch ok
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

Three mainstream patterns

EIP-1967: why fixed slots

The proxy needs to store things too (the implementation address, the admin), but its storage is shared with the implementation's. If the proxy put the implementation address in slot 0 and the implementation's first variable also landed in slot 0, they would overwrite each other.

EIP-1967 solves this by placing those values somewhere an ordinary variable will essentially never reach: the keccak256 of a string, minus one.

// The three standard slots (worth memorising; you will read them while debugging)
implementation : 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
admin          : 0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103
beacon         : 0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50

// Derivation: bytes32(uint256(keccak256('eip1967.proxy.implementation')) - 1)
// The minus one makes the value the hash of no known preimage, lowering collision risk further

Practical use: to find which implementation any proxy currently points at, read the EIP-1967 implementation slot above, not slot 0; for a Beacon proxy, resolve the beacon implementation — that is exactly what a block explorer's "Read as Proxy" does.

Storage layout: the big trap

An upgrade replaces code, not data. So the new version's understanding of the layout must be fully compatible with the old one, or every field shifts meaning — without reverting.

// ERC-7201 in practice (used throughout OZ v5 internally)
/// @custom:storage-location erc7201:myapp.main
struct MainStorage {
    address owner;
    uint256 total;
}

// slot = keccak256(abi.encode(uint256(keccak256("myapp.main")) - 1)) & ~bytes32(uint256(0xff))
// compute the real value with a tool (a forge script, or OZ's helper) — never by hand
bytes32 private constant MAIN_STORAGE = 0x…computed from the formula above…;

function _main() private pure returns (MainStorage storage $) {
    assembly { $.slot := MAIN_STORAGE }
}

function setTotal(uint256 v) external {
    _main().total = v;        // preserve compatible field layout inside this namespace
}

Initialisation: constructors do not work

A constructor runs at deployment and writes to the implementation's own storage — which the proxy never sees. So upgradeable contracts use initialize() instead, which creates a new problem: it is an ordinary function anyone can call.

contract MyApp is UUPSUpgradeable, OwnableUpgradeable {
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();          // ★ locks the implementation itself; mandatory
    }

    function initialize(address owner_) public initializer {
        __Ownable_init(owner_);          // the initializer modifier enforces once-only
        __UUPSUpgradeable_init();
    }

    // Adding fields in a later upgrade: use reinitializer with a version number
    function initializeV2(uint256 migratedTotal_) public onlyOwner reinitializer(2) {
        _main().total = migratedTotal_; // illustrative migration of existing state
    }

    // UUPS's upgrade guard — the only permission check; omit it and anyone can upgrade
    function _authorizeUpgrade(address newImpl) internal override onlyOwner {}
}

Standard OpenZeppelin UUPS checks the new implementation’s proxiableUUID; incompatible implementations normally revert. This is not full safety validation: compatible malicious code can still remove future upgrade ability. Validate authority, storage layout, and behavior, then run the authorized migration atomically with upgradeToAndCall. A reinitializer limits version execution, not caller authority.

What does the initialization version mean?

initializeV2 is just a function name. reinitializer(2) enforces the version. The proxy stores the highest initialized version: normally 1 after its first initializer, then 2 after a successful V2 migration. Repeating that version reverts. Changing implementation neither resets this record nor automatically runs initialization.

OperationPurposeConstraint
initializerFirst proxy setupDo not rerun it to update ownership
reinitializer(n)New module or one-time migrationHigher version required; access control still required
onlyInitializingInternal initialization helpersNeither an admin check nor a once-only guard
_disableInitializers()Lock implementation initialization in its constructorDoes not lock the proxy's separate storage

Skipping from 1 to 3 does not execute version 2, and prevents running version 2 afterward. Sequence dependent migrations or include every required step in one migration. Do not nest external reinitializers; extract internal helpers with onlyInitializing. Product code versions and initialization versions are separate: a logic-only fix may need no migration.

Operational flow: upgrade and initialize in one transaction

Suppose V1 already set its owner. V2 appends feeBps in a validated compatible layout. This fragment preserves existing ownership and does not rerun __Ownable_init:

// V2 fragment: append only after validating the V1 layout
uint256 public feeBps;
function initializeV2(uint256 feeBps_)
    external onlyOwner reinitializer(2)
{
    require(feeBps_ <= 1_000, "fee too high");
    feeBps = feeBps_;
}

Deploy and validate V2, then have the authorized signer submit through the proxy address. This OpenZeppelin 5.x UUPS call sketch requires the actual ABI and pinned dependencies:

bytes memory data = abi.encodeCall(MyAppV2.initializeV2, (100));
// authorized owner; 100 bps = 1%
MyAppV1(proxyAddress).upgradeToAndCall(v2Implementation, data);

The transaction authorizes through V1, changes the implementation, then delegatecalls the V2 migration into proxy storage. A migration revert rolls back the implementation change too. Separate upgrade and initialization transactions leave an intermediate configuration gap and can expose unprotected migration functions to competing callers.

Transparent differs: with OpenZeppelin 5.x, the ProxyAdmin owner normally calls ProxyAdmin.upgradeAndCall. The migration sees ProxyAdmin as msg.sender, not its owner. The owner-only UUPS example therefore cannot be copied unchanged. Design migration authorization for the actual route and simulate the real multisig, timelock, and ProxyAdmin callers.

Acceptance and recovery

  • Verify the implementation address, proxy transaction events Upgraded and Initialized(2), and new parameters.
  • Verify existing ownership, roles, balances and liabilities; duplicate and unauthorized initialization must fail.
  • Simulate migration failure and atomic rollback; verify future V3 upgrade authorization still works.
  • Switching code back to V1 does not undo migrated storage or initialization versions. Large migrations need explicit pause policy, batch progress, and feature restrictions until complete.

A fresh proxy deployed directly with V2 needs a complete first-time setup path; an owner-only migration cannot initialize its missing owner. Upgrades tooling does not validate reinitializers as initializers by default. Use @custom:oz-upgrades-validate-as-initializer when appropriate for a complete first-time initializer, rather than marking every migration. See Initializable and initializer validation.

Prevent beginner mistakes with release gates

Turn recurring mistakes into template, validation, test, and deployment checks. Reviewers still need to assess requirements and economics. Passing tools reduces routine mistakes; it does not prove the absence of vulnerabilities.

A minimal development workflow

  1. Define acceptance rules: owner preserved, balances and debt preserved, fee set to 100 bps, withdrawals working. For intentional transformations, specify the relationship between old and new data.
  2. Populate a V1 fixture: include roles, users, balances and boundary cases. Empty-contract upgrades miss storage and business failures.
  3. Gate CI: require compatibility, state preservation, unauthorized-call, repeat-initialization and atomic-rollback tests.
  4. Rehearse on a fork: use the real authority route and exact transaction. Record block, bytecode and calldata; reassess and simulate again after material code, parameter or on-chain changes.
  5. Verify after submission: inspect receipt, implementation, owner, roles, parameters and key operations. Transaction success alone is insufficient.
Populated V1 fixture
  → V2 compatibility validation
  → upgrade + migration tests
  → unauthorized / duplicate / rollback tests
  → governance-route fork simulation
  → submission and post-upgrade reads

Tools cannot decide whether a zero withdrawal limit means disabled withdrawals or unlimited withdrawals, or whether new fees should affect existing positions. Specify these requirements and test them. Code rollback does not restore migrated data; plan recovery or a corrective migration in advance.

This is a recommended workflow, not an executable CI package or a completed on-chain simulation. Build a reusable template using the OpenZeppelin guide; the reinitializer validation limitation is explained above.

Selector clash: where Transparent came from

If the proxy itself exposes upgradeTo(address) and the implementation happens to have a function with the same name or the same four-byte selector, the call is intercepted by the proxy and never reaches the implementation. That is a function selector clash.

The transparent pattern resolves it by routing on the caller: admin calls hit the proxy's admin logic, everyone else is forwarded straight through. The cost is reading the admin on every call — which is exactly why OZ v5 made the admin immutable.

UUPS resolves it more cleanly: the proxy has no admin functions at all. Upgrade logic lives in the implementation, so a clash is impossible by construction — one reason UUPS became the default.

Pre-upgrade checklist

  1. Diff the storage layout with a tool. OpenZeppelin Upgrades (Hardhat and Foundry) blocks incompatible changes automatically. Do not eyeball the diff.
  2. Confirm the new version is still upgradeable (UUPS must keep inheriting UUPSUpgradeable).
  3. The implementation's constructor must call _disableInitializers().
  4. New initialisation goes in reinitializer(n), never a reused initializer.
  5. Rehearse on a fork: run upgradeToAndCall against mainnet state, then assert that key fields still read correctly.
  6. Put upgrade rights behind a multisig and a timelock, so users have time to observe and exit.
  7. Mind OZ v4 → v5: sequential and namespaced storage are incompatible; validate carefully across that boundary.

Smart-contract security (developers)

  • Layout drift does not revert: it silently returns wrong values. This is the pattern's most dangerous property — tests that only check "did it succeed" miss it entirely.
  • Immutables do not live in storage: immutable and constant are baked into bytecode, so swapping the implementation swaps their values with no trace in the proxy's storage.
  • Never delegatecall an untrusted address: it hands over your storage to be rewritten at will.
  • Inheritance order changes layout: under sequential storage, reordering parents alone is enough to shift every field.
  • A beacon's blast radius is every instance: one bad beacon upgrade breaks all proxies at once.
  • Verify and publish both proxy and implementation on the explorer, or users cannot tell what code they are interacting with.

Upgrade acceptance: V1 → V2

The assembly and namespace snippets explain mechanics; placeholder slots are not deployable. Pin OpenZeppelin and upgrade tooling: deploy implementation → initialize atomically through proxy construction → establish V1 state → validate V2 layout → authorize upgradeToAndCall → verify state. Do not repurpose existing fields during migration; append new fee state compatibly and validate it.

Test locked implementation initialization, repeated proxy initialization, unauthorized upgrade/reinitialization, preserved balances/roles, and atomic rollback when migration reverts. Runtime UUPS compatibility does not validate storage or business logic. OpenZeppelin’s storage validation covers compatibility within namespaces.

PM: who can change rules, and when?

Map implementation, ProxyAdmin/beacon, owner, multisig signers, timelock, and emergency bypass. Compare upgrade notice against actual exit latency: 24-hour notice with a seven-day exit is not a full exit window. Bind audit coverage to implementation bytecode, compiler, library, and configuration, rather than an auditor logo.
