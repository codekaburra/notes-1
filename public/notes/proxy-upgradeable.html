Proxy 與可升級合約

2026-10-08 · SOLIDITY · 代理模式 · 儲存佈局 · 開發者指南

合約部署後不可變，但產品需要修 bug、加功能。代理模式是整個產業的解法——代價是引入了一組全新的、而且安靜失敗的錯誤類型。這則講三種主流模式、儲存佈局怎麼對齊，以及升級本身為何已成為頂級攻擊面。

三句話版本
  • 原理只有一句：proxy 持有儲存與地址，implementation 只提供程式碼，兩者靠 delegatecall 接起來。升級＝換掉那個程式碼地址。
  • 最大的風險不是寫錯邏輯，而是儲存佈局錯位——它不會 revert，只會安靜地把某個欄位讀成另一個欄位的值。
  • 而且「可升級」本身就是一種中心化：誰握有升級權，誰就能重寫規則。2026 年單筆約 $280M 的 Drift 事件，根因就在升級機制。

誰讀哪裡：初學者 → 「delegatecall 到底做了什麼」與三種模式對照；Solidity 工程師 → 儲存佈局、ERC-7201、初始化與升級清單；PM／風控 → 市場背景與使用者風險。

市場背景

可升級在生產環境幾乎是預設值——主流 DeFi 協議大多跑在代理之後。這帶來一個常被低估的事實：你評估一個協議的安全性時，實際上是在評估「誰能升級它」。

指標狀態
2026 年最大事件之一：Drift約 $280M，根因為升級機制漏洞
OpenZeppelin v5 的儲存方案改用 ERC-7201 命名空間儲存，取代 __gap
OZ v5 的介面變動upgradeTo 已移除，只剩 upgradeToAndCall
OZ v5 的 Transparent proxyadmin 改為 immutable，升級權改由 ProxyAdmin 的 ownership 控制
學術關注度代理碰撞偵測已是獨立研究主題（Proxion、USCSA 等）

狀態以 2026-10 查得為準；函式庫介面變動頻繁，實作前請對照你實際安裝的版本。

如果你讀的教學還在教 __gap 與 upgradeTo，它寫在 OZ v5 之前。v4 與 v5 的儲存模型不相容——從 v4 的順序儲存升級到 v5 的命名空間儲存若沒處理好，已有回報造成無法復原的鎖死。跨大版本升級前務必先驗證佈局。

delegatecall 到底做了什麼

一般的 call 是「去對方家、用對方的東西」；delegatecall 是「把對方的程式碼搬來、用自己的東西執行」。所以：

  • 執行的是 implementation 的程式碼。
  • 讀寫的是 proxy 的儲存。
  • msg.sender 與 msg.value 維持原本的呼叫者與金額。
  • address(this) 是 proxy，不是 implementation。
// proxy 的核心就這一段——所有未匹配的呼叫都轉給 implementation
fallback() external payable {
    address impl = _implementation();          // 從 EIP-1967 固定槽位讀出
    assembly {
        calldatacopy(0, 0, calldatasize())     // 原封不動複製 calldata
        // 用「本合約的 storage」執行 impl 的 code
        let ok := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch ok
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

三種主流模式

EIP-1967：為什麼需要固定槽位

proxy 自己也要存東西（implementation 位址、admin），但它的儲存跟 implementation 共用同一個空間。如果 proxy 把 implementation 位址放在 slot 0，而 implementation 的第一個變數剛好也在 slot 0——兩者會互相覆蓋。

EIP-1967 的解法是把這些值放到幾乎不可能被一般變數佔用的位置：取一個字串的 keccak256 再減 1。

// 三個標準槽位（直接背起來也無妨，debug 時很常用）
implementation : 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
admin          : 0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103
beacon         : 0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50

// 推導方式：bytes32(uint256(keccak256('eip1967.proxy.implementation')) - 1)
// 減 1 是為了讓這個值不等於任何已知 preimage 的雜湊，進一步降低碰撞可能

實務用途：想知道任何一個代理合約現在指向哪個 implementation，直接讀它的第一個槽位即可——區塊瀏覽器的「Read as Proxy」就是這樣做的。

儲存佈局：最大的坑

升級只換程式碼，不動資料。所以新版對儲存佈局的理解必須與舊版完全相容，否則欄位含義會整排位移——而且不會 revert。

// ERC-7201 的實際寫法（OZ v5 內部全面採用）
/// @custom:storage-location erc7201:myapp.main
struct MainStorage {
    address owner;
    uint256 total;
}

// 槽位 = keccak256(abi.encode(uint256(keccak256("myapp.main")) - 1)) & ~bytes32(uint256(0xff))
// 實際數值請用工具算（forge script 或 OZ 的 helper），不要手寫
bytes32 private constant MAIN_STORAGE = 0x…由上式計算…;

function _main() private pure returns (MainStorage storage $) {
    assembly { $.slot := MAIN_STORAGE }
}

function setTotal(uint256 v) external {
    _main().total = v;        // 透過 $ 存取，不再有順序問題
}

初始化：constructor 不能用

constructor 在部署時執行，而且寫進的是 implementation 自己的儲存——proxy 根本看不到。所以可升級合約改用 initialize()，但這就產生了新問題：它是一個誰都能呼叫的普通函式。

contract MyApp is UUPSUpgradeable, OwnableUpgradeable {
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();          // ★ 鎖死 implementation 自身，必寫
    }

    function initialize(address owner_) public initializer {
        __Ownable_init(owner_);          // initializer 修飾器保證只跑一次
        __UUPSUpgradeable_init();
    }

    // 第二次升級要加欄位時，用 reinitializer 指定版本號
    function initializeV2(uint256 fee_) public reinitializer(2) {
        _main().fee = fee_;
    }

    // UUPS 的升級守衛——這是唯一的權限檢查，漏了等於任何人都能升級
    function _authorizeUpgrade(address newImpl) internal override onlyOwner {}
}

UUPS 特有的致命失誤：新版的 implementation 忘記繼承 UUPSUpgradeable。升級成功之後，升級函式本身消失了——這個 proxy 從此永久無法再升級，資金也可能跟著鎖死。OZ 的升級外掛會檢查這一點，手動部署則完全沒有保護。

選擇器衝突：Transparent 的由來

如果 proxy 自己有 upgradeTo(address)，而 implementation 剛好也有同名或相同四位元組選擇器的函式，那麼這個呼叫會被 proxy 攔截，永遠到不了 implementation。這就是 function selector clash。

Transparent 模式的解法是依呼叫者分流：admin 呼叫走 proxy 的管理邏輯，其他人一律直接轉給 implementation。代價是每次呼叫都要讀一次 admin 做判斷（OZ v5 把 admin 改成 immutable 就是為了省掉這次讀取）。

UUPS 的解法更乾淨：proxy 身上根本沒有管理函式，升級邏輯放在 implementation 裡，自然不可能衝突。這也是 UUPS 成為主流的原因之一。

升級前的檢查清單

  1. 用工具比對儲存佈局。OpenZeppelin Upgrades（Hardhat／Foundry 皆有）會自動擋下不相容的變更。不要靠肉眼看 diff。
  2. 確認新版仍保有升級能力（UUPS 必須繼續繼承 UUPSUpgradeable）。
  3. implementation 的 constructor 要有 _disableInitializers()。
  4. 新增的初始化邏輯用 reinitializer(n)，不要重用 initializer。
  5. 在 fork 上演練升級：用主網狀態跑一次 upgradeToAndCall，再驗證關鍵欄位的值沒有跑掉。
  6. 升級權交多簽 + 時間鎖，讓使用者有時間觀察與退出。
  7. 注意 OZ v4 → v5：順序儲存與命名空間儲存不相容，跨版本升級要特別驗證。

智慧合約安全風險（開發者）

  • 儲存錯位不會 revert：它安靜地回傳錯誤的值。這是代理模式最危險的特性——測試若只檢查「有沒有成功」會完全漏掉。
  • 不可變數不存在儲存裡：immutable 與 constant 被編進 bytecode，升級換掉 implementation 就等於換掉它們的值，而且 proxy 的儲存毫無記錄。
  • 絕不 delegatecall 到不可信位址：等同於把自己的儲存交出去任意改寫。
  • 繼承順序會改變佈局：在順序佈局下，調整父合約的繼承次序就足以讓所有欄位位移。
  • Beacon 的影響範圍是全部實例：一次錯誤的 beacon 升級會同時打壞所有 proxy。
  • 驗證與開源：proxy 與 implementation 都要在區塊瀏覽器驗證，否則使用者無從得知自己在跟什麼程式碼互動。

使用者風險

風險說明
規則可被重寫你審過的程式碼隨時可能被換掉。「這個協議安全嗎」實質上是「誰能升級它」。
單一金鑰的升級權若升級權在一個 EOA 手上，該私鑰外洩即等同整個協議被接管。進場前確認是否多簽。
沒有時間鎖 = 沒有退出窗口有時間鎖時，惡意升級至少會先公開排隊，你有機會撤資；沒有的話，變更在一個區塊內生效。
審計的範圍「已審計」通常指某個版本的 implementation。升級後的新版未必在審計範圍內。
升級本身就是事故來源2026 年約 $280M 的 Drift 事件根因即在升級機制——這不是罕見的邊緣案例。

Proxies and Upgradeable Contracts

2026-10-08 · SOLIDITY · PROXY PATTERNS · STORAGE LAYOUT · DEVELOPER GUIDE

Deployed contracts are immutable, but products need bug fixes and new features. Proxies are the industry's answer — at the cost of a whole new category of errors that fail silently. Here are the three mainstream patterns, how to keep storage aligned, and why the upgrade mechanism is now a first-class attack surface.

In three lines
  • One sentence covers the mechanism: the proxy owns the storage and the address, the implementation only supplies code, joined by delegatecall. Upgrading swaps that code address.
  • The biggest risk is not buggy logic but storage layout drift — it does not revert, it quietly reads one field as another field's value.
  • And "upgradeable" is itself a form of centralisation: whoever holds the upgrade key can rewrite the rules. The ~$280M Drift incident in 2026 traced back to the upgrade mechanism.

Where to start: beginners → "What delegatecall actually does" and the pattern comparison; Solidity engineers → storage layout, ERC-7201, initialisers and the upgrade checklist; PMs and risk → market background and user risk.

Market background

Upgradeability is effectively the default in production — most major DeFi protocols run behind a proxy. That makes an under-appreciated point: when you assess a protocol's safety, you are really assessing who can upgrade it.

MetricStatus
One of 2026's largest incidents: Drift~$280M, root cause in the upgrade mechanism
OpenZeppelin v5 storage approachMoved to ERC-7201 namespaced storage, replacing __gap
OZ v5 interface changeupgradeTo removed; only upgradeToAndCall remains

If the tutorial you are reading still teaches __gap and upgradeTo, it predates OZ v5. The v4 and v5 storage models are incompatible — upgrading from v4's sequential storage to v5's namespaced storage has been reported to cause unrecoverable deadlock when mishandled. Validate the layout before any major-version upgrade.

What delegatecall actually does

A normal call means "go to their house and use their things"; delegatecall means "bring their code here and run it on my things". So:

  • The code executed belongs to the implementation.
  • The storage read and written belongs to the proxy.
  • msg.sender and msg.value stay as the original caller and amount.
  • address(this) is the proxy, not the implementation.
// The core of a proxy is this one block — every unmatched call is forwarded
fallback() external payable {
    address impl = _implementation();          // read from the fixed EIP-1967 slot
    assembly {
        calldatacopy(0, 0, calldatasize())     // copy calldata verbatim
        // run impl's code against THIS contract's storage
        let ok := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch ok
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

Three mainstream patterns

EIP-1967: why fixed slots

The proxy needs to store things too (the implementation address, the admin), but its storage is shared with the implementation's. If the proxy put the implementation address in slot 0 and the implementation's first variable also landed in slot 0, they would overwrite each other.

EIP-1967 solves this by placing those values somewhere an ordinary variable will essentially never reach: the keccak256 of a string, minus one.

// The three standard slots (worth memorising; you will read them while debugging)
implementation : 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
admin          : 0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103
beacon         : 0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50

// Derivation: bytes32(uint256(keccak256('eip1967.proxy.implementation')) - 1)
// The minus one makes the value the hash of no known preimage, lowering collision risk further

Practical use: to find which implementation any proxy currently points at, just read its first slot — that is exactly what a block explorer's "Read as Proxy" does.

Storage layout: the big trap

An upgrade replaces code, not data. So the new version's understanding of the layout must be fully compatible with the old one, or every field shifts meaning — without reverting.

// ERC-7201 in practice (used throughout OZ v5 internally)
/// @custom:storage-location erc7201:myapp.main
struct MainStorage {
    address owner;
    uint256 total;
}

// slot = keccak256(abi.encode(uint256(keccak256("myapp.main")) - 1)) & ~bytes32(uint256(0xff))
// compute the real value with a tool (a forge script, or OZ's helper) — never by hand
bytes32 private constant MAIN_STORAGE = 0x…computed from the formula above…;

function _main() private pure returns (MainStorage storage $) {
    assembly { $.slot := MAIN_STORAGE }
}

function setTotal(uint256 v) external {
    _main().total = v;        // accessed through $; ordering no longer matters
}

Initialisation: constructors do not work

A constructor runs at deployment and writes to the implementation's own storage — which the proxy never sees. So upgradeable contracts use initialize() instead, which creates a new problem: it is an ordinary function anyone can call.

contract MyApp is UUPSUpgradeable, OwnableUpgradeable {
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();          // ★ locks the implementation itself; mandatory
    }

    function initialize(address owner_) public initializer {
        __Ownable_init(owner_);          // the initializer modifier enforces once-only
        __UUPSUpgradeable_init();
    }

    // Adding fields in a later upgrade: use reinitializer with a version number
    function initializeV2(uint256 fee_) public reinitializer(2) {
        _main().fee = fee_;
    }

    // UUPS's upgrade guard — the only permission check; omit it and anyone can upgrade
    function _authorizeUpgrade(address newImpl) internal override onlyOwner {}
}

A fatal UUPS-specific mistake: the new implementation forgets to inherit UUPSUpgradeable. The upgrade succeeds, and with it the upgrade function disappears — that proxy can never be upgraded again, and funds may be stranded with it. OZ's upgrade plugin catches this; a manual deployment has no protection at all.

Selector clash: where Transparent came from

If the proxy itself exposes upgradeTo(address) and the implementation happens to have a function with the same name or the same four-byte selector, the call is intercepted by the proxy and never reaches the implementation. That is a function selector clash.

The transparent pattern resolves it by routing on the caller: admin calls hit the proxy's admin logic, everyone else is forwarded straight through. The cost is reading the admin on every call — which is exactly why OZ v5 made the admin immutable.

UUPS resolves it more cleanly: the proxy has no admin functions at all. Upgrade logic lives in the implementation, so a clash is impossible by construction — one reason UUPS became the default.

Pre-upgrade checklist

  1. Diff the storage layout with a tool. OpenZeppelin Upgrades (Hardhat and Foundry) blocks incompatible changes automatically. Do not eyeball the diff.
  2. Confirm the new version is still upgradeable (UUPS must keep inheriting UUPSUpgradeable).
  3. The implementation's constructor must call _disableInitializers().
  4. New initialisation goes in reinitializer(n), never a reused initializer.
  5. Rehearse on a fork: run upgradeToAndCall against mainnet state, then assert that key fields still read correctly.
  6. Put upgrade rights behind a multisig and a timelock, so users have time to observe and exit.
  7. Mind OZ v4 → v5: sequential and namespaced storage are incompatible; validate carefully across that boundary.

Smart-contract security (developers)

  • Layout drift does not revert: it silently returns wrong values. This is the pattern's most dangerous property — tests that only check "did it succeed" miss it entirely.
  • Immutables do not live in storage: immutable and constant are baked into bytecode, so swapping the implementation swaps their values with no trace in the proxy's storage.
  • Never delegatecall an untrusted address: it hands over your storage to be rewritten at will.
  • Inheritance order changes layout: under sequential storage, reordering parents alone is enough to shift every field.
  • A beacon's blast radius is every instance: one bad beacon upgrade breaks all proxies at once.
  • Verify and publish both proxy and implementation on the explorer, or users cannot tell what code they are interacting with.
