從零把一個站部署到 Cloudflare Pages：連 Git、設 build、綁網域、加 Function，以及正式上線前要知道的限制。文末附上目前該選 Pages 還是 Workers 的判斷，以及遷移路徑。

三句話版本
  • Pages 的核心體驗是「連上 Git，push 就部署」，外加每個分支自動有一個預覽網址。免費方案頻寬不計量。
  • 但要先知道一件事：Pages 目前處於維護模式——不是棄用，現有專案照常運作，但 Cloudflare 的新功能都優先進 Workers。
  • 因此：既有 Pages 專案不必急著搬；全新專案建議直接用 Workers，兩者的靜態託管能力自 2026-03 起已對等。

誰讀哪裡：只想把站放上線 → 看「步驟一～四」就夠；後端／全端工程師 → 加看 Functions 與 _headers；PM／技術決策 → 直接看「市場背景」與「該選 Pages 還是 Workers」。

市場背景

靜態託管這塊已經高度商品化，真正的差異在免費額度的計費方式與邊緣運算能力。Cloudflare 的賣點一直是頻寬不計量；代價是它正在把 Pages 併進 Workers。

對照其他選項：GitHub Pages 免費但要求 repo 公開（私有需付費方案），且沒有伺服器端能力；Vercel／Netlify 開發體驗好但免費額度對頻寬計量。Cloudflare 的「頻寬不計量」在流量成長時是實質優勢——但要接受它的產品線正在整併。

兩種部署方式，先選一種

Pages 有兩條路，差別在「build 在誰那裡跑」：

步驟一：連上 Git repo

  1. Cloudflare Dashboard → Workers & Pages → Create → Pages → Connect to Git。
  2. 授權 GitHub／GitLab。建議只授權「選定的 repo」而非整個帳號——這是最小權限原則，之後要加 repo 再回來調。
  3. 選 repo，選 production 分支（通常是 main）。

授權那一步是唯一會動到你 GitHub 帳號權限的地方。Cloudflare 需要讀取程式碼與寫入 commit status（好把部署結果標回 PR）。

步驟二：build 設定

這一步最常卡住，關鍵只有兩個欄位：build command（怎麼建）與 output directory（建完的檔案在哪）。填錯 output directory 就會部署出一個空站。

框架Build commandOutput directory
純靜態 HTML（留空）public 或 /
Vite / Reactnpm run builddist
Astronpm run builddist
Next.js（靜態匯出）npx next buildout
Hugohugopublic

另外兩個實務上必設的：

  • 環境變數：分 Production 與 Preview 兩組，可以給不同值。密鑰請用 Encrypt 存成 secret，不要當明文變數。
  • Node 版本：設環境變數 NODE_VERSION（例如 22），或在 repo 放 .nvmrc。不設會用預設版本，常常就是「本機能建、雲端建不起來」的原因。

步驟三：預覽部署

這是 Pages 相對 GitHub Pages 最實際的優勢：每個分支、每個 PR 都自動拿到一個獨立網址，可以直接把連結丟給同事或客戶看。

步驟四：自訂網域

  1. 專案 → Custom domains → Set up a domain，輸入網域。
  2. 網域若已在同一個 Cloudflare 帳號，DNS 記錄會自動建立；若在外部，照畫面指示新增 CNAME 指向 <project>.pages.dev。
  3. TLS 憑證自動簽發，通常幾分鐘內生效，免費且自動續期。

根網域（example.com）也可以直接用——Cloudflare 以 CNAME flattening 處理，不需要另外設 A 記錄。

重導向與標頭：_redirects 與 _headers

這兩個檔案放在輸出目錄的根層（不是專案根目錄），Pages 會自動識別。

# _redirects —— 每行：來源 目標 狀態碼
/old-post   /notes/new-post   301
/docs/*     /notes/:splat     301
# SPA fallback：所有未命中的路徑都交給 index.html
/*          /index.html       200
# _headers —— 為路徑加上回應標頭
/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin

# 帶雜湊的靜態資產可以長快取
/assets/hashed/*
  Cache-Control: public, max-age=31536000, immutable

那行 /* /index.html 200 是 SPA 的關鍵：狀態碼用 200 而不是 301，代表「內部改寫」而非「轉址」，網址列才會保留原路徑讓前端路由接手。

Pages Functions：加上伺服器端

在專案根目錄建一個 functions/ 目錄，裡面的檔案路徑就是 API 路徑，會自動變成邊緣執行的端點。

// functions/api/hello.ts  →  /api/hello
export const onRequestGet: PagesFunction = async (context) => {
  const { request, env } = context;
  const name = new URL(request.url).searchParams.get("name") ?? "world";

  return new Response(JSON.stringify({ hello: name }), {
    headers: { "Content-Type": "application/json" },
  });
};

env 裡放的是你綁定的資源——環境變數、KV、D1、R2。動態路由用中括號命名檔案：functions/api/[id].ts 對應 /api/123。

該選 Pages 還是 Workers

這是現在最該先想清楚的一題。Pages 沒有被棄用，現有專案可以繼續跑，Cloudflare 也沒有公布強制遷移期限。但官方已明講：所有新投資都放在 Workers，Pages 只拿到維護性更新。

你的情況建議
已經在跑的 Pages 專案不用急著搬。等下次重構或框架升級時順手做，比單獨搬一次划算。
全新專案直接用 Workers。靜態託管能力自 2026-03 起已對等，而且未來功能都先到 Workers。
需要 Durable Objects、Containers、Secrets Store只能用 Workers。這些從未登陸 Pages。
純靜態、且極度重視「連 Git 就好」的簡單度Pages 仍然最省事；Workers 也能連 Git，但設定檔要自己寫。

純靜態站遷到 Workers 的設定就這麼短：

{
  "name": "my-site",
  "compatibility_date": "2026-09-15",
  "assets": {
    "directory": "./dist/",
    "html_handling": "auto-trailing-slash",
    "not_found_handling": "404-page"
  }
}
# 部署（首次要先登入）
npx wrangler login
npx wrangler deploy

安全與設定風險（開發者）

  • 預覽網址預設公開。任何知道網址的人都看得到未發表的內容。敏感專案要在設定裡開 Access 保護預覽環境。
  • 密鑰別用明文環境變數。用 Encrypt 存成 secret；明文變數會出現在建置紀錄裡。
  • Git 授權範圍。授權時選「特定 repo」而非整個帳號，降低憑證外洩時的影響面。
  • 建置指令會執行 repo 內的程式碼。合併不信任的 PR 前要注意，惡意的 postinstall 可以在建置環境竊取你的環境變數。
  • 預設沒有安全標頭。X-Frame-Options、Content-Security-Policy 這些要自己在 _headers 加。

營運風險

  • 產品整併風險。Pages 處於維護模式。雖無期限，但新功能不會來，長期應規劃遷移。
  • 建置額度。免費方案每月 500 次建置、同時只能跑 1 個。分支多的團隊很容易排隊，CI 高峰期會變慢。
  • 檔案數上限。免費 20,000 檔／次部署。大型文件站或圖庫容易撞到，撞到就整個部署失敗。
  • 供應商綁定。_redirects、_headers、Functions、以及 KV／D1／R2 綁定都是 Cloudflare 專屬；純靜態部分可攜，這些則否。

Web3 前端上線與回復

發布前驗證 chain ID、官方合約地址、RPC、wallet network switch、approval spender 與連結。Secret 不可打包進 client JS；即使 build variable 加密，輸出到前端的值仍公開。DNS、repo、CI 和部署帳戶被接管，都可能替換使用者簽署的 calldata。

建立 preview → review → production → smoke check → rollback 的流程；保留上一版 artifact、記錄 commit 與部署版本。驗證首頁、筆記深連結、語言切換、404 與資產 cache。版本指紋 asset 才適合長時間 immutable；穩定檔名要 revalidate。回滾網頁不會撤銷使用者已簽署或已執行的鏈上動作。

Deploying with Cloudflare Pages

Getting a site onto Cloudflare Pages from zero: connect Git, configure the build, attach a domain, add a Function, and the limits worth knowing before you go live. At the end: whether to pick Pages or Workers today, and the migration path.

In three lines
  • The core of Pages is "connect Git, push to deploy", plus an automatic preview URL for every branch. Bandwidth is unmetered on the free plan.
  • But know this first: Pages is in maintenance mode — not deprecated, existing projects run fine, but Cloudflare ships new features to Workers first.
  • So: don't rush to migrate an existing Pages project; start new ones on Workers. Static hosting reached parity between the two in March 2026.

Where to start: just want the site live → steps one to four are enough; backend / full-stack engineers → add Functions and _headers; PMs and tech leads → read "Market background" and "Pages or Workers" only.

Market background

Static hosting is heavily commoditised; the real differences are how the free tier meters you and what edge compute you get. Cloudflare's pitch has always been unmetered bandwidth — the cost is that it is folding Pages into Workers.

Against the alternatives: GitHub Pages is free but requires a public repo (private needs a paid plan) and has no server-side capability; Vercel / Netlify have excellent DX but meter bandwidth on the free tier. Cloudflare's unmetered bandwidth is a genuine advantage as traffic grows — provided you accept that its product line is consolidating.

Pick one of two deployment modes

Pages offers two routes; the difference is where the build runs:

Step one: connect the Git repo

  1. Cloudflare Dashboard → Workers & Pages → Create → Pages → Connect to Git.
  2. Authorise GitHub / GitLab. Grant access to selected repositories rather than the whole account — least privilege; you can add more later.
  3. Pick the repo and the production branch (usually main).

That authorisation step is the only place this touches your GitHub account permissions. Cloudflare needs to read code and write commit statuses so results appear on your PRs.

Step two: build configuration

This is where people get stuck, and only two fields matter: the build command (how to build) and the output directory (where the built files land). Get the output directory wrong and you deploy an empty site.

FrameworkBuild commandOutput directory
Plain static HTML(leave empty)public or /
Vite / Reactnpm run builddist
Astronpm run builddist
Next.js (static export)npx next buildout
Hugohugopublic

Two more you will want in practice:

  • Environment variables: separate Production and Preview sets, which can hold different values. Store credentials with Encrypt as secrets, never as plaintext variables.
  • Node version: set the NODE_VERSION variable (e.g. 22) or commit an .nvmrc. Leaving it default is the classic cause of "builds locally, fails in the cloud".

Step three: preview deployments

This is the most practical advantage over GitHub Pages: every branch and every PR gets its own URL automatically, ready to send to a colleague or client.

Step four: custom domain

  1. Project → Custom domains → Set up a domain, enter the domain.
  2. If the domain is already on the same Cloudflare account the DNS record is created for you; if it is external, add the CNAME to <project>.pages.dev as instructed.
  3. TLS certificates are issued automatically, usually within minutes, free and auto-renewing.

An apex domain (example.com) works directly — Cloudflare handles it with CNAME flattening, so no separate A record is needed.

Redirects and headers: _redirects and _headers

Both files go in the root of the output directory (not the project root); Pages picks them up automatically.

# _redirects — one per line: from to status
/old-post   /notes/new-post   301
/docs/*     /notes/:splat     301
# SPA fallback: hand every unmatched path to index.html
/*          /index.html       200
# _headers — attach response headers to paths
/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin

# hashed assets can be cached forever
/assets/hashed/*
  Cache-Control: public, max-age=31536000, immutable

That /* /index.html 200 line is the key for SPAs: the status is 200, not 301, meaning an internal rewrite rather than a redirect, so the URL bar keeps the original path for your client-side router to handle.

Pages Functions: adding a server side

Create a functions/ directory in the project root; file paths inside become API routes, running at the edge.

// functions/api/hello.ts  →  /api/hello
export const onRequestGet: PagesFunction = async (context) => {
  const { request, env } = context;
  const name = new URL(request.url).searchParams.get("name") ?? "world";

  return new Response(JSON.stringify({ hello: name }), {
    headers: { "Content-Type": "application/json" },
  });
};

env holds your bindings — environment variables, KV, D1, R2. Dynamic routes use bracketed filenames: functions/api/[id].ts serves /api/123.

Pages or Workers

This is the question to settle first. Pages is not deprecated, existing projects keep running, and Cloudflare has announced no forced migration deadline. But it has said plainly that all new investment goes to Workers; Pages gets maintenance updates.

Your situationRecommendation
An existing Pages projectNo rush. Fold the migration into your next refactor or framework upgrade — cheaper than doing it on its own.
A brand-new projectGo straight to Workers. Static hosting reached parity in March 2026, and new features land there first.
You need Durable Objects, Containers, Secrets StoreWorkers only. These never came to Pages.
Purely static and you value "just connect Git"Pages is still the least effort; Workers can also connect Git but you write the config yourself.

For a purely static site the Workers config is this short:

  "name": "my-site",
  "compatibility_date": "2026-09-15",
  "assets": {
    "directory": "./dist/",
    "html_handling": "auto-trailing-slash",
    "not_found_handling": "404-page"
  }
}

Security and configuration risk (developers)

  • Preview URLs are public by default. Anyone with the link sees unpublished work. Enable Access on previews for sensitive projects.
  • Never put credentials in plaintext variables. Use Encrypt to store them as secrets; plaintext variables show up in build logs.
  • Scope the Git authorisation. Grant selected repositories rather than the whole account, to limit blast radius if the token leaks.
  • The build command executes repo code. Be careful merging untrusted PRs — a malicious postinstall can exfiltrate your build-time environment variables.
  • No security headers by default. X-Frame-Options, Content-Security-Policy and friends must be added in _headers yourself.

Operational risk

  • Product consolidation. Pages is in maintenance mode. No deadline, but no new features either — plan a migration for the long run.
  • Build quota. 500 builds a month on the free plan, one at a time. Teams with many branches queue quickly and slow down at CI peaks.
  • File-count ceiling. 20,000 files per deployment on free. Large docs sites or image galleries hit it, and hitting it fails the whole deployment.
  • Vendor lock-in. _redirects, _headers, Functions and KV/D1/R2 bindings are Cloudflare-specific; the static files are portable, these are not.

Shipping and recovering a Web3 frontend

Before release verify chain ID, official contract addresses, RPCs, wallet network switching, approval spenders, and links. Never bundle secrets into client JavaScript: encrypted build variables become public if emitted into the frontend. Compromised DNS, repositories, CI, or deployment accounts can change the calldata users sign.

Use preview → review → production → smoke check → rollback. Retain the previous artifact and record commit/deployment versions. Check home, deep note links, language toggle, 404, and asset caching. Long immutable caching requires fingerprinted filenames; stable names should revalidate. Website rollback cannot undo signed or executed on-chain actions.
