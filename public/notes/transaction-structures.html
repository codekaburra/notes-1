範圍與核心概念

本系列比較 Ethereum、Cosmos 與 Solana 的交易結構。本篇先完成 Ethereum 的一般 EOA 交易，以 EIP-1559 type 2 為主；Solana 與 Token-2022 見第二篇；Cosmos 與 IBC 見第三篇。先讀 簽章與 r、s、v。

交易是帳戶簽署的一份執行請求。發送 ETH、approve、swap 都可以是交易；合約執行時再發出的 CALL 則不是另一筆由 EOA 簽署的頂層交易。區塊瀏覽器的 internal transactions 通常是執行 trace，不是多一份簽章交易。

先看三層：內容、簽章、結果

交易內容：chainId / nonce / to / value / data / gas / fees
   ↓ 依 type 編碼並 hash，錢包簽署
已簽署交易：內容 + yParity / r / s
   ↓ 廣播、節點檢查、區塊收錄、EVM 執行
執行結果：receipt / status / gasUsed / logs

transaction hash 不是 receipt，也不是成功證明。簽署完成還沒廣播；RPC 接受也不代表已收錄；已收錄的交易還可能 revert。應分開追蹤 pending、included、execution status 與 finality。

Type 2 欄位逐一拆解

欄位用途開發注意
type交易 envelope 類型；type 2 的前綴是 0x02不是合約函式 selector
chainId指定鏈並納入簽署確認 RPC 與錢包鏈一致
noncesender 的交易序號不是 ECDSA 的秘密 k；同帳戶並行送單要管理
maxPriorityFeePerGas願意支付的每 gas tip 上限不是總手續費
maxFeePerGas每 gas 的總費率上限包含 base fee 與 tip，不是一定會全付
gasLimit交易可使用的 gas 上限包含 intrinsic gas 等成本；不是實際 gasUsed
to收款或被呼叫的地址一般合約建立交易使用空 destination；不等於零地址
value隨交易轉移的原生 ETH，單位 weiERC-20 數量通常在 data；value 不是 token amount
data / input任意 bytes；合約呼叫通常放 calldata部署時放 initcode；不是部署後 runtime bytecode 的簡單替代名稱
accessList事先列出的地址與 storage keys可為空；不是存取權限白名單，也不保證更省 gas
yParity、r、s簽章與恢復資訊type 2 的 yParity 為 0／1

RPC 常把整數以 hex quantity 回傳，例如 0x5208 = 21,000。bytes 與整數需按 schema 解析，不要把 0x 字串直接當十進位數字。

具體例子：ETH 轉帳與 ERC-20 transfer

// type 2：示意 unsigned 欄位，不是可直接廣播的 raw bytes
{
  type: 2,
  chainId: 1,
  nonce: 7,
  maxPriorityFeePerGas: 2_000_000_000, // 2 gwei
  maxFeePerGas: 30_000_000_000,       // 30 gwei
  gasLimit: 21_000,
  to: "0x1111111111111111111111111111111111111111",
  value: 10_000_000_000_000_000n,     // 0.01 ETH
  data: "0x",
  accessList: []
}

這是對無程式碼接收者的簡單轉帳示意；若接收者執行程式碼，不能假設 21,000 gas 足夠。不要用這個示意地址做真實轉帳。

ERC-20 transfer：to 改成 token 合約地址，value 通常為 0，data 為 transfer(address,uint256) 的 selector 加 ABI 編碼 recipient 與 amount。使用 ABI encoder，不手動拼字串；token amount 以該 token decimals 換成最小單位。ERC-20 approve 同樣是呼叫 token 合約，spender 在 calldata 中。

從欄位到 wire format

unsigned = 0x02 || RLP([
  chainId, nonce, maxPriorityFeePerGas, maxFeePerGas,
  gasLimit, to, value, data, accessList
])
signingDigest = keccak256(unsigned)

signedRaw = 0x02 || RLP([
  chainId, nonce, maxPriorityFeePerGas, maxFeePerGas,
  gasLimit, to, value, data, accessList, yParity, r, s
])
transactionHash = keccak256(signedRaw)

JSON 是方便人與 RPC 操作的表示法，不是 type 2 在網路上的交易編碼。from、hash、blockNumber、transactionIndex 等 RPC 欄位不都屬於上述 signed payload。簽後 SDK 應能解析 raw bytes 並恢復 sender；不要拿 JSON.stringify 的 hash 當 signing digest。

legacy type 0 使用不同欄位與 v 編碼；type 1 引入 access list；type 3 是 blob 交易；type 4 帶 authorization list。它們不能全部當成 type 2 解碼，本篇不展開其完整格式。

Receipt、logs 與執行失敗

資料回答什麼
交易誰授權，要求呼叫誰、帶多少 ETH 與什麼 calldata
receipt.status頂層執行成功或失敗；不是每次內部呼叫都成功的保證
gasUsed / effectiveGasPrice該筆實際使用 gas 與適用費率
logs成功保留的事件輸出；須按 emitting address 與 ABI 解碼
trace更詳細的呼叫與執行路徑，通常由特定 RPC 提供

被收錄但頂層 revert 的交易通常仍消耗 nonce 並支付 gas；其執行狀態改動與 logs 回滾。內部呼叫失敗若被捕捉，頂層仍可能 status = 1。Receipt 也不是一般函式 return value；前端若需要結果，可結合事件、狀態讀取或適當模擬。

例：gasUsed = 21,000，base fee = 20 gwei，tip 上限 2 gwei，max fee 30 gwei，則有效費率為 22 gwei，執行 gas 費為 0.000462 ETH。這裡只計 Ethereum type 2 執行 gas；L2 或其他交易型別可能有額外費用。

新手開發驗收與 PM 風險

  1. 建立交易前核對 chainId、帳戶、token 地址、decimals 與 ABI；清楚顯示 value 和 calldata 代表的操作。
  2. 模擬並估 gas，但不把模擬成功當成未來保證；狀態、價格與授權可能改變。
  3. 簽署後解析 raw transaction，比對 sender、to、value、data、nonce、gas 與費率。
  4. 廣播 timeout 時先查 hash、帳戶 nonce 與 pending 狀態；不要直接用新 nonce 重做業務動作。同 nonce replacement 需重新簽署，且費率規則依節點處理。
  5. 收錄後查 receipt、預期事件與最終狀態；依資產風險等待足夠確認，處理 reorg。

PM 應把使用者看到的「簽署、送出、收錄、執行、最終確認」分開。常見市場風險包括 pending 期間價格變動、MEV、滑點和過期報價；交易結構中的 calldata 必須包含協議需要的保護，例如 minOut 與 deadline，交易本身不會自動提供。

Scope and mental model

This series covers Ethereum, Cosmos and Solana transaction structures. Part I covers ordinary Ethereum EOA transactions, focusing on EIP-1559 type 2. Solana and Token-2022 are in Part II; Cosmos and IBC are in Part III. Read r, s, v first.

A transaction is a signed execution request. Contract CALLs during execution are not additional EOA-signed top-level transactions; explorer internal transactions usually describe traces.

Content, signature, outcome

Fields → type-specific encoding and signing digest
  → signed transaction → broadcast and inclusion
  → EVM execution → receipt, status, gasUsed, logs

A transaction hash is not proof of successful execution. Distinguish signing, submission, inclusion, execution status and finality.

Type 2 fields

FieldMeaning / caution
type0x02 envelope prefix, not a function selector
chainIdSigned chain identity; check wallet and RPC network
nonceSender transaction sequence, not secret ECDSA k
maxPriorityFeePerGasTip cap per gas
maxFeePerGasTotal fee cap per gas, not guaranteed actual price
gasLimitGas budget including intrinsic costs, not actual gas used
toDestination; empty for ordinary contract creation, not the zero address
valueNative ETH in wei; not an ERC-20 amount
data / inputCall bytes, or initcode for deployment
accessListAddresses and storage keys; not an authorization allowlist or guaranteed gas saving
yParity, r, sSignature; type 2 parity is 0 or 1

RPC quantities often use hex: 0x5208 means 21,000. Parse bytes and quantities according to their schema.

ETH transfer versus ERC-20 transfer

A simple example uses chainId 1, nonce 7, 2 gwei priority cap, 30 gwei total cap, gasLimit 21,000, value 0.01 ETH, empty data and access list. The 21,000 budget assumes a simple transfer to a recipient with no executing code; do not apply it blindly to contracts.

An ERC-20 transfer instead targets the token contract, normally sends zero native value, and encodes transfer(address,uint256) with recipient and token amount in calldata. Use an ABI encoder and the token decimals. An approve likewise targets the token contract, with spender in calldata.

Wire encoding and hashes

unsigned = 0x02 || RLP([
  chainId, nonce, maxPriorityFeePerGas, maxFeePerGas,
  gasLimit, to, value, data, accessList
])
signingDigest = keccak256(unsigned)
signedRaw = 0x02 || RLP([
  chainId, nonce, maxPriorityFeePerGas, maxFeePerGas,
  gasLimit, to, value, data, accessList, yParity, r, s
])
transactionHash = keccak256(signedRaw)

RPC JSON is not the wire encoding. Derived fields such as from, hash, blockNumber and transactionIndex are not all signed payload fields. Never substitute a hash of JSON.stringify. Legacy type 0, access-list type 1, blob type 3 and authorization-list type 4 have different layouts; this article does not detail them.

Receipts, logs, failure and fees

The transaction states the authorized request. The receipt reports top-level status and gas accounting; logs describe retained events, decoded with the emitting address and ABI. Traces show deeper execution paths. A receipt is not an ordinary function return value.

An included top-level revert normally consumes the sender nonce and gas while rolling back execution state changes and logs. Caught internal failures may coexist with top-level status 1. Verify expected business effects, not status alone.

With gasUsed 21,000, base fee 20 gwei, priority cap 2 gwei and total cap 30 gwei, effective price is 22 gwei and execution gas costs 0.000462 ETH. L2s and other transaction types may add other fees.

Development and product acceptance

  1. Check chain, signer, token address, decimals and ABI; display native value and the actual calldata action.
  2. Simulate and estimate gas; changing state and prices can invalidate assumptions.
  3. Parse signed bytes and compare sender, recipient, value, data, nonce, gas and fees.
  4. After a broadcast timeout, inspect transaction hash, nonce and pending state before repeating an operation with a new nonce. Same-nonce replacements need new signatures and must meet node fee policy.
  5. Inspect receipt, expected events and state; wait for suitable confirmation and handle reorgs.

Show signing, submission, inclusion, execution and finality separately. Pending price movements, MEV and stale quotes remain product risks. Protocol-specific minOut and deadline protections must be encoded and enforced; transactions do not supply them automatically.
