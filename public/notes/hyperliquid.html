Hyperliquid 架構

2026-09-09 · 永續合約 DEX · 開發者視角 · 變動快，落地前請再查證

Hyperliquid 不是一般 DEX，而是一條為永續合約而生的 L1。對開發者而言，關鍵在於它把系統切成兩層、並用 precompile 與 CoreWriter 把兩層縫在一起——這是本則三個重點（連動、Solidity、風險）的核心。

設計理念：CLOB + 雙層

多數鏈上永續 DEX 用預言機定價（GMX）或把訂單簿放鏈下（早期 dYdX）。Hyperliquid 反其道而行：整個中央限價訂單簿（CLOB）放上鏈，以自有共識 HyperBFT 撐低延遲，追求接近中心化交易所的體驗但保留鏈上可驗證。系統分兩層：

層職責你怎麼碰它
HyperCore原生層：訂單簿、撮合、清算、永續邏輯鏈下用簽名 API 下單；鏈上用 precompile／CoreWriter
HyperEVM相容 EVM 的通用合約層照常部署 Solidity 合約

兩層共享狀態，因此 HyperEVM 的合約能直接讀 HyperCore 的價格與部位、也能把動作寫回去——不需外部預言機。這正是它跟「一般 EVM 鏈 + 外掛交易所」最大的不同。

Solidity：讀狀態、寫動作

讀取——以 staticcall 打讀取類 precompile（起於 0x…0800，各查詢有各自位址，實際請對照官方文件或 hyper-evm-lib）：

// 讀取類 precompile 由 0x…0800 起；此處示意讀取某 index 的價格
address constant PX_PRECOMPILE = 0x0000000000000000000000000000000000000807;

function markPx(uint32 index) public view returns (uint64) {
    (bool ok, bytes memory ret) = PX_PRECOMPILE.staticcall(abi.encode(index));
    require(ok, "precompile failed");
    return abi.decode(ret, (uint64));          // 同步取得，可直接用於下游邏輯
}

寫入——透過 CoreWriter（0x3333…3333）的唯一函式 sendRawAction(bytes)。動作以「版本位元組 + action id + abi 編碼參數」組成。以下為官方文件的 USD class transfer 範例：

interface ICoreWriter { function sendRawAction(bytes calldata data) external; }
ICoreWriter constant CW = ICoreWriter(0x3333333333333333333333333333333333333333);

function usdClassTransfer(uint64 ntl, bool toPerp) external {
    bytes memory action = abi.encode(ntl, toPerp);
    bytes memory data = new bytes(4 + action.length);
    data[0] = 0x01; data[1] = 0x00; data[2] = 0x00; data[3] = 0x07;   // 版本 + action id
    for (uint256 i = 0; i < action.length; i++) data[4 + i] = action[i];
    CW.sendRawAction(data);                     // 只是「發出」動作——非同步！
}

智慧合約安全風險（開發者）

  • 寫入非同步是頭號陷阱。CoreWriter 送出後不代表已成交；同一筆 EVM 交易內「先下單、再讀部位確認」是行不通的，狀態要等後續區塊才更新。
  • precompile 是可信價源，但別誤用。它讀的是 HyperCore 的真實狀態（不像現貨池價可被閃電貸操縱），但仍要處理回傳解碼、gas，以及索引／市場對映錯誤。
  • 動作編碼要逐位元正確。版本位元組與 action id 錯一格，行為就不同；用經驗證的函式庫（hyper-evm-lib）而非自行拼 bytes。
  • HyperEVM 仍是新環境。雙區塊（小／大 block）、gas 模型、precompile 行為都與主流 EVM 有差異；上線前在測試網把邊界跑過。

使用者投資風險

永續合約的風險遠高於現貨，務必先懂再進場：

風險說明
槓桿清算永續是槓桿商品，價格反向到維持保證金以下即被強制平倉，本金可能歸零。
資金費率多空失衡時要持續支付對手方，長抱單邊會被費率慢慢侵蝕。
HLP 金庫回撤存入 HLP 等於當造市／清算對手方；極端行情或大額清算時，金庫可能承受可觀虧損，並非穩賺。
自動減倉（ADL）對手方爆倉且保險金不足時，你的獲利部位可能被強制部分平倉。
預言機／標記價清算依標記價而非最新成交價；標記價異常會觸發非預期清算。
合約與橋風險HyperEVM 上的借貸、LST 等協議各有智慧合約風險；跨鏈資產還有橋的風險。
代幣解鎖／集中度HYPE 等代幣的解鎖排程與持有集中度會影響價格波動。

一句話：現貨的敵人是「幣價跌」；永續多了「被清算」「付資金費」「被 ADL」——時間與槓桿都會咬人。

Hyperliquid Architecture

2026-09-09 · Perp DEX · Developer view · Moves fast, re-verify before building

Hyperliquid is not an ordinary DEX but an L1 purpose-built for perpetuals. For developers the key is that it splits the system into two layers and stitches them together with precompiles and CoreWriter — the core of this note's three themes (interconnection, Solidity, risk).

Design idea: CLOB + two layers

Most on-chain perp DEXs price via an oracle (GMX) or keep the book off-chain (early dYdX). Hyperliquid does the opposite: the whole central limit order book (CLOB) lives on-chain, with its own HyperBFT consensus for low latency — aiming for a CEX-like experience while staying verifiable. Two layers:

LayerResponsibilityHow you touch it
HyperCoreNative: order book, matching, liquidation, perp logicOff-chain via signed API; on-chain via precompiles / CoreWriter
HyperEVMEVM-compatible general contract layerDeploy Solidity as usual

The two share state, so HyperEVM contracts can read HyperCore's prices and positions directly, and write actions back — no external oracle needed. That is the biggest difference from an "ordinary EVM chain plus a bolted-on exchange."

Solidity: read state, write actions

Reading — staticcall a read precompile (starting at 0x…0800; each query has its own address, confirm against the official docs or hyper-evm-lib):

// read precompiles start at 0x…0800; here, reading a price for some index
address constant PX_PRECOMPILE = 0x0000000000000000000000000000000000000807;

function markPx(uint32 index) public view returns (uint64) {
    (bool ok, bytes memory ret) = PX_PRECOMPILE.staticcall(abi.encode(index));
    require(ok, "precompile failed");
    return abi.decode(ret, (uint64));          // synchronous, usable downstream
}

Writing — via CoreWriter (0x3333…3333) and its single function sendRawAction(bytes). An action is "version byte + action id + abi-encoded params". Here is the official docs' USD class transfer example:

interface ICoreWriter { function sendRawAction(bytes calldata data) external; }
ICoreWriter constant CW = ICoreWriter(0x3333333333333333333333333333333333333333);

function usdClassTransfer(uint64 ntl, bool toPerp) external {
    bytes memory action = abi.encode(ntl, toPerp);
    bytes memory data = new bytes(4 + action.length);
    data[0] = 0x01; data[1] = 0x00; data[2] = 0x00; data[3] = 0x07;   // version + action id
    for (uint256 i = 0; i < action.length; i++) data[4 + i] = action[i];
    CW.sendRawAction(data);                     // only EMITS the action — async!
}

Smart-contract security (for developers)

  • Async writes are the number-one trap. A CoreWriter send does not mean filled; "place an order then read the position to confirm" within one EVM tx does not work — state updates only in later blocks.
  • Precompiles are a trusted price source, but don't misuse them. They read HyperCore's real state (unlike a spot pool price a flash loan can push), but you still must handle decoding, gas, and index/market mapping errors.
  • Action encoding must be byte-exact. A wrong version byte or action id changes behaviour; use a vetted library (hyper-evm-lib) rather than assembling bytes by hand.
  • HyperEVM is still a new environment. Dual blocks (small/large), the gas model and precompile behaviour differ from mainstream EVM; exercise the edges on testnet before shipping.

User investment risk

Perpetuals carry far more risk than spot; understand them before entering:

RiskWhat it is
Leverage liquidationPerps are leveraged; move against you past maintenance margin and you're force-closed — principal can go to zero.
Funding rateWhen longs and shorts are imbalanced you continually pay the other side; holding one side long is eroded by funding.
HLP vault drawdownDepositing into HLP makes you the market-maker / liquidation counterparty; in extreme moves or large liquidations the vault can take real losses — not guaranteed yield.
Auto-deleveraging (ADL)If a counterparty blows up and the insurance fund is short, your winning position may be partially force-closed.
Oracle / mark priceLiquidation uses the mark price, not the last trade; an abnormal mark can trigger unexpected liquidation.
Contract and bridge riskLending, LSTs and other HyperEVM protocols each carry smart-contract risk; cross-chain assets add bridge risk.
Token unlocks / concentrationHYPE and other tokens' unlock schedules and holder concentration affect price volatility.

In short: spot's enemy is "price falls"; perps add "getting liquidated," "paying funding," and "being ADL'd" — time and leverage both bite.
