Hyperliquid 架構

2026-09-12 · HyperCore · HyperEVM · 永續 DEX · 開發者指南 · 變動快，落地前請再查證

Hyperliquid 不是「EVM 鏈外掛一座交易所」，而是一條為永續合約而生的 L1：HyperCore 跑訂單簿與清算，HyperEVM 跑 Solidity，兩邊由 precompile 與 CoreWriter 縫在一起。本則給要寫合約或 bot 的人：資產實際在哪、account mode 不是 ERC-4337、讀寫時序、gas、agent 權限、跨層 vs 跨鏈，以及儲備證明能證明什麼。

先記住三件事：相同地址在 Core 與 EVM 不是同一份 state；REST／WebSocket 只是提交介面，撮合仍在 HyperCore；CoreWriter 送出 ≠ 已成交。

設計理念：CLOB + 雙層，同一條 L1

多數鏈上永續 DEX 用預言機定價（GMX）或把訂單簿放鏈下（早期 dYdX）。Hyperliquid 把整個中央限價訂單簿（CLOB）放上 HyperCore，以 HyperBFT 撐低延遲。HyperEVM 是同一條 L1 上的 EVM 執行環境，不是另一條 rollup。

層職責你怎麼碰它
HyperCore訂單簿、撮合、清算、spot／perp 餘額簽名 API 提交動作；合約用 precompile 讀、CoreWriter 寫
HyperEVM相容 EVM 的合約層、原生 HYPE gas照常部署 Solidity；ERC-20 balanceOf 只看見這一層

讀取是同步的：precompile 回傳「建構這顆 EVM block 當下」的 HyperCore 狀態。寫入是非同步的：CoreWriter 只把動作排進 HyperCore 佇列。

Account abstraction modes：不是 ERC-4337

Hyperliquid 的「Account Abstraction」是 spot 與 perps 保證金怎麼共用，跟 ERC-4337 的 Smart Account 無關。切換用 userSetAbstraction／CoreWriter action id 16。

模式餘額怎麼算誰該用
Unified（建議一般使用者）同一資產一份餘額：現貨與該資產的 cross-margin perps 共用一般交易
Portfolio margin合格資產（目前 HYPE、BTC、USDC、USDT）合成一份投資組合保證金要最高資金效率
Standard／Manualspot、perp、各 DEX 分開；cross 只在單一 DEX 內做市、高頻、builder
DEX abstraction已停用不要再用
  • Builder-fee 收款地址必須是 Standard，否則收不到 builder fee。
  • Unified 與 Portfolio margin 每天最多約 5 萬筆 user action；Standard 無此上限。
  • API 在 Unified／PM 下，餘額與 hold 都出現在 spot clearinghouse；個別 perp DEX user state 沒有意義。
  • CoreWriter 的 USD class transfer（action id 7）只在「spot 與 perp 分開記帳」時有意義，不是通用餘額模型。

資產實際在哪：HyperCore vs HyperEVM

同一個 20-byte 地址在兩邊各有一份帳本。合約裡的 token.balanceOf(addr) 只讀 HyperEVM；perp 保證金、Core spot、未成交單，都在 HyperCore。

你看到的實際位置
EVM balanceOf／原生 HYPEHyperEVM
Core spot、perp 保證金、掛單凍結HyperCore clearinghouse
子帳戶獨立 Core 帳戶，不與主帳戶合併
已連結的 Core spot ↔ EVM ERC-20經 system address 互轉，不是自動共用

System address：第一個 byte 為 0x20，其餘為 0，token index 以 big-endian 寫在尾端（例如 index 200 → 0x2000…00c8）。HYPE 例外：0x2222…2222，對應 EVM 原生 gas，不是 ERC-20。

  • Core → EVM：sendAsset 到該 token 的 system address。下一顆 EVM block 由系統以 system address 對 linked ERC-20 呼叫 transfer(recipient, amount)。花費約 20 萬 gas，以下一顆 EVM block 的 base fee 計。
  • EVM → Core：對 linked ERC-20（或 HYPE 轉 value 到 0x2222…）Transfer 到 system address。同一顆產出 EVM 的 L1 block 裡、EVM block 建完後入帳。
  • 官方目前不檢查 system address 是否有足夠供給、也不檢查合約是不是合法 ERC-20。linked 合約可以是任意 bytecode。
  • EVM 比 Core 多出來的 wei decimals：金額若沒對齊（末尾不是 extraWeiDecimals 個 0），非整部分會被燒毀（保證 < 1 Wei）。

Solidity：讀 precompile、寫 CoreWriter

讀取——staticcall 打讀取類 precompile（從 0x…0800 起，沒有 4-byte selector，參數直接 ABI encode）。價格是 raw uint64：永續除以 10^(6 - szDecimals)，現貨除以 10^(8 - base szDecimals)。無效資產或 vault 會讓該 call frame 吃光傳入的 gas。費用約 2000 + 65 * (input_len + output_len)。

// 示意；完整介面見 L1Read.sol / hyper-evm-lib
address constant MARK_PX   = 0x0000000000000000000000000000000000000806;
address constant ORACLE_PX = 0x0000000000000000000000000000000000000807; // 不是 markPx
address constant SPOT_PX   = 0x0000000000000000000000000000000000000808;

function oraclePx(uint32 index) public view returns (uint64) {
    (bool ok, bytes memory ret) = ORACLE_PX.staticcall(abi.encode(index));
    require(ok, "oraclePx failed");                  // 失敗會耗盡本 frame gas
    return abi.decode(ret, (uint64));
}

寫入——CoreWriter（0x3333…3333）唯一函式 sendRawAction(bytes)。編碼：1 byte 版本（目前 0x01）+ 3 byte big-endian action id + ABI 參數。先燒掉約 25k gas，實際呼叫約 47k。以下官方 USD class transfer 範例只適用「spot／perp 分開」的帳戶；Unified／PM 不要拿它當通用轉帳。

interface ICoreWriter { function sendRawAction(bytes calldata data) external; }
ICoreWriter constant CW = ICoreWriter(0x3333333333333333333333333333333333333333);

function usdClassTransfer(uint64 ntl, bool toPerp) external {
    bytes memory action = abi.encode(ntl, toPerp);
    bytes memory data = new bytes(4 + action.length);
    data[0] = 0x01; data[1] = 0x00; data[2] = 0x00; data[3] = 0x07;   // 版本 + action 7
    for (uint256 i = 0; i < action.length; i++) data[4 + i] = action[i];
    CW.sendRawAction(data);                     // 只是發出——非同步
}

動作以合約自己的 HyperCore 地址執行，不是 tx.origin。訂單與 vault transfer 會再延遲數秒，避免用 EVM 繞過 L1 mempool。新 Core 帳戶第一次當收款人要付 1 顆 quote token（如 1 USDC）啟動費；未啟動的地址不能送 CoreWriter。合約部署者應先對合約地址做一筆 Core 啟動轉帳。

時序：同一 L1 block 內誰先誰後

Core → EVM 轉帳排到下一顆 EVM block。EVM → Core 轉帳發生在「有產出 EVM 的那顆 L1 block」裡、EVM block 建完之後。該 L1 block 的順序是：

  1. 建 L1 block
  2. 建 EVM block
  3. 處理 EVM → Core 轉帳
  4. 處理 CoreWriter 動作

CoreWriter 的帳戶必須在 EVM block 開始前就已存在於 HyperCore。同一 block 先 EVM→Core 啟動帳戶、再 CoreWriter，會被拒絕。

Gas：小塊、大塊與 CoreWriter

HyperEVM 把吞吐量拆成兩種 block、兩份 mempool，block number 仍單調遞增：

小塊大塊
間隔約 1 秒約 1 分鐘
gas 上限3M30M
用途一般交易、確認速度大型部署

每個地址 mempool 只收接下來 8 個 nonce；超過一天的交易會被修剪。切到大塊用 Core action evmUserModify.usingBigBlocks: true（這是 HyperCore 使用者旗標，要先成為 Core user）。估大塊 base fee 用 RPC bigBlockGasPrice，不要用普通 gasPrice。

Precompile 失敗會燒光該 frame 的 gas：呼叫時不要把剩餘 gas 全傳進去。CoreWriter 本身先燒 ~25k；合約還要為後續 HyperCore 執行與 20 萬 gas 的 Core→EVM 轉帳留預算。

鏈下 API：提交介面，撮合仍在 HyperCore

高頻下單、撤單、改槓桿走 REST／WebSocket，不經過 HyperEVM。這不是鏈下訂單簿：簽名動作送到交換端點後，撮合、優先順序與成交仍在 HyperCore 上發生。

權限：主錢包、agent、子帳戶

API wallet（文件裡的 agent）只能簽名：能下單、改槓桿、把你送進清算，不能提款，本身也不持有資金。查餘額要傳主帳戶或子帳戶地址；傳 agent 地址會得到空結果。

  • Nonce 跟簽署者（agent 位址）走，不是跟被代理的使用者走。每個 signer 保留最高 100 個 nonce；新 nonce 必須大於集合裡最小的、且未用過；時間窗是區塊時間 (T-2 天, T+1 天)。
  • 一個 agent 簽主帳戶、vault、子帳戶，共用同一份 nonce 集合。每個程序／子帳戶用不同 agent。
  • Agent 被撤銷、過期、或主帳戶沒資金時，nonce 狀態可能被修剪。不要重用已撤銷的 agent 地址——修剪後舊簽名可能被重放。
  • ApproveBuilderFee 必須由主錢包簽，agent 不行。

跨層 vs 跨鏈

HyperCore 與 HyperEVM 是同一條 HyperBFT L1 的兩層，不是兩條鏈，也沒有七日挑戰期。跨出去才是另一回事：

  • USDC：優先走 Circle CCTP 在 Hyperliquid 上原生鑄造。舊的 Arbitrum 橋已棄用。
  • 舊橋：主網 0x2df1…3df7。最低入金 5 USDC，低於這個不會入帳且永遠拿不回。出金只在 Hyperliquid 簽名，由驗證者在 Arbitrum 放行，約 3–4 分鐘。

合約不要假設「EVM 上一筆 transfer 等於 Core 已有保證金」；也不要假設 CCTP mint 與 Core 入帳是同一筆原子交易。

Proof of reserve：有資產 ≠ 可償付

三件不同的事：

  1. 原生 USDC／CCTP： Circles 鑄造模型；贖回走 CCTP，不是 Hyperliquid 自建的 lock-mint。
  2. 舊 Arbitrum 橋 escrow：仍鎖在橋合約裡的 USDC。這是歷史路徑的儲備，不是「全部 HyperCore USDC」。
  3. 已連結的 Core／EVM token：system address 在 EVM 側應持有足以對應 Core 可贖回供給的餘額；還要核對 code hash、mint／升級權、decimals。官方不替你做這項檢查。

PoR 證明不了償付能力：HLP 金庫、未成交凍結、借貸／再質押、Portfolio margin 的交叉保證金，都不會出現在「system address 有多少 token」這一個數字裡。

智慧合約安全風險（開發者）

  • 寫入非同步是頭號陷阱。同一筆 EVM 交易內「先下單、再讀部位確認」行不通。同一 block 先啟動帳戶再 CoreWriter 會被拒。
  • precompile 位址不要抄錯。0x0806 markPx、0x0807 oraclePx、0x0808 spotPx。無效輸入耗盡 gas；raw 價格要自己做 decimals scaling。
  • 不要把 EVM balanceOf 當 Core 保證金。linked 轉帳沒有官方供給檢查；非整 wei 會被燒。
  • 動作編碼要逐位正確。用 hyper-evm-lib，別手拼 bytes。USD class transfer 不是萬用轉帳。
  • 雙區塊與 8 nonce。大合約部署要切 big blocks；mempool 只收接下來 8 個 nonce。

使用者投資風險

永續的風險遠高於現貨：

風險說明
槓桿清算價格反向到維持保證金以下即被強制平倉，本金可能歸零。Agent 也能把你送進這個狀態。
資金費率多空失衡時持續支付對手方。
HLP 金庫回撤存入 HLP 等於當造市／清算對手方；極端行情可能虧損。這不是 PoR 涵蓋的範圍。
自動減倉（ADL）對手方爆倉且保險金不足時，獲利部位可能被強制部分平倉。
標記價清算依 mark／oracle，不是最新成交價。
橋與 linked token舊橋低於 5 USDC 的入金會消失；linked ERC-20 的實作可能與 Core 脫鉤。
代幣解鎖／集中度HYPE 等代幣的解鎖與持有集中度會放大波動。

現貨的敵人是「幣價跌」；永續多了清算、資金費、ADL。時間與槓桿都會咬人。

Hyperliquid Architecture

2026-09-12 · HyperCore · HyperEVM · Perp DEX · Developer guide · Moves fast; re-verify before shipping

Hyperliquid is not "an EVM chain with an exchange bolted on." It is an L1 purpose-built for perpetuals: HyperCore runs the book and liquidations, HyperEVM runs Solidity, and precompiles plus CoreWriter stitch the two together. This note is for people writing contracts or bots: where assets actually live, why "account abstraction" here is not ERC-4337, read/write timing, gas, agent authority, cross-layer vs cross-chain, and what a proof of reserve can actually prove.

Three facts first: the same address on Core and EVM is not the same state; REST / WebSocket is a submission interface, matching stays on HyperCore; a CoreWriter send is not a fill.

Design idea: CLOB + two layers, one L1

Most on-chain perp DEXs price via an oracle (GMX) or keep the book off-chain (early dYdX). Hyperliquid puts the whole central limit order book (CLOB) on HyperCore, with HyperBFT for low latency. HyperEVM is an EVM environment on that same L1, not a separate rollup.

LayerResponsibilityHow you touch it
HyperCoreBook, matching, liquidation, spot/perp balancesSigned API to submit; contracts read via precompiles and write via CoreWriter
HyperEVMEVM contracts, native HYPE gasDeploy Solidity as usual; ERC-20 balanceOf sees only this layer

Reads are synchronous: a precompile returns HyperCore state as of the EVM block being built. Writes are asynchronous: CoreWriter only enqueues an action on HyperCore.

Account abstraction modes: not ERC-4337

Hyperliquid "Account Abstraction" is how spot and perp margin share balances. It has nothing to do with ERC-4337 Smart Accounts. Switch with userSetAbstraction / CoreWriter action id 16.

ModeHow balances workWho it's for
Unified (recommended for most users)One balance per asset: spot and that asset's cross-margin perps share itOrdinary trading
Portfolio marginEligible assets (currently HYPE, BTC, USDC, USDT) form one portfolio marginMaximum capital efficiency
Standard / ManualSeparate spot, perp, and per-DEX balances; cross applies inside one DEXMMs, high-frequency, builders
DEX abstractionDiscontinuedDo not use
  • Builder-fee recipient addresses must be in Standard mode or they do not accrue builder fees.
  • Unified and Portfolio margin are capped at about 50k user actions per day; Standard is not.
  • For API users in Unified / PM, balances and holds live in the spot clearinghouse; individual perp DEX user states are not meaningful.
  • CoreWriter USD class transfer (action id 7) only makes sense when spot and perp are booked separately. It is not a universal balance model.

Where assets actually live: HyperCore vs HyperEVM

The same 20-byte address has two ledgers. token.balanceOf(addr) in a contract reads HyperEVM only. Perp margin, Core spot, and open-order holds live on HyperCore.

What you seeWhere it sits
EVM balanceOf / native HYPEHyperEVM
Core spot, perp margin, resting holdsHyperCore clearinghouse
Sub-accountsSeparate Core accounts; not merged with master
Linked Core spot ↔ EVM ERC-20Moved via a system address, not shared automatically

A system address starts with byte 0x20, the rest zeros, with the token index in big-endian at the end (index 200 → 0x2000…00c8). HYPE is the exception: 0x2222…2222, mapping to native EVM gas, not an ERC-20.

  • Core → EVM: sendAsset to that token's system address. The next EVM block, a system transaction calls transfer(recipient, amount) on the linked ERC-20 as the system address. Costs ~200k gas at the next EVM block's base fee.
  • EVM → Core: ERC-20 Transfer to the system address (or send HYPE value to 0x2222…). Credited in the same L1 block that produced the EVM block, after that EVM block is built.
  • Officially there is no check that the system address holds enough supply, or that the contract is a valid ERC-20. Linked bytecode can be arbitrary.
  • If the EVM has extra wei decimals, a non-round amount (not ending in extraWeiDecimals zeros) burns the dust (guaranteed < 1 Wei).

Solidity: read precompiles, write CoreWriter

Reading — staticcall a read precompile (from 0x…0800, no 4-byte selector; ABI-encode the args directly). Prices are raw uint64: divide perps by 10^(6 - szDecimals) and spot by 10^(8 - base szDecimals). An invalid asset or vault consumes all gas passed into that call frame. Cost is about 2000 + 65 * (input_len + output_len).

// schematic; full interface in L1Read.sol / hyper-evm-lib
address constant MARK_PX   = 0x0000000000000000000000000000000000000806;
address constant ORACLE_PX = 0x0000000000000000000000000000000000000807; // not markPx
address constant SPOT_PX   = 0x0000000000000000000000000000000000000808;

function oraclePx(uint32 index) public view returns (uint64) {
    (bool ok, bytes memory ret) = ORACLE_PX.staticcall(abi.encode(index));
    require(ok, "oraclePx failed");                  // failure burns this frame's gas
    return abi.decode(ret, (uint64));
}

Writing — CoreWriter (0x3333…3333) and its only function sendRawAction(bytes). Encoding: 1-byte version (currently 0x01) + 3-byte big-endian action id + ABI params. It burns ~25k gas first; a typical call is ~47k. The official USD class transfer example below only applies when spot and perp are booked separately — do not treat it as a universal transfer in Unified / PM.

interface ICoreWriter { function sendRawAction(bytes calldata data) external; }
ICoreWriter constant CW = ICoreWriter(0x3333333333333333333333333333333333333333);

function usdClassTransfer(uint64 ntl, bool toPerp) external {
    bytes memory action = abi.encode(ntl, toPerp);
    bytes memory data = new bytes(4 + action.length);
    data[0] = 0x01; data[1] = 0x00; data[2] = 0x00; data[3] = 0x07;   // version + action 7
    for (uint256 i = 0; i < action.length; i++) data[4 + i] = action[i];
    CW.sendRawAction(data);                     // emit only — async
}

The action runs as the contract's own HyperCore address, not tx.origin. Order and vault-transfer actions are delayed a few seconds so HyperEVM cannot skip the L1 mempool. A new Core account pays a 1 quote-token activation fee (e.g. 1 USDC) on first receipt; an unactivated address cannot send CoreWriter actions. Contract deployers should activate the contract address on Core first.

Timing: who runs first inside one L1 block

Core → EVM transfers queue until the next EVM block. EVM → Core transfers run in the same L1 block that produced the EVM block, immediately after it is built. On an L1 block that produces EVM:

  1. Build the L1 block
  2. Build the EVM block
  3. Process EVM → Core transfers
  4. Process CoreWriter actions

The CoreWriter account must already exist on HyperCore before the EVM block is built. Initializing via EVM→Core in the same block, then CoreWriter, is rejected.

Gas: small blocks, big blocks, and CoreWriter

HyperEVM splits throughput into two block types and two mempools. EVM block numbers still increase monotonically:

SmallBig
Interval~1 second~1 minute
Gas limit3M30M
ForOrdinary txs, fast confirmLarge deploys

Each address's mempool accepts only the next 8 nonces; txs older than a day are pruned. Opt into big blocks with Core action evmUserModify.usingBigBlocks: true (a HyperCore user flag — you must already be a Core user). Estimate the next big-block base fee with RPC bigBlockGasPrice, not ordinary gasPrice.

A failed precompile burns that frame's gas: do not forward all remaining gas. CoreWriter itself burns ~25k; still budget for later HyperCore execution and the 200k-gas Core→EVM transfer.

Off-chain API: submission only; matching stays on HyperCore

High-frequency orders, cancels, and leverage changes go over REST / WebSocket, not HyperEVM. That is not an off-chain order book: after the signed action hits the exchange endpoint, matching, priority, and fills still happen on HyperCore.

Authority: master wallet, agent, sub-account

An API wallet (an "agent" in the docs) only signs: it can trade, change leverage, and walk you into liquidation. It cannot withdraw and holds no funds. Query balances with the master or sub-account address; the agent address returns empty.

  • Nonces follow the signer (the agent address), not the user being proxied. Each signer keeps the 100 highest nonces; a new nonce must be larger than the smallest in that set and unused; the window is (T-2 days, T+1 day) around the block timestamp.
  • One agent signing for a master, a vault, and a sub-account shares one nonce set. Use a different agent per process / sub-account.
  • When an agent is deregistered, expires, or the master is empty, nonce state may be pruned. Never reuse a deregistered agent address — after prune, old signatures can replay.
  • ApproveBuilderFee must be signed by the master wallet, not an agent.

Cross-layer vs cross-chain

HyperCore and HyperEVM are two layers of one HyperBFT L1, not two chains, and there is no seven-day challenge window. Leaving the L1 is a different story:

  • USDC: prefer Circle CCTP to mint natively on Hyperliquid. The legacy Arbitrum bridge is deprecated.
  • Legacy bridge: mainnet 0x2df1…3df7. Minimum deposit 5 USDC; below that it is never credited and is lost. Withdrawals are signed only on Hyperliquid; validators release on Arbitrum in about 3–4 minutes.

Do not assume an EVM transfer is Core margin, or that a CCTP mint and a Core credit are one atomic transaction.

Proof of reserve: assets are not solvency

Three different things:

  1. Native USDC / CCTP: Circle's mint/burn model; redemption is CCTP, not a Hyperliquid lock-mint.
  2. Legacy Arbitrum bridge escrow: USDC still locked in the bridge contract. That is the historical path's reserve, not "all HyperCore USDC."
  3. Linked Core / EVM tokens: the system address on EVM should hold enough to cover Core redeemable supply; also check code hash, mint/upgrade authority, and decimals. Official docs do not perform this check for you.

PoR does not prove solvency. HLP, resting holds, lending / rehypothecation, and portfolio-margin cross-collateral never appear in "how many tokens sit at the system address."

Smart-contract security (for developers)

  • Async writes are the number-one trap. "Place then read the position" inside one EVM tx does not work. Same-block activate-then-CoreWriter is rejected.
  • Do not mix up precompile addresses. 0x0806 markPx, 0x0807 oraclePx, 0x0808 spotPx. Invalid input burns gas; raw prices need decimal scaling.
  • EVM balanceOf is not Core margin. Linked transfers have no official supply check; non-round wei is burned.
  • Action encoding must be byte-exact. Use hyper-evm-lib; do not assemble bytes by hand. USD class transfer is not a universal transfer.
  • Dual blocks and 8 nonces. Large deploys need big blocks; the mempool only takes the next 8 nonces.

User investment risk

Perpetuals carry far more risk than spot:

Leverage liquidationMove against you past maintenance margin and you are force-closed — principal can go to zero. An agent can put you there.
Funding rateWhen longs and shorts are imbalanced you continually pay the other side.
HLP vault drawdownDepositing into HLP makes you the market-maker / liquidation counterparty; extreme moves can lose money. PoR does not cover this.
Auto-deleveraging (ADL)If a counterparty blows up and the insurance fund is short, winning positions may be partially force-closed.
Mark priceLiquidation uses mark / oracle, not the last trade.
