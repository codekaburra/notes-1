跨鏈交易結構（二）：Solana 與 Token-2022

先換一個模型：帳戶、程式與指令

接續 Ethereum 交易結構；Cosmos 與 IBC 見第三篇。本篇以常見 legacy／v0 message 模型說明 Solana；其他版本應依目標叢集與 SDK 規格解析。Solana 交易把 signatures 與 message 分開；message 包含帳戶清單和一組 instructions。Token-2022 則是處理 token 的程式，不是新的交易簽章演算法或 envelope。

程式執行邏輯，accounts 存狀態。每個 instruction 指定 program、需要的 accounts 與 data；可以在一筆交易依序做多個操作。程式再呼叫另一程式是 CPI。與 Ethereum 對照：program ID 類似呼叫目標，instruction data 類似 calldata，但不能把 Ethereum 的單一 to／value 直接套過來。

交易結構與簽署範圍

Transaction
├─ signatures[]          每份 Ed25519 簽章為 64 bytes
└─ message
   ├─ header            signer 與 read-only 數量
   ├─ accountKeys[]     共用的帳戶／program 地址
   ├─ recentBlockhash   交易有效期相關的近期 blockhash
   └─ instructions[]
      ├─ programIdIndex
      ├─ accounts[]     指向帳戶清單的索引
      └─ data           由目標程式定義的 bytes

v0 message 另外包含 addressTableLookups[]

legacy／v0 的 signer 是 static account keys 前方由 header 指定的帳戶，簽章依順序對應；fee payer 位於第一個帳戶並簽署，其第一份簽章也是常用 transaction ID。這不像 Ethereum 以完整 signed bytes 的 Keccak hash 當交易 ID。所有 signer 簽同一份序列化 message；改 blockhash、指令或帳戶後，相關既有簽章都需重做。

v0 的 ALT 用查表引用減少地址在 message 中的空間，不會自動增加權限；從表載入的地址不能作為交易 signer。解碼 instruction 索引時要解析完整帳戶集合，不能只看 static keys。ALTs、可用容量與費用限制應依版本與叢集核對，不能假設任何版本都相同。

簽署、費用與送出後的狀態

  1. 建立 instructions，標示 signer／writable，設定 fee payer。
  2. 取得 blockhash 與 lastValidBlockHeight；必要時設定 Compute Budget 指令的 CU limit／price。
  3. 模擬、核對帳戶與資產變化，再收集所有 signer 的簽章。
  4. 送出相同 signed bytes，追蹤 signature status、meta.err 與 commitment；RPC 接受不等於執行成功。
  5. 若 blockhash 過期，要先確認舊交易是否已執行，再重建並重新簽署。Durable nonce 是另一條流程，不直接套用一般過期判斷。

Solana 不以每個使用者的 Ethereum 式連續 nonce 作一般交易模型。不要用固定幾秒推算是否過期，應追蹤取得的有效高度。交易通常原子執行：失敗時業務狀態回滾，但仍可能支付費用；不要把費用扣款誤判為 token 轉帳成功。

Priority fee 與所要求的 CU limit、CU price 有關，不應只看實際消耗。建立 ATA 所需的 rent-exempt 資金也不同於交易 fee。結果需查看 meta.err、logs、innerInstructions、pre/post balances 與 token balances；確認真實經濟效果。

Token 模型：Mint、Token Account、ATA

物件用途容易混淆
Mint定義 token、decimals、供給與 authorities／extensionsticker 與 metadata 不是 token 身分
Token account持有某一 mint 的餘額，記錄持有人 authority一個使用者可有多個同 mint 的 token accounts
ATA依 wallet authority、token program ID 與 mint 推導的慣例 token account不是一般 SOL wallet 地址，也不是唯一可能持幣帳戶
Program owneraccount 外層 owner，表示管理其資料的程式不同於 token account 資料裡的 owner／authority

原生 SOL 常透過 System Program 轉移 lamports；SPL token 則透過對應 Token Program，移動 source／destination token accounts 的餘額。資產識別應確認 cluster、mint 與 mint 的 program owner；不能只看名稱。

Token-2022 是什麼，為什麼不能當普通 token

Token-2022 是不同地址上的 Token Extensions Program，保留基本 token 功能並擴充行為。不是所有 Token-2022 token 都有費用或 hook；要讀每個 mint 與 account 的實際 extensions。同一 ATA Program 支援兩種 token programs，但 ATA 推導需使用正確 token program ID。

Extension行為／整合風險防線
TransferFeeConfig收款者可用淨額低於發送額；另有 withheld fee 記錄讀當期配置、cap 與 authority；按淨入帳算存款／minOut
TransferHook轉帳觸發外部程式 CPI，可能需額外 accounts 或拒絕轉帳使用支援 hook 的 builder；驗證 hook、額外 accounts 與升級權限
PermanentDelegate特定 authority 可對該 mint 的 token accounts 行使轉移／銷毀權限揭露與評估其權限，不假設只有持有人可動幣
NonTransferable／DefaultAccountState可能限制轉移或讓新帳戶預設 frozen確認交易與退出是否可用，評估 freeze／thaw authority
MemoTransfer／CpiGuard帳戶可能要求 memo，或限制特定 CPI 操作讀 account extensions，測直接操作與 CPI 路徑
InterestBearing／Scaled UI Amount顯示數量可有額外換算語意區分 raw amount 與 UI；不能把顯示增長當成新增底層資產收益

有些 extensions 不相容，且不少配置需在 mint／account 初始化前規劃。資料長度可變，應用支援 extensions 的 decoder，不硬寫固定 account size，也不假設之後可任意補上功能。

完整例子：Alice 轉 100 顆 Token-2022 給 Bob

讀 mint → 確認 Token-2022 owner、decimals、extensions
  → 找 Alice source 與 Bob destination token account
  → 必要時建立 Bob ATA（由 payer 支付所需資金）
  → 組 TransferChecked 或適用的 extension-aware 指令
  → 加入 memo／hook 額外 accounts（若需要）
  → 模擬、簽署、送出 → 核對 meta.err 與淨餘額

假設當期 transfer fee = 1%，cap 不影響本例，且數量無取整歧義：Alice 的 token amount 扣 100，Bob 可用餘額增加 99，1 顆記為 withheld fee。這不是 network SOL fee，也不表示費用立即進入某個 fee wallet。實際需使用官方整數與取整規則。

若協議收到 99 卻按 100 發 shares，會產生會計缺口；若多跳 swap 每段都有 fee，淨輸出需逐段計算。對不支援的 extensions 明確拒絕，比盲目換 program ID 更安全。此流程為設計示意，未附可直接廣播的完整 SDK 專案。

開發驗收與 PM 市場風險

  • 測錯 mint／program owner、缺 signer、read-only 帳戶、錯誤 ATA 推導、過期 blockhash與多簽收集後改 message。
  • 測 fee 的零值、cap、取整與配置切換；以實際淨入帳記帳並檢查 withheld fee。
  • 測 hook 缺 accounts、拒絕、配置更新，以及可升級程式的 authority；不能只在無 extensions 的 mint 上測成功。
  • 測凍結、delegate、memo、CPI 限制、ATA 不存在與資金不足；追蹤重送和 timeout，避免業務重複。
  • PM 建立 extension 支援矩陣：wallet、DEX、借貸、託管、橋與退出路徑分別驗證。支援 Token-2022 不代表支援其每個 extension。

流動性與可退出性會受轉帳政策、管理權限、fee 與 hook 可用性影響。上架前讀配置與 authority，持續監控可變設定；不要只因 token 可顯示就認定能成交或安全作抵押。

Accounts, programs, instructions

Following Ethereum transaction structures, this article explains common Solana legacy/v0 messages. Cosmos and IBC are covered in Part III. Other versions require their own cluster and SDK specifications. Transactions contain signatures and a message; Token-2022 is a token program, not a signature or envelope type.

Programs execute logic; accounts hold state. Instructions specify a program, accounts and data. Several instructions can form one transaction. Program-to-program calls are CPIs.

Message structure and signatures

Transaction
├─ signatures[]: 64-byte Ed25519 signatures
└─ message
   ├─ header
   ├─ accountKeys[]
   ├─ recentBlockhash
   └─ instructions[]: programIdIndex, account indexes, data
v0 also includes addressTableLookups[]

Legacy/v0 signers occupy the required prefix of static keys. The first key is the signing fee payer; its signature is the usual transaction ID, unlike Ethereum's hash of the signed transaction. All signers sign the same serialized message. Changing blockhash, accounts or instructions requires new signatures.

V0 address lookup tables compress address references, not permissions. Loaded addresses cannot be transaction signers. Resolve the complete account list when decoding instruction indexes. Limits differ by version and cluster.

Signing, fees and confirmation

  1. Build instructions and signer/writable metadata; choose payer.
  2. Fetch blockhash and lastValidBlockHeight; configure compute budget where needed.
  3. Simulate, inspect effects and collect signatures.
  4. Submit signed bytes; track signature status, meta.err and commitment.
  5. Before rebuilding an expired transaction, check whether it already executed. Durable nonce transactions use a separate lifecycle.

Ordinary Solana transactions do not use Ethereum's per-sender sequential nonce model. Track validity height rather than a fixed timer. Failed transactions can still charge fees while business state rolls back. Priority fees depend on requested compute limit and price; ATA rent-exempt funding is separate. Inspect logs, inner instructions and actual balance changes.

Mint, token account, ATA

A mint defines the token, decimals, supply and authorities. A token account holds one mint's balance and its authority. An ATA is the conventional account derived from wallet authority, token program ID and mint; other token accounts may exist. The account's outer program owner differs from its token-holder authority.

Native SOL uses lamports and the System Program; token transfers use the applicable token program and source/destination token accounts. Identify assets by cluster, mint and mint program owner, not ticker.

Token-2022 extensions

Token-2022 is a distinct program with optional mint and account extensions. Not every mint charges fees or uses a hook. The same ATA Program supports both token programs, with the correct token program included in derivation.

  • TransferFeeConfig: net received amount can be lower; track withheld fees, current configuration and authorities.
  • TransferHook: external CPI, extra accounts and possible rejection; inspect dependencies and upgrade authority.
  • PermanentDelegate: designated authority can transfer or burn tokens across accounts of that mint.
  • NonTransferable / DefaultAccountState: transfers or new accounts may be restricted or frozen.
  • MemoTransfer / CpiGuard: account-level conditions can change transfer and CPI compatibility.
  • InterestBearing / Scaled UI Amount: distinguish display conversion from raw balances and actual asset yield.

Some extensions are incompatible, and many require planning before initialization. Use extension-aware decoders rather than fixed-size assumptions; do not assume features can always be added later.

Worked transfer: Alice sends 100 tokens

Inspect mint owner, decimals and extensions
  → resolve source and destination; create ATA if needed
  → build checked / extension-aware transfer
  → add required memo and hook accounts
  → simulate, sign, submit, inspect net balances

With a 1% active fee, a non-binding cap and no rounding ambiguity, sending 100 credits 99 spendable tokens and withholds 1. This is separate from SOL fees and is not necessarily an immediate payment to a fee wallet. Apply actual integer rounding rules.

A vault issuing shares for 100 after receiving 99 creates an accounting gap. Model each fee-bearing swap leg and reject unsupported extensions. This is an integration sketch, not a runnable SDK project.

Acceptance and market risk

  • Test wrong mint/program, missing signer, writable flags, ATA derivation, expiry and message mutation after partial signing.
  • Test fee caps, rounding, configuration changes and net accounting.
  • Test missing hook accounts, hook rejection and authority changes.
  • Test frozen accounts, delegates, memo/CPI restrictions, missing ATA and retry ambiguity.
  • Maintain separate support matrices for wallets, DEXs, lending, custody, bridges and exits.

Token-2022 support does not imply support for every extension. Transfer policy, mutable authority and hook availability can impair liquidity or exits. Monitor configuration rather than relying on token display or branding.
