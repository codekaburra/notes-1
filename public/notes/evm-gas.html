EVM Gas 與 EIP-1559

2026-09-19 · EVM · LONDON 硬分叉 · 費用市場 · 開發者指南

London 硬分叉（2021-08-05）改寫了以太坊的收費方式。這則講清楚之前是什麼、之後是什麼、為什麼要改，以及作為工程師你該怎麼設參數、怎麼省。

三句話版本
  • London 之前是第一價格拍賣：你盲目出一個 gasPrice，出高了白付、出低了卡住。體驗差的根源是你在猜別人出多少。
  • London 之後費用拆成兩塊：base fee 由協議依區塊擁擠度自動定價並銷毀，priority fee 是你給驗證者的小費。你只需設一個能接受的上限。
  • 重點澄清：EIP-1559 沒有讓 gas 變便宜，它讓價格可預測。真正讓費用下降的是 L2 與 EIP-4844 的 blob。

誰讀哪裡：初學者 → 「兩個時代的對照」與「一筆交易的費用怎麼算」；工程師 → 參數設定與 gas 優化；PM → 市場背景與「為什麼費用仍會暴漲」。

市場背景

那個「銷毀 450 萬枚」的數字常被當成 EIP-1559 的賣點，但銷毀其實是副作用而非目的。真正的目的是修好費用市場的使用者體驗；ETH 因此具備通縮可能，是附帶結果。

兩個時代的對照

base fee 怎麼自動調整

協議設定每個區塊的目標用量為上限的一半（目前目標約 1,500 萬 gas、上限約 3,000 萬）。下一個區塊的 base fee 依上一個區塊的滿載程度調整，單次最多變動 ±12.5%。

一筆交易的費用怎麼算

Type 2（EIP-1559）交易由你設兩個參數：

maxPriorityFeePerGas  // 小費上限：你願意給驗證者多少
maxFeePerGas          // 總價上限：base fee + 小費，加起來最多多少
// 實際計費（每單位 gas）
effectiveGasPrice = min(maxFeePerGas, baseFeePerGas + maxPriorityFeePerGas)

// 總花費
totalFee = gasUsed × effectiveGasPrice

// 分配
銷毀    = gasUsed × baseFeePerGas
驗證者  = gasUsed × (effectiveGasPrice - baseFeePerGas)
退還    = gasUsed × (maxFeePerGas - effectiveGasPrice)   // 多設的上限不會被拿走

前端怎麼設（viem）

import { parseGwei } from "viem";

// 多數情況：讓 viem 自己估，它會讀鏈上 base fee 並加上合理緩衝
const hash = await walletClient.sendTransaction({ to, value });

// 需要自己控制時：分開設上限與小費
const block = await publicClient.getBlock();
const base = block.baseFeePerGas;            // 當前 base fee
const tip  = parseGwei("1");                 // 小費

await walletClient.sendTransaction({
  to, value,
  maxPriorityFeePerGas: tip,
  // 抓 2 倍 base fee 當緩衝：即使連續數個滿載區塊也還撐得住
  maxFeePerGas: base * 2n + tip,
});

那個 base * 2n 不是隨便抓的：base fee 每區塊最多漲 12.5%，2 倍緩衝約可撐過 6 個連續滿載區塊（1.125⁶ ≈ 2.03），對多數交易足夠。

Gas 優化：省在哪裡

以下依實際效益排序。前兩項的量級遠大於其餘：

手段為什麼有效
少碰 storage冷讀取與寫入是 EVM 最貴的操作，比運算貴好幾個數量級。能算出來的就不要存。
變數打包同一個 32 bytes 槽位能塞下多個小變數（如兩個 uint128），一次寫入取代兩次。順序很重要——宣告順序決定打包結果。
transient storageEIP-1153 的 TSTORE/TLOAD 只在交易內有效、結束即棄，比真正的 storage 便宜非常多。適合重入鎖與暫時性記帳。
calldata 取代 memory外部函式的唯讀參數用 calldata 可省下複製成本。
uncheckedSolidity 0.8 預設每次算術都檢查溢位。在你能證明不會溢位的迴圈計數器上，跳過檢查有實質節省。
用事件取代儲存只給鏈下讀取的歷史資料，寫成 event 比存進 storage 便宜得多。

但先量測再優化。用 forge test --gas-report 找出真正昂貴的函式，別把時間花在省幾百 gas 的微調上——一次多餘的 SSTORE 抵得過幾十處迴圈優化。

L2 與 blob：費用真正下降的地方

L2 上的交易費由兩部分組成：L2 執行成本（很便宜）加上把資料發布到 L1 的成本（過去是主要開銷）。EIP-4844 引入 blob——一種專為 rollup 設計的資料格式，有獨立的費用市場，與一般交易的 base fee 分開計價，且資料只保留一段時間後即可丟棄。

結果是 L2 費用大幅下降。但也帶來新的波動來源：blob 的供需自成一個市場，當多條 rollup 同時搶 blob 空間時，blob base fee 會獨立飆升，此時 L2 費用會上漲而 L1 一般交易費卻毫無變化。想了解細節，見 Optimistic Rollup 與 ZK Rollup 兩則。

開發者注意事項

  • 不要把 gas 成本寫死：硬分叉會改變 opcode 定價（歷史上多次發生）。寫死的 gas 上限在未來的分叉後可能失效。
  • 避免 transfer 與 send：它們固定只轉 2300 gas，收款方若是合約可能因此失敗。改用 call{value: x}("") 並檢查回傳值（記得搭配重入防護）。
  • 估算要留緩衝：eth_estimateGas 在當前狀態下模擬，實際執行時狀態可能已變。常見做法是乘上 1.2–1.5 倍。
  • 退款規則已縮減：清空 storage 的 gas 退款上限在 London 時被大幅調低，別再依賴「gas token」那類技巧。
  • L1 與 L2 的費用模型不同：在 L2 上，calldata 大小往往比執行步數更影響成本。

使用者風險

風險說明
上限設太低 → 交易卡住base fee 漲過你的 maxFeePerGas，交易會一直待在 mempool。可用相同 nonce 提高費用重送來取代。
小費設太低 → 排序落後在擁擠時段，小費太低的交易可能延遲很久，對有時效的操作（如避免清算）可能致命。
費用尖峰無法預防base fee 可在兩分鐘內漲數倍。非緊急交易建議避開熱門鑄造或清算潮。
失敗的交易仍要付費交易 revert 一樣消耗 gas。滑點設定不當導致失敗，錢照樣花掉。
MEV提高小費不會保護你不被夾擊。大額交易應考慮私有 mempool。

EVM Gas and EIP-1559

2026-09-19 · EVM · LONDON HARD FORK · FEE MARKET · DEVELOPER GUIDE

The London hard fork (2021-08-05) rewrote how Ethereum charges for blockspace. This note covers what came before, what came after, and why it changed — plus how to set the parameters and where the savings actually are.

In three lines
  • Before London it was a first-price auction: you guessed a gasPrice, overpaid if too high, got stuck if too low. The bad experience came from having to guess what everyone else would bid.
  • After London the fee splits in two: a base fee priced by the protocol from congestion and then burned, plus a priority fee tip to the validator. You only set a ceiling you can live with.
  • An important correction: EIP-1559 did not make gas cheaper, it made the price predictable. What actually lowered fees was L2s and EIP-4844 blobs.

Where to start: beginners → "The two eras" and "How a fee is computed"; engineers → parameters and gas optimisation; PMs → market background and "why fees still spike".

That "4.5M ETH burned" number gets cited as the point of EIP-1559, but the burn is a side effect, not the goal. The goal was fixing the fee market's user experience; ETH's potential deflation is a consequence.

The two eras

How the base fee adjusts

The protocol targets each block at half the limit (currently ~15M gas target, ~30M limit). The next block's base fee adjusts from how full the last one was, by at most ±12.5% per block.

How a fee is computed

A type 2 (EIP-1559) transaction takes two parameters from you:

maxPriorityFeePerGas  // tip ceiling: what you will pay the validator
maxFeePerGas          // total ceiling: base fee + tip, combined maximum
// What you actually pay, per unit of gas
effectiveGasPrice = min(maxFeePerGas, baseFeePerGas + maxPriorityFeePerGas)

// Total
totalFee = gasUsed x effectiveGasPrice

// Where it goes
burned    = gasUsed x baseFeePerGas
validator = gasUsed x (effectiveGasPrice - baseFeePerGas)
refunded  = gasUsed x (maxFeePerGas - effectiveGasPrice)   // headroom is never taken

Setting it from the front end (viem)

import { parseGwei } from "viem";

// Usually: let viem estimate — it reads the on-chain base fee and adds sane headroom
const hash = await walletClient.sendTransaction({ to, value });

// When you need control: set the ceiling and the tip separately
const block = await publicClient.getBlock();
const base = block.baseFeePerGas;            // current base fee
const tip  = parseGwei("1");                 // the tip

await walletClient.sendTransaction({
  to, value,
  maxPriorityFeePerGas: tip,
  // 2x base fee as headroom: survives several consecutive full blocks
  maxFeePerGas: base * 2n + tip,
});

That base * 2n is not arbitrary: at a maximum of +12.5% per block, 2x headroom survives about six consecutive full blocks (1.125⁶ ≈ 2.03), which is enough for most transactions.

Gas optimisation: where the savings are

Ordered by real impact. The first two dwarf the rest:

TechniqueWhy it works
Touch storage lessCold reads and writes are the EVM's most expensive operations, orders of magnitude above computation. If it can be derived, do not store it.
Pack variablesOne 32-byte slot holds several small variables (two uint128s, say), turning two writes into one. Declaration order decides the packing.
Transient storageEIP-1153's TSTORE/TLOAD live only for the transaction and cost far less than real storage. Ideal for reentrancy locks and scratch accounting.
calldata over memoryRead-only parameters of external functions avoid a copy when declared calldata.
uncheckedSolidity 0.8 checks every arithmetic op for overflow. On loop counters you can prove safe, skipping the check saves real gas.
Events instead of storageHistory only read off-chain is far cheaper as an event than as stored state.

But measure before optimising. Use forge test --gas-report to find the genuinely expensive functions rather than shaving a few hundred gas — one avoidable SSTORE outweighs dozens of loop micro-optimisations.

L2s and blobs: where fees really fell

An L2 transaction fee has two parts: L2 execution (very cheap) and publishing data to L1 (historically the bulk). EIP-4844 introduced blobs — a data format built for rollups with its own fee market, priced separately from ordinary transactions and discarded after a retention window.

L2 fees dropped sharply as a result. It also created a new source of volatility: blob space has its own supply and demand, so when many rollups compete for it the blob base fee spikes independently — L2 fees rise while ordinary L1 fees do not move at all. For details see the Optimistic Rollup and ZK Rollup notes.

Developer notes

  • Never hardcode gas costs: hard forks reprice opcodes, and have several times. A hardcoded gas stipend can break after a future fork.
  • Avoid transfer and send: they forward a fixed 2300 gas, which fails when the recipient is a contract. Use call{value: x}("") and check the return (with reentrancy protection).
  • Pad your estimates: eth_estimateGas simulates against current state, which may have changed by execution time. Multiplying by 1.2–1.5 is common.
  • Refunds were cut back: the gas refund for clearing storage was sharply reduced at London — "gas token" tricks no longer work.
  • L1 and L2 fee models differ: on an L2, calldata size often matters more than execution steps.

User risk

RiskWhat it is
Ceiling too low → stuckIf the base fee climbs past your maxFeePerGas, the transaction sits in the mempool. Replace it by resending with the same nonce at a higher fee.
Tip too low → slow orderingIn congestion a low tip can delay you a long time, which matters for time-sensitive actions like avoiding liquidation.
Spikes cannot be preventedThe base fee can multiply within minutes. For non-urgent transactions, avoid popular mints and liquidation waves.
Failed transactions still costA revert consumes gas. A badly set slippage that fails still spends your money.
MEVA bigger tip does not protect you from being sandwiched. Large trades should consider a private mempool.
